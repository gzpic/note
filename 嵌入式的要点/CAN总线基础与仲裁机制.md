# CAN 总线基础与仲裁机制

## 1. CAN 的核心特点

CAN（Controller Area Network）可以理解为一种：

> **多主、广播式、基于消息 ID、支持优先级仲裁、硬件错误检测与故障隔离的面向帧总线协议。**

它和 UART 最大的区别之一是：CAN 不是连续字节流，而是天然以“帧”为单位通信。

---

## 2. CAN 数据帧结构

经典 CAN 数据帧大体结构：

```text
SOF → 仲裁段 → 控制段 → 数据段 → CRC → ACK → EOF
```

主要字段：

| 字段 | 作用 |
|---|---|
| SOF | 帧起始 |
| Identifier | 消息 ID，同时决定仲裁优先级 |
| RTR | 区分数据帧与远程帧 |
| IDE | 区分标准帧和扩展帧 |
| DLC | 数据长度 |
| Data | 有效数据 |
| CRC | 差错检测 |
| ACK | 接收确认 |
| EOF | 帧结束 |

经典 CAN：
- 标准帧 ID：11 bit
- 扩展帧 ID：29 bit
- 单帧数据最大：8 Byte

---

## 3. CAN 的 ID 不是设备地址

CAN 没有像很多点对点协议那样固定的“源地址 + 目的地址”。

CAN ID 更接近：

> **“这一帧数据是什么类型，以及它的优先级是多少。”**

例如：

```text
ID 0x101 → 电机转速
ID 0x102 → 电机温度
ID 0x200 → 电机控制命令
```

所有节点都可以看到总线上的报文，再通过 CAN 硬件过滤器筛选自己关心的 ID。

因此可以概括为：

> **广播 + ID 过滤。**

---

## 4. CAN 仲裁

多个节点可以同时尝试发送，因此 CAN 属于多主总线。

CAN 中：

```text
0 = 显性位 Dominant
1 = 隐性位 Recessive
```

显性 0 会覆盖隐性 1。

仲裁时各节点一边发送，一边监听总线实际状态。

例如：

```text
节点 A 发送：0
节点 B 发送：1
总线实际：0
```

节点 B 会发现：

```text
我发的是 1
但总线读回来是 0
```

于是节点 B 判断自己输了仲裁，并退出本轮发送。

因此：

> **CAN ID 数值越小，通常优先级越高。**

CAN 的这种机制叫：

> **无破坏性仲裁**

输掉仲裁的节点不会破坏正在发送的高优先级报文，只会等待下次总线空闲再发送。

---

## 5. CAN 的校验是谁完成的

CAN 协议层的大多数工作都是由 **CAN 控制器硬件** 自动完成的。

例如：

- CRC 计算与检查
- ACK 检查
- 位填充 Bit Stuffing
- 仲裁
- 位错误检测
- 格式错误检测
- CRC 错误检测
- 错误帧处理
- TEC / REC 错误计数
- 自动重发（取决于配置）

软件通常主要关心：

```text
ID
DLC
Data
```

因此发送一帧时，应用软件通常只需要把 ID、长度、数据交给 CAN 外设。

### 注意

CAN 自带 CRC 主要保证：

> **这帧数据在总线上传输过程中有没有被破坏。**

它不能保证业务数据本身一定正确。

例如软件本来应该发送 25℃，但程序错误算成了 250℃，CAN CRC 仍然可能完全正确。

因此高可靠系统有时还会在应用层额外加入：

- Counter
- Sequence Number
- 应用层 CRC
- Checksum

这部分才通常由软件完成。

---

## 6. CAN 有几根线

### MCU 与 CAN 收发器之间

一般有两根逻辑信号：

```text
CAN_TX
CAN_RX
```

### CAN 收发器与总线之间

一般有两根差分线：

```text
CAN_H
CAN_L
```

实际工程中通常还会带 GND，所以线束常见：

```text
CAN_H
CAN_L
GND
```

---

## 7. CAN_TX / CAN_RX 与 CAN_H / CAN_L 的关系

它们不是一对一对应关系。

错误理解：

```text
CAN_TX → CAN_H   ×
CAN_RX → CAN_L   ×
```

正确关系：

```text
MCU
 CAN_TX ─────→ CAN 收发器
 CAN_RX ←───── CAN 收发器
                  │
             CAN_H + CAN_L
                  │
               CAN 总线
```

CAN_H 和 CAN_L 是一对共同表示同一个 bit 的差分信号线。

发送时：

```text
MCU TX
  ↓
CAN 收发器
  ↓
同时驱动 CAN_H 与 CAN_L
```

接收时：

```text
CAN_H + CAN_L
      ↓
CAN 收发器判断差分电压
      ↓
MCU RX
```

因此：

> **TX 和 RX 在 MCU 侧是两根逻辑信号，但最终都通过同一对 CAN_H / CAN_L 总线进行通信。**

---

## 8. CAN_H 和 CAN_L 是否可以理解成“一根线”

物理上不能说是一根线，因为它确实是两根导线。

但从“信号通道”的角度，可以理解成：

> **CAN_H + CAN_L 共同组成一条差分通信通道。**

它们不是各自独立承载 TX 和 RX。

---

## 9. CAN_TX / CAN_RX 的 GPIO 模式

典型 MCU 中：

### CAN_TX

通常配置为：

```text
复用推挽输出
Alternate Function Push-Pull
```

### CAN_RX

通常配置为：

```text
输入模式 / 复用输入
```

新一些的 STM32 系列中，选择对应 Alternate Function 后，输入通路也会自动连接到 CAN 外设。

结构可以理解为：

```text
MCU 内部 CAN 外设
   │
   ├── TX → GPIO 复用推挽 → CAN 收发器 TXD
   │
   └── RX ← GPIO 输入/复用 ← CAN 收发器 RXD
```

---

## 10. CAN 为什么不用像 I²C 那样把 TX 配成开漏

这是 CAN 和 I²C 非常重要的区别。

### I²C

I²C 的 SDA / SCL 使用：

> **开漏输出 + 上拉电阻**

设备不能主动输出高电平，只能：

- 拉低
- 或释放总线

这样多个设备同时操作时，不会出现：

```text
一个 GPIO 强拉高
另一个 GPIO 强拉低
```

导致的大电流硬冲突。

因此 I²C 的“线与”是在总线 GPIO 电气层直接实现的。

---

### CAN

MCU 的 CAN_TX 通常仍然是推挽输出。

但 CAN_TX **并没有直接连接到共享总线**。

中间还有专用的：

> **CAN Transceiver（CAN 收发器）**

结构：

```text
MCU CAN_TX / CAN_RX
        │
        ↓
   CAN Controller
        │
        ↓
   CAN Transceiver
        │
        ↓
   CAN_H / CAN_L
```

真正处理总线电气层“显性覆盖隐性”的，是 **CAN 收发器的专用输出级**。

因此：

| 协议 | 如何避免仲裁时电气冲突 |
|---|---|
| I²C | 开漏 GPIO + 上拉电阻 |
| CAN | CAN 收发器专用差分驱动电路 |

需要特别区分：

> **CAN 控制器负责协议逻辑；CAN 收发器负责总线电气层。**

CAN 控制器主要处理：
- 帧格式
- 仲裁逻辑
- CRC
- ACK
- 错误检测
- 错误计数

CAN 收发器主要处理：
- TXD/RXD 与 CAN_H/CAN_L 之间的电平转换
- 差分驱动
- 显性 / 隐性物理电平
- 总线电气兼容

---

## 11. CAN 与 UART 的 TX/RX 区别

UART：

```text
TX → 独立发送线
RX ← 独立接收线
```

发送和接收有独立线路，因此 UART 可以天然做全双工。

CAN：

```text
MCU TX/RX
    ↓
CAN 收发器
    ↓
CAN_H / CAN_L
```

真正的总线只有这一对共享差分线。

因此 CAN 总线本质上是：

> **共享总线、半双工通信。**

---

## 12. 为什么 CAN 可以“边发边听”

发送时，CAN 控制器不仅让 TX 输出数据，还同时通过 RX 观察总线实际状态。

可以理解成：

```text
CAN Controller
     │
     ├── TX → 我想发什么
     │
     └── RX ← 总线上实际上是什么
```

如果：

```text
自己发送 1
总线读回 0
```

说明其他节点正在发送显性 0。

在仲裁字段中，这意味着：

> 当前节点输掉了仲裁。

这就是 CAN 仲裁能够正常工作的基础之一。

---

## 13. 一句话总结

CAN 的完整通信链路可以记成：

```text
应用程序
   ↓
ID + DLC + Data
   ↓
CAN 控制器
   ↓
帧格式 / 仲裁 / CRC / ACK / 错误处理
   ↓
CAN_TX / CAN_RX
   ↓
CAN 收发器
   ↓
CAN_H / CAN_L
   ↓
共享差分总线
```

最重要的几个结论：

1. CAN 是面向帧的广播总线。
2. CAN ID 表示消息类型，同时决定优先级。
3. CAN ID 越小，通常优先级越高。
4. CAN 使用显性 0、隐性 1 进行无破坏性仲裁。
5. CRC、ACK、仲裁、错误检测等主要由 CAN 控制器硬件完成。
6. MCU 侧是 CAN_TX / CAN_RX。
7. 总线侧是 CAN_H / CAN_L。
8. CAN_TX 并不是只对应 CAN_H，CAN_RX 也不是只对应 CAN_L。
9. CAN_H / CAN_L 是一对共同承载同一个差分信号的线路。
10. MCU CAN_TX 通常是复用推挽输出，RX 通常是输入/复用输入。
11. I²C 靠开漏 + 上拉避免电气冲突。
12. CAN 靠专用 CAN 收发器实现显性/隐性与差分总线电气特性。
13. CAN 控制器负责协议层，CAN 收发器负责物理电气层。

## 14. I²C 仲裁时为什么主要看“发 1、读 0”

I²C 的 SDA 是开漏结构，设备实际上只有两种动作：

- **拉低 SDA** → 表示 0
- **释放 SDA** → 表示 1，由上拉电阻把总线拉高

也就是说：

> **I²C 设备不能主动把 SDA 拉高。**

因此总线满足“0 优先于 1”的线与关系。

### 发送与读取组合

| 自己发送 | SDA 实际读取 | 含义 |
|---|---|---|
| 0 | 0 | 正常，继续发送 |
| 1 | 1 | 正常，继续发送 |
| 1 | 0 | 有别的主机拉低 SDA，当前主机输掉仲裁 |
| 0 | 1 | 正常电气条件下一般不应该发生 |

原因是：

- 当自己发送 0 时，本节点正在主动拉低 SDA；
- 其他节点即使想发送 1，也只是“释放总线”；
- 因此别人无法把已经被拉低的 SDA 强行变成高电平。

所以 I²C 仲裁最关键的判据就是：

> **自己想发 1（释放 SDA），但读回来是 0（有人拉低）→ 输掉仲裁。**

### “SDA 高时谁都能拉低”怎么理解

如果 SDA 当前为高，说明没有任何节点在拉低，电平是由上拉电阻维持的；这时任意节点都可以主动把 SDA 拉低。

如果 SDA 当前为低，说明至少有一个节点正在拉低。其他节点无法主动把 SDA 拉高。

只有 **所有正在拉低 SDA 的节点都释放总线之后**，SDA 才会被上拉电阻重新拉回高电平。

因此准确表述是：

> **SDA 高电平表示所有设备都在释放总线；SDA 低电平表示至少有一个设备在拉低。低电平不能被其他设备主动拉高，只能等所有拉低者释放后由上拉电阻恢复为高。**

---

## 15. CAN 与 I²C 仲裁逻辑的共同点

CAN 和 I²C 的仲裁在抽象逻辑上非常相似：

> **节点一边发送，一边读取总线；弱状态被强状态覆盖时，发送弱状态的节点退出。**

两者都可以简化为：

| 自己发送 | 总线读取 | 仲裁结果 |
|---|---|---|
| 0 | 0 | 继续 |
| 1 | 1 | 继续 |
| 1 | 0 | 输掉仲裁 |
| 0 | 1 | 正常情况下不应出现 |

区别主要在物理实现：

- **I²C**：开漏 + 上拉，0 = 主动拉低，1 = 释放
- **CAN**：CAN 收发器实现显性/隐性，0 = 显性，1 = 隐性

此外，不能把任何“发送值与读取值不一致”都直接理解为仲裁失败，必须结合协议阶段：

- I²C 的 ACK 位中，主机释放 SDA、从机拉低 SDA 是正常 ACK，不是仲裁失败；
- CAN 在仲裁字段中“发 1 读 0”表示输掉仲裁，但在非仲裁字段中发生类似不一致，通常会按位错误等错误机制处理。
