# FreeRTOS 调度优化与中断影响

## 1. 为什么要进行任务调度优化

任务调度优化通常不是修改 FreeRTOS 调度器本身，而是重新安排任务的优先级、执行周期、阻塞方式和任务间通信，使系统同时满足实时性、稳定性与资源占用要求。

常见触发原因：

- CPU 占用率过高，很多任务一直轮询而不阻塞。
- 关键任务响应不及时，例如通信数据到了却迟迟得不到处理。
- 单次任务执行时间过长，长期占用 CPU。
- 优先级不合理，高优先级任务压制低优先级任务。
- 任务过多或唤醒过于频繁，造成大量上下文切换。
- 周期任务产生漂移，实际执行周期越来越偏离目标周期。
- 多任务访问共享资源时出现竞争、死锁或数据错乱。
- 系统偶发卡死、喂狗任务得不到执行，最终触发看门狗复位。

核心目标可以概括为：

> 让重要任务及时运行，让无事可做的任务进入阻塞，减少无意义的 CPU 占用和任务切换。

---

## 2. 调度优化最终可能改动什么

### 2.1 调整任务优先级

按照实时性而不是任务名称分配优先级。例如：

```text
紧急控制、通信接收
        ↓
数据解析、普通控制
        ↓
状态检测
        ↓
日志打印
```

高优先级不等于更重要，而表示该任务在 Ready 时需要更快获得 CPU。

### 2.2 将轮询改为阻塞等待

优化前：

```c
while (1)
{
    if (rx_flag)
    {
        process_data();
    }
}
```

优化后可让任务等待队列、信号量或任务通知：

```c
while (1)
{
    ulTaskNotifyTake(pdTRUE, portMAX_DELAY);
    process_data();
}
```

没有事件时任务处于 Blocked，不占用 CPU。

### 2.3 调整任务周期

例如温度变化较慢，原来每 10 ms 检测一次，可能改为每 500 ms 检测一次。任务周期应由业务需要决定，而不是越短越好。

### 2.4 拆分或合并任务

- 一个任务同时负责接收、解析、控制和打印，执行路径过长时，可以拆分。
- 多个任务工作量很小、周期接近且频繁切换时，也可能合并。

### 2.5 将耗时操作移出高优先级任务

高优先级任务中应尽量避免：

- 大量 `printf`；
- Flash 擦写；
- 长时间复杂计算；
- 长时间轮询等待外设；
- 没有超时的阻塞式通信。

高优先级任务可以只完成紧急处理，再通过队列通知低优先级任务处理后续工作。

### 2.6 减少临界区和关中断时间

`taskENTER_CRITICAL()`、关闭中断或禁止调度的范围越大，系统实时性越差。临界区应只包含必须原子执行的少量代码。

### 2.7 增加监控

常见监控项：

- 每个任务的平均和最大执行时间；
- CPU 使用率；
- 任务堆栈余量 `uxTaskGetStackHighWaterMark()`；
- Ready、Blocked 等任务状态；
- 队列最大积压量；
- 中断最大执行时间；
- 各任务心跳和看门狗状态。

## 3. FreeRTOS 调度的第一性原理

调度器主要面对的是不同状态的任务：

```text
Blocked：等待时间或事件，还不能运行
Ready：运行条件已经满足，正在等 CPU
Running：当前正在使用 CPU
```

因此必须区分：

> 到达唤醒时间，只表示任务由 Blocked 进入 Ready；不代表它能在这一瞬间立即开始运行。

任务能否真正运行，还取决于：

- 当前是否处于中断；
- 是否存在更高优先级 Ready 任务；
- 是否禁止了调度；
- 同优先级任务如何轮转。

任务不会因为错过原计划时间就自动作废。它会继续留在 Ready 队列中等待 CPU。

## 4. 长中断结束后，两个同优先级任务如何执行

假设：

```text
A 应在 95 ms 唤醒
B 应在 150 ms 唤醒
ISR 在 90～105 ms 执行
A 需要 55 ms 的纯 CPU 执行时间
```

过程如下：

```text
95 ms：A 到达唤醒时间，但 CPU 正在执行 ISR
105 ms：ISR 结束，A 已经 Ready，B 尚未到时间
105 ms：A 开始运行
150 ms：B 到达唤醒时间并进入 Ready
```

如果 105～150 ms 之间没有别的抢占，A 已获得约 45 ms CPU 时间，还剩约 10 ms。

150 ms 后的结果取决于配置和运行条件：

- 若 B 与 A 同优先级，且发生了同优先级轮转，B 可以在 150 ms 附近获得 CPU。
- 某些 FreeRTOS 配置或版本中，同优先级任务刚解除阻塞时也可能立即引发一次切换。
- 如果没有发生切换，并且 A 不阻塞、不让出 CPU，A 可能继续到约 160 ms，B 因此延迟约 10 ms。
- 如果 B 的优先级高于 A，B 一旦变成 Ready，通常会立即抢占 A。
- 如果 B 的优先级低于 A，通常要等 A 阻塞、结束本轮工作或主动让出 CPU。

所以工程上不能只凭“同优先级”断言固定的先后顺序，还要查看：

```c
configUSE_PREEMPTION
configUSE_TIME_SLICING
```

以及 FreeRTOS 版本、任务解除阻塞的时机和任务代码是否主动阻塞。

## 5. 时间片到底是什么

FreeRTOS 的同优先级时间片通常由系统 Tick 推动。它不是给每个任务单独设置一个“纯 CPU 时间倒计时器”。

假设 Tick 周期为 1 ms：

```text
100.0 ms    101.0 ms    102.0 ms
   │            │            │
 Tick         Tick         Tick
```

如果 A 在 100.3 ms 才开始运行，那么到 101.0 ms 就遇到了下一次 Tick。A 这次可能只连续运行了约 0.7 ms，并不是必须真正运行满 1 ms 才能轮转。

更准确的理解是：

> 每到一个有效的 Tick 调度点，调度器检查是否需要让同优先级 Ready 任务轮转。

只有 A 一个同优先级 Ready 任务时，即使经过很多 Tick，A 也无需为了“时间片到期”切给不存在的任务。

## 6. A 运行时发生中断，中断时间算不算 A 的时间

要区分两种时间。

### 6.1 A 的纯 CPU 执行时间

不包含 ISR 的执行时间。

```text
100～110 ms：A 执行 10 ms
110～120 ms：ISR 执行 10 ms
120～140 ms：A 执行 20 ms
```

结果：

```text
A 的纯 CPU 执行时间 = 30 ms
A 从开始到完成的墙上时间 = 40 ms
ISR 时间 = 10 ms
```

### 6.2 A 所处时间片的墙上时间

中断期间真实时间仍在流逝。如果 SysTick 能正常发生，或者退出中断后处理了已经挂起的 Tick，那么系统可能已经到达新的调度点。

因此，如果 B 与 A 同优先级且已经 Ready，长 ISR 返回后可能直接运行 B，而不是先恢复 A。

可以这样记：

```text
ISR 时间不属于 A 的纯 CPU 执行时间
但 ISR 可能跨过调度 Tick，影响 A 是否还能继续运行
```

## 7. 中断与 SysTick 优先级的关键细节

“ISR 期间经过了一个 Tick”不一定表示 SysTick 处理函数已经执行，必须看中断优先级和屏蔽状态。

### 情况一：SysTick 可以抢占当前 ISR

SysTick 会在 ISR 中间执行，内核 Tick 正常推进，并可能请求任务切换。真正的任务切换通常要等所有中断退出后发生。

### 情况二：当前 ISR 优先级高于 SysTick

SysTick 只能先进入 Pending 状态，等待当前 ISR 结束。ISR 退出后通常先处理挂起的 SysTick，再返回任务，因此仍可能直接切换到 B。

### 情况三：长时间关闭中断或屏蔽了 SysTick

内核时基会延迟更新。若屏蔽时间过长，甚至可能产生丢 Tick 或系统时间漂移等问题，具体取决于 MCU、FreeRTOS 端口和时钟补偿机制。

这正是 ISR 和关中断区间必须尽可能短的重要原因。

---

## 8. 错过多个周期会不会补执行多次

假设 A 每 10 ms 执行一次，但一个长 ISR 让它错过了 10、20、30、40 ms 四个时刻。

FreeRTOS 不会自动把同一个任务并行排队四份，也不会天然保证退出中断后连续补执行四次。任务通常只是处于一次 Ready 状态。

是否需要补处理四次业务，取决于事件保存方式：

- 二值标志只能表达“发生过”，多次事件可能合并。
- 计数信号量或通知计数可以保存发生次数。
- 队列可以保存多条独立数据。
- 周期任务使用 `vTaskDelayUntil()` 时，会根据既定唤醒基准继续运行；若已严重超期，可能连续快速迭代，任务代码需要自行决定补算还是丢弃旧周期。

因此，不能把任务调度和业务事件计数混为一谈。

## 9. `vTaskDelay()` 与 `vTaskDelayUntil()`

### `vTaskDelay()`

表示从当前时刻开始再等待一段时间：

```c
while (1)
{
    do_work();
    vTaskDelay(pdMS_TO_TICKS(100));
}
```

如果 `do_work()` 执行 15 ms，实际周期约为：

```text
15 ms 执行时间 + 100 ms 延时 = 115 ms
```

每次执行时间不同，周期也会跟着变化并持续漂移。

### `vTaskDelayUntil()`

以预定唤醒时间为基准保持周期：

```c
TickType_t last_wake = xTaskGetTickCount();

while (1)
{
    do_work();
    vTaskDelayUntil(&last_wake, pdMS_TO_TICKS(100));
}
```

目标时刻尽量保持为：

```text
0、100、200、300、400 ms……
```

它能防止误差不断累积，但不能保证绝对准时。到点时如果 ISR、临界区或更高优先级任务占着 CPU，该任务仍然只能先进入 Ready 并等待。

## 10. 工程中的优化原则

### 周期任务

- 使用 `vTaskDelayUntil()` 保持周期。
- 周期根据业务需要设置，不盲目追求高频。
- 记录最大执行时间，并确保最坏执行时间明显小于周期。

### 事件任务

- 使用队列、信号量或任务通知阻塞等待。
- 需要保存次数时，不要只使用一个布尔标志。

### 高优先级任务

- 每次只做少量、确定时长的工作。
- 避免打印、Flash 操作和长计算。
- 处理完成后尽快阻塞或让出 CPU。

### 中断

- 只完成必须立刻完成的动作。
- 搬运少量数据、清除中断标志、通知任务后尽快退出。
- 复杂解析和业务逻辑交给任务。
- 测量中断最坏执行时间，而不只看平均值。

### 同优先级任务

- 不依赖“碰巧的轮转顺序”实现业务逻辑。
- 有明确实时性差异时，应重新划分优先级或设计显式同步。
- 对执行时间较长的任务，拆成小段并在合适位置阻塞。

---

## 11. 判断是否需要调度优化的检查表

- 是否存在长时间不阻塞的普通任务？
- Idle 任务是否几乎没有运行机会？
- 高优先级任务是否执行 `printf`、Flash 擦写或复杂计算？
- 是否存在超过一个 Tick 的 ISR 或长临界区？
- 周期任务是否使用 `vTaskDelay()` 导致累积漂移？
- 某任务的最坏执行时间是否接近或超过自身周期？
- 队列是否积压，消息是否因容量不足被丢弃？
- 是否有低优先级任务长期得不到运行？
- 喂狗任务是否只证明自己活着，而没有检查其他关键任务的心跳？
- 系统偶发卡死或复位时，是否记录了任务状态、栈余量和异常原因？

---

## 12. 最终结论

1. FreeRTOS 调度的是 Ready 任务，不是“错过即作废”的时间表。
2. 到达唤醒时间只代表进入 Ready，不代表立刻获得 CPU。
3. 中断时间不计入任务的纯 CPU 执行时间，但会增加任务完成的墙上时间。
4. 时间片通常以 Tick 调度时刻为基准，不精确统计每个任务实际使用了多少 CPU 时间。
5. 长 ISR 可能使任务延迟，也可能使 ISR 返回后直接切换到另一个 Ready 任务。
6. 优化的核心是缩短连续占用 CPU 的时间，让无事可做的任务阻塞，并让关键任务及时响应。
