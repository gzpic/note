# 一、MCU 与启动流程

## 1. MCU、Cortex-M4、STM32 分别是什么？

**短答：** MCU 是把 CPU、存储器和外设集成在一颗芯片上的微控制器；Cortex-M4 是 Arm 设计的处理器内核；STM32 是 ST 公司基于 Cortex-M 等内核推出的一系列 MCU。

- Cortex-M4 规定指令集、核心寄存器、异常模型、NVIC、SysTick 等。
- STM32 在内核外围集成 Flash、SRAM、时钟树、GPIO、Timer、ADC、UART、SPI、I²C 等。
- 同样使用 Cortex-M4 的芯片可以来自不同厂商，内核机制相近，但外设寄存器不同。
- MCU 强调实时控制、低功耗和片上集成；MPU 通常算力更高，配外部 DDR/MMU 运行 Linux 等复杂系统。边界并非绝对。

## 2. MCU 上电启动流程

**短答：** 上电复位后，芯片锁存启动配置并映射启动存储器；CPU 从向量表第 0 项取 MSP 初值、第 1 项取 `Reset_Handler` 地址，随后完成 `.data` 搬运、`.bss` 清零、时钟和运行库初始化，最后进入 `main()`。

```text
上电/复位
  ↓
电源稳定、加载 Option Bytes、锁存 BOOT 配置
  ↓
选择用户 Flash / System Memory / SRAM（具体型号为准）
  ↓
[0x0000_0000] → MSP，[0x0000_0004] → Reset_Handler
  ↓
SystemInit（时钟、FPU、向量表等，依工程而定）
  ↓
.data：Flash → SRAM；.bss：清零；初始化 C/C++ 运行库
  ↓
main() → 外设初始化 → 裸机循环或启动 RTOS
```

### MCU 复位后的启动地址是固定的吗？

先纠正一个常见写法：STM32 用户 Flash 的典型起始地址是 **`0x08000000`**，不是 `0x80000`。`0x80000` 是一个偏移量（512 KB），含义完全不同。

**结论：要区分“CPU 复位看到的启动地址”和“实际存储器的物理映射地址”。**

- Cortex-M 复位时按架构从向量表的启动别名地址 `0x00000000` 读取初始 MSP，从 `0x00000004` 读取复位入口 PC。
- STM32 会根据 BOOT 引脚、Option Bytes 或具体系列的启动配置，把用户 Flash、System Memory（ROM Bootloader）或 SRAM 映射/别名到 `0x00000000`。
- 当用户 Flash 被选为启动空间时，向量表的实际内容通常位于 `0x08000000`，但复位阶段可通过地址别名从 `0x00000000` 访问到同一内容。
- 因此，`0x00000000` 往往是**启动窗口/别名地址**；`0x08000000` 才是 STM32 Flash 的典型实际地址。具体别名规则必须查该型号 Reference Manual。

```text
复位时 CPU 访问 0x00000000
          │
          ├─ Boot 配置选择用户 Flash  → 映射到 Flash 向量表
          ├─ Boot 配置选择 System Memory → 进入厂家 Bootloader
          └─ Boot 配置选择 SRAM       → 从 SRAM 向量表启动（依型号支持）
```

### 启动地址能不能在运行中配置？

**启动源的选择通常在复位时决定，不能在程序运行到一半时直接把 CPU 的复位入口改掉。** 但有两种常见的“可配置”容易混淆：

1. **复位启动源配置**：通过 BOOT0/BOOT1、Option Bytes 或芯片特定启动配置，改变下一次复位从哪块存储器开始。
2. **向量表重定位**：启动后通过 `SCB->VTOR` 把异常向量表改到 SRAM 或 Flash 的另一个偏移地址，例如 Bootloader 在 `0x08000000`，App 在 `0x08020000`。这改变的是中断/异常入口，不等于改变已经完成的本次复位来源。

向量表重定位示意：

```c
SCB->VTOR = APP_ADDRESS;  // APP_ADDRESS 必须满足该内核/芯片要求的对齐
__DSB();
__ISB();
```

Bootloader 跳转 App 还必须从 App 向量表第 0 项加载 MSP、第 1 项取复位入口 PC，并关闭旧的中断、SysTick 和外设状态。不能只把 PC 跳过去，否则 App 的中断仍可能进入 Bootloader 的向量表。

**面试短答：** “Cortex-M 复位从 `0x00000000` 的向量表窗口取 MSP 和复位向量；STM32 通过启动配置把 Flash、System Memory 或 SRAM 映射到这个窗口。用户 Flash 常位于 `0x08000000`。运行中可以用 `VTOR` 重定位向量表，也可以在下一次复位前改变 Boot 配置，但这两个概念都不等同于随意修改 CPU 的固定复位流程。”

### 为什么搬 `.data`、清 `.bss`？

- `.text/.rodata`：代码和只读常量，通常在 Flash。
- `.data`：有非零初值的全局/静态变量；初值存在 Flash，运行实体在 SRAM，所以要搬运。
- `.bss`：未初始化或初始化为 0 的全局/静态变量；C 语言要求初值为 0，启动时统一清零可节省 Flash。
- 栈保存局部变量、返回地址和现场；堆用于动态分配。

### Bootloader 和 `Reset_Handler` 一样吗？

不一样。System Memory Bootloader 是厂家固化的下载程序；用户 Bootloader 负责升级、校验、回滚和跳转；`Reset_Handler` 是当前镜像向量表中的复位入口。

用户 Bootloader 跳转 App 时通常要：关闭中断/SysTick 和已用外设，校验镜像，设置 `SCB->VTOR`，从 App 向量表装载 MSP，最后跳到 App 的复位向量。还要按具体芯片处理 Cache、MPU 等状态。

### MCU 应该如何选型？

**短答：** 先把需求量化，再按“硬性条件淘汰、性能与存储留余量、软件生态验证、成本和供应链收口”的顺序选型，不能只比较主频和价格。

1. **应用与实时性**：控制周期、最坏中断延迟、算法算力、是否需要 FPU/DSP、是否运行 RTOS/Linux。
2. **存储**：根据 map 文件或原型估算 Flash、静态 RAM、任务栈、通信缓冲和升级双分区，通常留出合理增长空间。
3. **外设**：接口种类、数量、引脚复用是否冲突；ADC 精度/采样率、Timer 通道、DMA 请求映射、USB/CAN/Ethernet 等必须逐项核对。
4. **电气与环境**：供电电压、IO 电平和 5 V 容忍、工作温度、EMC、低功耗电流、唤醒源、功能安全等级。
5. **封装和硬件**：GPIO 数量、PCB 层数、焊接能力、晶振/外部存储需求、调试接口是否保留。
6. **软件生态**：编译器、调试器、驱动库、RTOS/中间件、示例、勘误和社区成熟度；还要评估从旧平台迁移的工作量。
7. **量产因素**：单价只是其一，还要看供货周期、生命周期、第二来源、烧录测试、失效率和厂家技术支持。

> [!tip] 选型验证方法
> 建一张“必须满足/期望满足/可放弃”的选型表，用 Datasheet 做初筛，再用 Reference Manual 核对引脚复用、时钟、DMA 和外设细节，最后拿开发板验证最高风险项。不要在只看选型手册后直接定板。

## 4. 为什么有 I-Code、D-Code、System Bus？

**短答：** Cortex-M4 用分离的取指、代码区数据访问和系统访问通路，使取指与数据访问可并行，降低争用、提高吞吐率。

- I-Code：从代码区取指，也用于读取向量。
- D-Code：访问代码区中的数据，如 Flash 常量。
- System Bus：访问 SRAM、外设和系统资源。

这是改进型哈佛结构，但仍是统一地址空间。真实性能还受 Flash 等待周期、预取、总线矩阵和 DMA 争用影响。

# 二、通信与总线

## 1. SPI、I²C、UART 对比与选型

| 项目 | SPI | I²C | UART/USART 异步模式 |
|---|---|---|---|
| 信号 | SCK、MOSI、MISO、CS | SCL、SDA | TX、RX，可选流控 |
| 时钟 | 同步 | 同步 | 异步 |
| 双工 | 通常全双工 | 半双工 | 通常全双工 |
| 寻址 | 靠 CS | 7/10 位地址 | 无总线寻址 |
| 电气 | 通常推挽 | 开漏 + 上拉 | 通常推挽 |
| 特点 | 快、开销小、占引脚 | 少引脚、多设备 | 点对点、无需共享时钟 |

**选型：** 大数据量、低延迟、板内短线选 SPI；低速配置器件多且引脚少选 I²C；点对点、两端不共享时钟或搭配 RS-485/RS-232 收发器时常选 UART。

## 2. SPI 时序与四种模式

**短答：** 主机输出 SCK/CS，双方按 CPOL、CPHA 约定一个边沿采样、另一个边沿改变数据。CPOL 决定空闲电平，CPHA 决定第几个有效边沿采样。

| Mode | CPOL | CPHA | 空闲 | 采样边沿 |
|---|---:|---:|---|---|
| 0 | 0 | 0 | 低 | 第一个，即上升沿 |
| 1 | 0 | 1 | 低 | 第二个，即下降沿 |
| 2 | 1 | 0 | 高 | 第一个，即下降沿 |
| 3 | 1 | 1 | 高 | 第二个，即上升沿 |

判断时先由 CPOL 找空闲电平，再数第一/第二边沿；最终以从机 Datasheet 时序图为准。SPI 没有统一规定地址、命令和帧格式。

### 为什么 SPI 有四种模式而 I²C 通常只有一种时序？

**短答：** SPI 只规定了基本的移位通信框架，没有统一规定时钟空闲电平和采样边沿；因此用 `CPOL` 和 `CPHA` 组合出 4 种模式。I²C 是一套完整的共享总线协议，必须统一 START/STOP、ACK、仲裁和数据采样规则，所以通常只有一种逻辑时序。

#### SPI 为什么需要四种模式？

SPI 的两根数据线是独立方向，主机提供时钟，协议本身很简单。不同厂商的从机可能要求：

- SCK 空闲为低或高，即 `CPOL = 0/1`；
- 在第一个或第二个有效边沿采样，即 `CPHA = 0/1`。

两种空闲电平 × 两种采样边沿 = 四种组合：Mode 0、1、2、3。四种模式不是让一次通信同时使用四种模式，而是为了兼容不同器件的时序约定；一次 SPI 事务中主从必须使用同一种模式。

#### I²C 为什么不设计成四种模式？

I²C 的 SCL/SDA 是开漏共享线，多个设备可能同时观察和驱动总线。协议统一规定：

- 空闲时 SCL、SDA 为高；
- SCL 为高时 SDA 必须稳定；
- SDA 在 SCL 高时由高变低表示 START，由低变高表示 STOP；
- **每 8 位数据后固定有第 9 个 ACK/NACK 时钟：ACK 为 SDA 低电平，NACK 为 SDA 高电平；这个定义固定不变。**
- SCL 低电平还允许从机进行 clock stretching，多主机可以进行仲裁。

如果允许每个设备自由选择 CPOL/CPHA，设备就无法可靠判断 START/STOP、数据位和 ACK，也无法保证多个主机对“谁把时钟拉低、谁赢得仲裁”的共同理解。因此 I²C 把逻辑采样规则固定下来，以换取多设备互操作性和总线仲裁能力。

#### I²C 真的只有一种“速度”吗？

不是。I²C 有 Standard-mode、Fast-mode、Fast-mode Plus、High-speed mode 等速率等级，不同等级会规定不同的最大频率、上升/下降时间和电气要求；这改变的是**允许的时间尺度**，不是像 SPI Mode 0~3 那样改变采样边沿和空闲电平。

一句话对比：

> SPI 把时钟相位和极性留给器件协商，所以有四种模式；I²C 为了让共享总线上的所有设备识别同一套 START、数据、ACK 和仲裁规则，把逻辑时序固定，只通过速率等级改变时间参数。

### STM32 的 SPI Mode 应该怎样确定？

**SPI Mode 不是由 STM32 自己随意选择，而是由通信对端器件的 Datasheet 和时序图决定；主机与从机的 CPOL、CPHA 必须一致。** STM32 作为主机连接传感器、Flash 等器件时，应以从机要求为准；STM32 作为从机时，则要与外部主机约定相同模式。

从机芯片对 SPI Mode 通常有三种规定：只支持一种 Mode（最常见）、同时兼容几种 Mode（如 Mode 0/3），或者允许通过引脚、寄存器配置 Mode。同一器件的各条 SPI 指令通常共用同一种 Mode，不能凭经验猜测，必须查看 Datasheet 的 Serial Interface、Timing Characteristics 和时序图。

作为主机的 STM32 通常能配置 Mode 0～3，但“支持四种”不代表通信时可以同时使用四种：**一次 SPI 事务只能采用当前配置的一种 Mode，并且必须是当前从机支持的 Mode。** 如果主机和从机都是自行设计的，可以约定任意一种双方都实现的 Mode。

确定模式分两步：

1. 看 SCK 空闲电平：空闲低为 `CPOL=0`，空闲高为 `CPOL=1`。
2. 看数据在哪个有效边沿采样：第一个有效边沿采样为 `CPHA=0`，第二个有效边沿采样为 `CPHA=1`。

```text
Mode 0：空闲低，第一个边沿（上升沿）采样
Mode 1：空闲低，第二个边沿（下降沿）采样
Mode 2：空闲高，第一个边沿（下降沿）采样
Mode 3：空闲高，第二个边沿（上升沿）采样
```

当 `CPHA=0` 时，第一位数据必须在第一个采样边沿到来前已经稳定；当 `CPHA=1` 时，第一个边沿用于推出/改变第一位，第二个边沿再采样。Datasheet 可能使用 rising/falling、leading/trailing、capture/shift 等不同术语，应以时序图中“空闲电平、数据改变边沿、数据采样边沿”为准，不能只凭文字猜模式。

STM32F4 中通过 `SPIx_CR1` 的 `CPOL`、`CPHA` 位配置，HAL 对应 `CLKPolarity`、`CLKPhase`：

```c
hspi1.Init.CLKPolarity = SPI_POLARITY_LOW;
hspi1.Init.CLKPhase    = SPI_PHASE_1EDGE;  // Mode 0

/* 寄存器方式：确认 SPI 不忙且 SPE=0 后配置 Mode 0 */
SPI1->CR1 &= ~(SPI_CR1_CPOL | SPI_CR1_CPHA);
```

本项目 Jetson 主机与 STM32F407 SPI1 从机约定为 Mode 0，所以 `spi_slave.c` 初始化 `SPI1->CR1 = 0` 时，`CPOL=0、CPHA=0`。这条赋值还同时保持 `MSTR=0`、8 bit、MSB first 和硬件 NSS 等默认配置，不能脱离其他位单独照搬。

若同一 SPI 控制器连接的多个从机要求不同 Mode，主机应在所有 CS 均无效、SPI 不忙并禁用外设后，按目标从机重新配置 CPOL/CPHA，再拉低对应 CS；不能在一个事务中途切换模式。换句话说，Mode 是 SPI 控制器的当前配置，不是永久绑定在 MCU 上；主机可在不同从机事务之间切换，但每次都必须匹配被选中的从机。

### SPI 的 dummy 字节是什么？

SPI 的 SCK 由主机产生，而且每个时钟都会同时在 MOSI 和 MISO 上移入/移出一位。主机想读取从机时，仍必须启动一次发送来产生时钟；此时主机在 MOSI 上发送的无业务意义占位数据就叫 **dummy byte（哑字节/占位字节）**。

```text
主机只想读 1 字节：

MOSI：主机发送 dummy 0xFF ─────────→ 从机通常忽略
SCK ：主机产生 8 个时钟
MISO：主机同时收到真实数据 0x5A ←─ 从机发送
```

常见 dummy 值是 `0x00` 或 `0xFF`，但不保证任意值都安全，必须看器件协议：某些从机会继续解析 MOSI，错误占位值可能被当成命令或数据；有些 Flash 还规定命令、地址之后必须插入若干 dummy clock/dummy cycle，给内部读取和总线换向留时间。

还要区分三种概念：

| 概念 | 含义 |
|---|---|
| 主机发送 dummy byte | 主机只想读，但必须通过发送占位数据产生 SCK |
| 主机收到 dummy data | 主机发送命令阶段同时收到的 MISO 字节暂时无效，应丢弃 |
| 协议规定 dummy cycle | 器件要求额外空时钟，数量可能不是完整字节 |

SPI 即使“只写”，接收寄存器仍可能同步收到数据；软件应按芯片要求读取 `DR`、清除 RX 状态或使用全双工收发接口，避免产生 `OVR`。本项目读取响应时，Jetson 第二次事务发送一串 `0xFF` 产生时钟，同时从 STM32 的 MISO 读取响应帧；这些 `0xFF` 只是物理层占位，不属于业务请求数据。

> [!tip] 面试短答
> SPI Mode 根据从机时序图确定：CPOL 看时钟空闲电平，CPHA 看第一个还是第二个有效边沿采样。dummy 字节是主机为了产生读时钟而在 MOSI 上发送的占位数据，常用 `0x00/0xFF`，但具体值和额外 dummy 周期必须服从器件协议。

### SPI 为什么是全双工？收发时序是什么？

**短答：** 标准四线 SPI 将两个数据方向拆成独立线路：MOSI 负责主机到从机，MISO 负责从机到主机。主机和从机内部各有发送、接收移位寄存器，在同一组 SCK 下同时移出一位并接收一位，所以每经过一个完整时钟周期，两个方向各传输一位，属于全双工。

```text
                 MOSI
主机 TX 移位寄存器 ─────────→ 从机 RX 移位寄存器
        ↑                           │
        └────────── SCK ────────────┤
        │                           ↓
主机 RX 移位寄存器 ←───────── 从机 TX 移位寄存器
                 MISO
```

假设帧长为 8 bit，一次字节交换过程如下：

```text
主机拉低 CS，选中从机
        ↓
主机写发送寄存器，SPI 开始产生 SCK
        ↓
每个 SCK 周期：一个边沿改变/推出数据，另一个边沿采样数据
        ↓
经过 8 个 SCK：主机发出 8 bit，同时收到 8 bit
        ↓
主机读取接收寄存器，等待不忙后释放 CS
```

CPOL/CPHA 只决定时钟空闲电平以及在哪个边沿改变和采样数据，不改变全双工能力，Mode 0~3 都可以全双工：

| CPHA | 第一个有效边沿 | 第二个有效边沿 | 第一位数据要求 |
|---:|---|---|---|
| 0 | 采样 | 改变并准备下一位 | CS 有效后、第一边沿到来前必须已经稳定 |
| 1 | 改变并推出数据 | 采样 | 第一位可在第一个边沿推出 |

“同时收发”不等于两端可以随意发送。SCK 始终由主机提供，因此即使主机只想读数据，也必须发送 dummy byte（常见为 `0x00` 或 `0xFF`）来产生时钟；主机只写时，接收寄存器仍可能收到从机同时移出的数据，需要按芯片要求读取或清除，避免 RX 溢出。

很多 SPI 器件在一帧内并不是立即返回当前命令的结果。例如主机发送“读寄存器命令 + 地址”时，MISO 同期可能返回无效字节，真正数据在后续 dummy 时钟中返回。这仍是物理层全双工，只是器件协议按“命令阶段、数据阶段”组织。

> [!warning] 不是所有 SPI 变体都全双工
> 如果所谓“三线 SPI”是 SCK、CS、SDIO，发送和接收共用 SDIO，只能分时切换方向，属于半双工。但“三线”命名并不统一：HC32F4A0 的三线时钟同步模式是 SCK、MOSI、MISO 三根线，只是不使用 SS，仍保留两个数据方向。判断双工方式必须看芯片手册中的实际信号定义。Dual/Quad SPI 的多根 IO 也常按阶段统一改变方向，不能直接按标准 MOSI/MISO 全双工理解。

### 为什么 SPI 没有 ACK/NACK？如何确认通信成功？

**标准 SPI 只规定 SCK、MOSI、MISO、CS 上如何同步移位数据，没有定义地址、字节边界后的应答或统一帧格式，因此协议层本身不存在 I²C 那样的 ACK/NACK。**

主机拉低 CS 并产生时钟后，无论从机是否存在、是否忙、是否理解命令，SPI 控制器都会完成规定数量的移位。`TXE/RXNE/BSY` 等标志只能说明本机硬件已发送或接收，不能证明对端正确处理了数据。若 MISO 悬空，主机甚至可能读到固定的 `0xFF`、`0x00` 或随机值。

```text
I²C：发送 8 bit → 第 9 个时钟由接收方返回 ACK/NACK
SPI：发送 8 bit ↔ 同时接收 8 bit → 没有额外的统一应答位
```

SPI 器件是否需要确认、如何确认，由具体芯片或上层协议自行规定，常见方法包括：

- 读取状态寄存器中的 READY/BUSY/ERROR 位。
- 让从机返回固定帧头、状态码、序号和 CRC，主机校验后才认为成功。
- 使用额外 READY/BUSY、IRQ 或 DONE 管脚通知主机。
- 设置响应超时；未收到合法响应时重试读操作，写操作是否能重试要考虑重复执行风险。

本项目采用“两次 SPI 事务”：第一次由 Jetson 写命令帧，STM32 校验并处理；第二次由 Jetson 发送 dummy byte 产生时钟，读取 STM32 返回的状态帧。主机检查帧头、状态码和 CRC 后才能确认命令成功，这相当于在应用层实现应答，但它不是 SPI 硬件自带的 ACK/NACK。

> [!tip] 面试短答
> SPI 不需要也没有统一 ACK/NACK，因为它只负责在 CS 和 SCK 控制下同步移位数据，不负责寻址和确认对端是否处理成功。需要可靠性时，由器件协议或应用层增加状态字节、响应帧、CRC、超时及 READY/IRQ 管脚。

### 同一组 SPI 管脚能否配置成主机或从机？

**可以，前提是该 MCU 的 SPI 外设和对应引脚复用支持两种模式。** 同一个 SPI 外设切换主从模式后，仍可使用同一组 SCK、MOSI、MISO、NSS 管脚，但外设控制的输入输出方向会改变：

| 管脚 | 主机模式 | 从机模式 |
|---|---|---|
| SCK | 输出时钟 | 输入主机时钟 |
| MOSI | 输出主机数据 | 输入主机数据 |
| MISO | 输入从机数据 | 被 NSS 选中时输出数据，未选中时通常高阻 |
| NSS/CS | 输出从机选择信号，或使用普通 GPIO 控制 | 输入片选信号 |

主机和从机不是两套物理管脚，而是同一 SPI 控制器的两种角色。同一时刻只能按一种角色运行，不能同时既做主机又做从机；如果产品需要同时承担两种角色，通常使用两个独立 SPI 外设。SPI 本身也没有像 I²C 那样的标准多主仲裁，动态切换角色必须由上层协议保证不会有两个主机同时驱动 SCK、MOSI 或 CS。

### CS 和 NSS 是什么关系？

**CS（Chip Select）是通用叫法，NSS 是 SPI 外设中表示片选/从机选择的信号名。** 两者在大多数 SPI 原理图里表示同一类功能：主机把目标从机的片选拉到有效电平，从机开始响应；事务结束后释放片选。

```text
主机                         从机
SCK   ─────────────────────→ SCK
MOSI  ─────────────────────→ MOSI
MISO  ←───────────────────── MISO
CS/NSS ─────────────────────→ NSS
```

常见区别在于“谁控制、怎么实现”：

| 场景 | CS/NSS 的典型用法 |
|---|---|
| 主机连接一个从机 | 可以使用 SPI 外设的硬件 NSS，也可以用普通 GPIO 手动控制 CS |
| 主机连接多个从机 | SCK/MOSI/MISO 共用，每个从机通常使用一个独立 GPIO CS；不能让所有从机共用同一个有效片选 |
| SPI 从机 | NSS/CS 通常是输入，片选有效时才接收 SCK/MOSI，并允许 MISO 输出；未选中时 MISO 应高阻 |
| 软件管理 NSS | STM32 常通过 `SSM/SSI` 等位让内部 SPI 状态机使用软件设定的 NSS 状态，具体行为依系列手册 |

**CS 不一定等于某个固定的 NSS 引脚。** 很多 STM32 主机工程直接把普通 GPIO 命名为 `CS_PIN`，因为硬件 NSS 的输出时序、脉冲行为或可用引脚不符合需求；这时 SPI 外设只产生 SCK/MOSI/MISO，CS 由软件在事务前后拉低/拉高。

一次完整事务通常应保持 CS 有效：

```text
CS 低 → 命令 → 地址 → 数据/读回 → 等待 SPI 不忙 → CS 高
```

不能在同一条器件命令的中间随意拉高 CS，否则很多 Flash、传感器会把后续字节当成新事务或直接丢弃。上电、复位和 GPIO 初始化期间还应让 CS 保持无效电平（常见为高），避免从机误选中。

**面试短答：** CS 是片选的通用名称，NSS 是 SPI 外设对从机选择信号的命名；主机可以用硬件 NSS，也常用普通 GPIO 作为 CS。多从机时每个从机通常独立 CS，NSS 有效期间从机才驱动 MISO，事务结束必须在 SPI 不忙后释放片选。

以 HC32F4A0 为例，参考手册第 31 章规定：

- `SPI_CR1.MSTR = 1` 为主机，`MSTR = 0` 为从机。
- `SPI_CR1.SPIMDS = 0` 为四线 SPI 运行模式；该模式主机和从机都支持。
- 主机模式下 SCK、MOSI、SS0~SS3 为输出，MISO 为输入。
- 从机模式下 SCK、MOSI、SS0 为输入，MISO 在选中时输出、未选中时为高阻。
- 主机使用内部波特率发生器产生 SCK；从机使用外部输入的 SCK，不配置自己的发送波特率。

STM32F407 的 RM0090 第 28 章规定：

- `SPI_CR1.MSTR = 1` 为主机，`MSTR = 0` 为从机。
- `SPI_CR1.BIDIMODE = 0、RXONLY = 0` 为双线全双工；MOSI 和 MISO 同时工作。
- `BIDIMODE = 0、RXONLY = 1` 为双线只接收；`BIDIMODE = 1` 为单数据线双向半双工，方向由 `BIDIOE` 控制。
- `SPI_CR1.BR[2:0]` 设置主机 SCK 分频；从机的 SCK 由外部主机输入。
- `SPI_CR1.DFF` 选择 8 bit 或 16 bit 数据帧；应在 `SPE = 0` 时修改。
- NSS 可使用硬件输入/输出，也可用 `SSM/SSI` 软件管理；工程中主机控制多个从机时也常用普通 GPIO 分别产生 CS。

### MSB 和 LSB 是什么？

**MSB（Most Significant Bit）是最高有效位，LSB（Least Significant Bit）是最低有效位。**它们表示的是数据位的权重，不是电平高低：在一个 8 位字节中，bit7 通常是 MSB，bit0 通常是 LSB。

例如 `0x96 = 1001 0110`：

| 发送方式 | 发送顺序（先发送的在左侧） |
|---|---|
| MSB first | `1 → 0 → 0 → 1 → 0 → 1 → 1 → 0`（bit7 到 bit0） |
| LSB first | `0 → 1 → 1 → 0 → 1 → 0 → 0 → 1`（bit0 到 bit7） |

在 SPI 中，`MSB first/LSB first` 指**一个数据帧内部的位发送顺序**。STM32 可通过 SPI 的位序配置选择它，主从两端必须一致；如果一端 MSB first、另一端 LSB first，同一个字节的位会被反向解释，例如发送 `0x12` 可能被接收为 `0x48`，从而导致命令和数据错误。

#### 位序和字节序不是一回事

- **位序（bit order）**：一个字节内部，先传 bit7 还是先传 bit0。
- **字节序（byte order/endianness）**：一个多字节数中，先放高字节还是低字节。

例如 16 位数 `0x1234`：

```text
大端/网络字节序：12 34
小端字节序：    34 12
```

一个协议完全可能采用“小端字节序”，同时规定每个字节在 SPI 上仍然“MSB first”。CPU 的小端存储方式也不会自动决定 SPI 的线上的位序，必须分别按照协议和外设手册配置、打包数据。

#### I²C、SPI、UART 一般先传哪一位？

| 总线 | 常见发送顺序 | 需要注意的内容 |
|---|---|---|
| I²C | **MSB first** | 一个字节通常先发送 bit7，再发送 bit0；随后还要发送 ACK/NACK 位。 |
| SPI | 通常 **MSB first**，也可配置为 LSB first | 由 SPI 控制器的位序配置决定，主从两端必须一致；不能只凭总线名称判断。 |
| UART | 数据位通常 **LSB first** | 线路顺序通常是：空闲高电平 → 起始位（低）→ bit0 到 bit7 → 可选校验位 → 停止位（高）。 |

例如发送 `0x96`：

```text
I²C / 常见 SPI（MSB first）：1 0 0 1 0 1 1 0
UART 数据位（LSB first）：   0 1 1 0 1 0 0 1
```

UART 的“先传 LSB”只针对数据位，不表示起始位或停止位也属于数据位；起始位、校验位和停止位按 UART 帧格式固定插入。工程中最终应以具体协议和外设手册为准。

> [!tip] 面试短答
> MSB 是最高有效位，LSB 是最低有效位；SPI 的 MSB/LSB first 表示一个字节内的位发送顺序。不要把它和多字节数据的大小端混淆，也不要把 MSB/LSB 理解成高电平/低电平。

### HC32F4A0 与 STM32F407 的 SPI 配置对照

| 对比项 | HC32F4A0 | STM32F407 | 共同点/注意事项 |
|---|---|---|---|
| 主从选择 | `SPI_CR1.MSTR`：1 主、0 从 | `SPI_CR1.MSTR`：1 主、0 从 | 位名相同，但不能据此假定其他寄存器也兼容 |
| 标准全双工 | `SPIMDS=0`，四线 SPI 运行模式 | `BIDIMODE=0、RXONLY=0`，双线全双工 | 都使用独立 MOSI/MISO，同时收发 |
| 所谓“三线” | `SPIMDS=1`：SCK+MOSI+MISO，不使用 SS | 常说的三线半双工一般是 SCK+NSS+单根双向数据线，`BIDIMODE=1` | 名称相同但线路含义不同，必须看信号定义 |
| 数据帧长度 | 4~32 bit | 8 bit 或 16 bit，由 `DFF` 选择 | 两端帧宽必须一致 |
| 时钟配置 | 主机内部波特率发生器；从机输入 SCK | 主机通过 `BR[2:0]` 分频；从机输入 SCK | 只有主机产生 SCK |
| 从机选择 | SPI 模式下主机可使用 SS0~SS3，从机使用 SS0 | 每个 SPI 外设有 NSS，可硬件或软件管理；多从机常用 GPIO CS | 未选中的从机必须释放 MISO |
| 主机管脚方向 | SCK/MOSI/SS 输出，MISO 输入 | SCK/MOSI 输出、MISO 输入；NSS 取决于管理方式 | GPIO 复用、输出类型和驱动能力仍要按各自手册配置 |
| 从机管脚方向 | SCK/MOSI/SS0 输入，MISO 输出/Hi-Z | SCK/MOSI/NSS 输入，MISO 输出 | NSS 无效时不能占用共享 MISO |
| 发送时的接收处理 | 全双工发送期间仍会收到数据，应处理接收状态 | 全双工下每次发送也会接收；不读 `DR` 可能置 `OVR` | 只写业务也不能忽略 RX 溢出 |

两款芯片的物理原理相同，但配置字段不能直接照搬。HC32F4A0 用 `SPIMDS` 区分带 SS 的 SPI 运行和不带 SS 的时钟同步运行；STM32F407 用 `BIDIMODE/RXONLY/BIDIOE` 区分双线全双工、双线只接收和单线半双工。移植驱动时应按“功能意图”重新映射配置，不能只替换寄存器前缀。

通用配置步骤如下：

1. 使能 SPI 和 GPIO 外设时钟，按数据手册确认这组引脚支持对应 SPI 复用功能。
2. 把 SCK、MOSI、MISO、NSS 配为 SPI Alternate Function；根据主从角色设置输入能力、输出类型、驱动能力和上下拉。
3. 选择主机或从机、四线全双工或三线半双工模式。
4. 配置 CPOL、CPHA、MSB/LSB first、帧宽；两端必须一致。
5. 主机配置 SCK 分频和 NSS 管理方式；从机配置 NSS 有效极性及相关接收行为。
6. 清除旧状态和错误标志，配置中断或 DMA，最后使能 SPI。

运行过程中确实需要切换主从角色时，应先停止新传输并等待 SPI 不忙，释放 CS，禁用 SPI，处理接收残留和错误标志，再修改主从位、NSS 和 GPIO 方向等配置，最后重新使能。不能在正在传输时直接改 `MSTR`。

参考：[HC32F4A0 系列参考手册](E:/HC32F4A0资料/RM_HC32F4A0系列参考手册_Rev1.50.pdf) 第 31.4 节“SPI 动作系统说明”和第 31.6 节“运行说明”；[STM32F407 系列参考手册 RM0090](https://www.st.com/resource/en/reference_manual/rm0090-stm32f407-advanced-armbased-32bit-mcus-stmicroelectronics.pdf) 第 28 章“Serial peripheral interface (SPI)”。

### 项目实例：SPI 主从 GPIO 和硬件如何配置？

工程 `spi_jetson_stm32` 中，Jetson Orin Nano 是主机，STM32F407ZG 的 SPI1 是从机，使用 Mode 0、8 bit、MSB first，初始联调频率为 100 kHz。

```text
Jetson 主机                         STM32 从机
J12 Pin 23 / SCK  ───────────────  PA5 / SPI1_SCK / AF5
J12 Pin 19 / MOSI ───────────────  PA7 / SPI1_MOSI / AF5
J12 Pin 21 / MISO ←──────────────  PA6 / SPI1_MISO / AF5
J12 Pin 24 / CS0  ───────────────  PA4 / SPI1_NSS / AF5
任意 GND          ───────────────  GND
```

#### 主从 GPIO 的配置原则

| 管脚 | 主机侧 | 从机侧 |
|---|---|---|
| SCK | 复用推挽输出 | 复用输入，由外部时钟驱动 |
| MOSI | 复用推挽输出 | 复用输入 |
| MISO | 复用输入 | 复用输出；未被 CS 选中时必须高阻 |
| CS/NSS | 推挽输出，常用普通 GPIO 或硬件 NSS | 输入；本项目使用硬件 NSS |

STM32 代码把四根管脚统一交给 SPI1 外设，实际输入/输出方向由从机模式自动控制：

```c
__HAL_RCC_GPIOA_CLK_ENABLE();
__HAL_RCC_SPI1_CLK_ENABLE();

gpio.Pin       = GPIO_PIN_4 | GPIO_PIN_5 | GPIO_PIN_6 | GPIO_PIN_7;
gpio.Mode      = GPIO_MODE_AF_PP;
gpio.Pull      = GPIO_NOPULL;
gpio.Speed     = GPIO_SPEED_FREQ_VERY_HIGH;
gpio.Alternate = GPIO_AF5_SPI1;
HAL_GPIO_Init(GPIOA, &gpio);

gpio.Pin  = GPIO_PIN_4;  // NSS 空闲时保持高，避免误选中
gpio.Pull = GPIO_PULLUP;
HAL_GPIO_Init(GPIOA, &gpio);
```

这里的 `GPIO_MODE_AF_PP` 表示复用功能的输出类型为推挽，不代表 PA4～PA7 全部同时向外输出；SPI1 从机模式会把 SCK、MOSI、NSS 当输入，只在选中时通过 MISO 输出。

#### 硬件连接重点

- 主从必须共地且 IO 电压兼容，本项目两端均为 3.3 V。
- SPI 不像 I²C 那样要求 SCK/MOSI/MISO 全部上拉；只建议给低有效 CS/NSS 加约 `10 kΩ` 上拉，保证上电和复位期间从机未选中。
- 多从机共用 MISO 时，所有未选中从机都必须释放 MISO，否则输出冲突。
- Jetson 需要先通过 pinmux/设备树启用 J12 的 `spi1`，C 程序只配置 `/dev/spidevB.C` 的模式、位宽和频率，不能代替管脚复用。
- PA4～PA7 必须查 STM32F407 AF 表并选择 AF5；仅修改接线而不修改复用和 NSS 策略不会生效。

#### STM32 从机外设的最小配置

```c
/* MSTR=0、SSM=0、CPOL=0、CPHA=0、DFF=0、LSBFIRST=0 */
SPI1->CR1 = 0;                           // 从机、硬件 NSS、Mode 0、8 bit、MSB first
SPI1->CR2 = SPI_CR2_RXDMAEN |
            SPI_CR2_TXDMAEN;             // DMA 收发
SPI1->CR1 = SPI_CR1_SPE;                 // 使能 SPI1
```

主从配置的主要区别是：**主机设置 `MSTR=1`、SCK 分频并控制 CS；从机设置 `MSTR=0`，接收主机的 SCK 和 NSS。** 从机不决定通信频率，但 CPOL、CPHA、位宽和位序必须与主机一致。本项目还把 PA4 连接到 EXTI4，用 CS 上升沿判断一次事务结束。

> [!tip] 面试短答
> SPI 主机的 SCK、MOSI、CS 是推挽输出，MISO 是输入；从机的 SCK、MOSI、NSS 是输入，MISO 在选中时输出、未选中时高阻。两端要共地、电平一致、模式参数一致，CS 应有稳定的默认未选中电平。

### SPI 多从机与数量

SCK/MOSI 共用，MISO 通常共用，每个从机独立 CS。理论数量受 CS 数量限制，可用译码器或菊花链扩展；实际还受 GPIO、负载电容、走线、频率和 MISO 高阻能力限制，没有统一最大值。同一时刻通常只选一个从机。

### SPI 现场算时间

```text
理想时间 ≈ 总位数 / SCK 频率
```

10 MHz 传 1000 字节：`1000 × 8 / 10 MHz = 0.8 ms`。实际还要加命令、地址、CS 建立/保持时间和软件/DMA 开销。

## 3. I²C 时序

**短答：** 空闲时 SCL/SDA 都为高；SCL 高时 SDA 高→低是 START、低→高是 STOP；数据在 SCL 高时稳定，每 8 位后第 9 位是 ACK/NACK。

- **ACK：第 9 个时钟 SDA = 0，接收方主动把 SDA 拉低。这个电平定义是 I²C 协议固定规定的。**
- **NACK：第 9 个时钟 SDA = 1，接收方释放 SDA，由上拉电阻拉高。**
- Repeated START：不发 STOP 就再次 START，可保持总线控制权。

典型读寄存器：

```text
START → 地址+W → ACK → 寄存器地址 → ACK
→ Repeated START → 地址+R → ACK → 数据……
→ 主机对最后一字节 NACK → STOP
```

### SCL 和 SDA 由谁拉高、拉低？

**一句话：I²C 设备只能主动拉低 SCL/SDA；当所有设备释放总线时，外部上拉电阻负责把它们拉高。**

```text
             VCC                         VCC
              |                           |
           上拉电阻                    上拉电阻
              |                           |
SCL ----------+----------     SDA --------+----------
       主机/从机只能拉低             主机/从机只能拉低
```

因此 I²C 引脚使用 **开漏输出（Open-Drain）**：输出 `0` 表示导通内部晶体管并拉低总线；输出 `1` 实际表示关闭晶体管、释放总线，并不是主动输出高电平。任何设备拉低时总线都是低，只有所有设备都释放时总线才为高。

| 线 | 主要控制者 | 谁可以拉低 |
|---|---|---|
| SCL | 主机产生时钟 | 主机正常拉低；支持时钟拉伸的从机也可暂时拉低 |
| SDA | 当前发送方 | 主机写数据时由主机控制；从机读数据或回复 ACK 时由从机控制 |

数据传输时，`SDA 高 = 1`、`SDA 低 = 0`，每字节按 MSB 优先发送。SDA 通常在 SCL 低电平期间改变，在 SCL 高电平期间保持稳定供接收方采样；START 和 STOP 是例外。

```text
前 8 个 SCL：D7 D6 D5 D4 D3 D2 D1 D0
第 9 个 SCL：ACK/NACK

ACK  = 接收方拉低 SDA = 0（固定规则）
NACK = 接收方释放 SDA = 1（由上拉电阻拉高）
```

> [!tip] 面试记忆
> **I²C 的 ACK 是低电平，不是高电平。** 低电平是设备“拉”出来的，高电平是设备“放手”后由上拉电阻形成的；ACK 表示接收方在第 9 个时钟主动拉低 SDA，NACK 才是高电平。

### 什么是 I²C 时钟拉伸？为什么需要？

**时钟拉伸（Clock Stretching）是从机在主机释放 SCL 后继续把 SCL 拉低，要求主机暂停传输，等从机准备完成后再继续。**

```text
主机：拉低 SCL → 释放 SCL ─────────────→ 等待
从机：                  继续拉低 ─────→ 释放
总线：___________低电平被延长__________/‾‾‾高电平
                                       ↑
                                从机已经准备好
```

I²C 的 SCL 是开漏线。主机所谓“输出高”其实只是释放 SCL；如果从机仍在拉低，总线实际电平还是 0。因此主机释放 SCL 后必须检查管脚的真实电平，只有确认 SCL 已经为高，才能进入当前时钟的高电平阶段。

从机需要时钟拉伸的常见原因：

- 还没有准备好下一个要发送的数据字节。
- 接收缓冲区或状态机暂时来不及处理新数据。
- 正在等待中断、DMA、传感器转换或内部计算完成。
- 主机产生时钟的速度超过从机当前能够处理的速度。

```text
主机释放 SCL
      ↓
读取实际 SCL 电平
      ├─ SCL=0：从机正在拉伸，继续等待
      └─ SCL=1：从机已经释放，继续传输
```

从机只能延长 SCL 的低电平，不能主动产生时钟或提高总线频率。并非所有主机控制器和驱动都完整支持时钟拉伸，使用前应查主机手册；主机还必须设置合理超时，否则从机故障并持续拉低 SCL 时，会表现为总线永久卡死。

时钟拉伸适合短暂等待，不适合掩盖毫秒级以上的长期阻塞。耗时操作更适合采用 BUSY 状态、异步命令、READY/IRQ 管脚或由主机稍后重试。

> [!tip] 面试短答
> I²C 时钟拉伸是从机在主机释放 SCL 后继续拉低 SCL，让主机等待自己准备完成。它利用了 SCL 的开漏线与特性，解决从机暂时跟不上主机的问题；主机必须读取 SCL 真实电平并设置超时，防止从机异常导致总线永久卡死。

### I²C 完整的写过程和读过程是什么？

**写寄存器：**

```text
START → 7 位从机地址 + W(0) → 从机 ACK
→ 寄存器地址 → ACK
→ 数据 1 → ACK → 数据 2 → ACK……
→ STOP
```

**读寄存器：** 主机通常先用“写”告诉从机要读哪个寄存器，再切换方向读取：

```text
START → 从机地址 + W → ACK → 寄存器地址 → ACK
→ Repeated START → 从机地址 + R(1) → ACK
→ 从机发送数据；主机对需继续读取的字节回 ACK
→ 主机对最后一个字节回 NACK → STOP
```

纯接收型设备可能不需要先写寄存器地址；16 位寄存器地址、命令字节和自动地址递增也由从机协议决定。7 位地址与 R/W 位合成总线上的第一个字节，但不同驱动 API 可能要求传“原始 7 位地址”或“左移后的地址”，必须看 API 约定。

### I²C 和 SPI 常用速率是多少？为什么 I²C 通常更慢？

I²C 标准常见模式包括 Standard-mode 100 kbit/s、Fast-mode 400 kbit/s、Fast-mode Plus 1 Mbit/s；更高速模式必须由控制器、器件和电气设计共同支持。SPI 没有统一速率档位，常见从几百 kHz 到几十 MHz，高速 Flash/显示器可更高，最终看主从 Datasheet 和板级信号完整性。

I²C 通常更慢的原因：

- 开漏输出靠上拉电阻和总线电容形成 RC 上升沿，物理上限制速度；SPI 推挽能主动拉高/拉低。
- I²C 每字节还有 ACK、地址、START/STOP 等开销；SPI 每个 SCK 通常都在搬数据。
- I²C 是共享多设备总线，要支持仲裁、时钟同步/拉伸，时序更保守。

**提高 I²C 速率：**

- 硬件：主从都切换到支持的高速模式；按电容和灌电流重新计算上拉；缩短走线、减少支路/连接器和设备数量；合理布局地参考，必要时用 I²C buffer/repeater。
- 软件：优先硬件 I²C + 中断/DMA；减少逐字节函数和日志开销；合并连续寄存器访问，利用自动地址递增；避免无意义 STOP/重新寻址。
- 不能只提高外设分频：若上升时间已超标，频率越高错误越多。应使用示波器验证上升时间和电平。

### 为什么 I²C 是半双工，SPI 是全双工？

I²C 只有一根双向数据线 SDA，同一时刻数据只能朝一个方向传输，所以是半双工；R/W 位和 Repeated START 用来切换方向。

标准四线 SPI 有两条独立数据线 MOSI 和 MISO，每个 SCK 周期双方各传输一位，所以天然全双工。即使应用只想“读”，主机也要发送 dummy 字节来产生时钟；三线/单线双向 SPI 复用数据线，属于半双工变体。完整收发过程见 [[#SPI 为什么是全双工？收发时序是什么？]]。

### I²C 如何进行多主仲裁？什么是“线与”？

SCL/SDA 都是开漏 + 上拉：任何设备拉低，总线就是低；只有所有设备都释放，总线才为高。这种“低电平占优”的共享逻辑常称为 **wired-AND（线与）**；若以“低为真”的负逻辑看，也可描述成线或。

多主同时发送时，每个主机在释放 SDA 发送“1”的同时读取总线：

- 想发 1、实际读到 0，说明另一主机在发 0，本主机立即判定仲裁失败并停止驱动。
- 发 0 的主机继续，不会破坏获胜帧。
- 仲裁通常发生在地址和数据位；相同前缀的主机继续比较，直到出现不同位。

时钟线也通过开漏实现同步：SCL 被任一设备拉低就维持低电平。仲裁只解决总线所有权，软件仍需处理仲裁丢失标志、重试和超时；单主系统通常不会遇到多主仲裁。

#### I²C 多主机之间如何进行时钟同步？

多主机时钟同步不是让多个 MCU 的晶振频率完全相同，而是利用 SCL 的开漏线与特性，把同时工作的主机对齐到同一组总线时钟边界，保证它们能够在同一个 SCL 高电平阶段比较 SDA 并完成仲裁。

多个主机同时拉低 SCL 后，低电平会一直保持到最后一个主机释放：

```text
主机 A：拉低 ──── 释放
主机 B：拉低 ────────── 释放
实际 SCL：低────────────高
```

因此，**实际低电平时间由所有参与者中最长的低电平时间决定**。主机 A 即使已经释放 SCL，读到总线仍是低，也必须等待。支持时钟拉伸的从机继续拉低 SCL 时，同样会延长这个低电平阶段。

当最后一个参与者释放 SCL、总线真正变高后，各主机开始计算自己的高电平时间；最先结束高电平计时的主机首先把 SCL 拉低，其他主机检测到低电平后也同步进入下一周期：

```text
主机 A：释放──────拉低
主机 B：释放────────────准备拉低
实际 SCL：高──────低
```

因此：

```text
实际 SCL 低电平时间 = 各参与者低电平时间中的最长值
实际 SCL 高电平时间 = 各主机高电平时间中的最短值
```

时钟同步和 SDA 仲裁作用不同：SCL 同步负责让各主机的 bit 边界对齐；SDA 仲裁负责决定总线归谁。某个主机想发送 `1`、却在 SCL 高时读到 `0`，说明另一主机正在发送 `0`，它必须判定仲裁失败并停止驱动；获胜主机随后继续产生时钟和传输数据。

> [!tip] 面试短答
> I²C 多主时钟同步利用 SCL 的开漏线与特性：低电平由最晚释放者决定，高电平由最早重新拉低者结束，使所有主机在相同 bit 边界上进行 SDA 仲裁。它同步的是总线时序，不是各 MCU 的晶振频率。

### SPI 与 I²C 的硬件电气特征为什么这样设计？

| 特征 | I²C | SPI |
|---|---|---|
| 输出结构 | SCL/SDA 开漏，外部上拉 | SCK/MOSI/CS 通常推挽，MISO 由被选从机推挽输出 |
| 拓扑 | 多设备共享两根线，协议内寻址 | 主从结构，每从机通常独立 CS |
| 方向 | SDA 双向半双工 | MOSI/MISO 分离，全双工 |
| 设计目标 | 少引脚、可共享、支持仲裁 | 高速度、低协议开销、边沿明确 |

I²C 不能用多个普通推挽输出共线，否则一个拉高、另一个拉低会短路冲突；开漏让多设备安全共享并能边发送边检测仲裁。SPI 用 CS 保证同一时刻仅一个从机驱动 MISO，因此可用推挽获得更快边沿，但软件/硬件必须确保未选从机 MISO 真正高阻。

### I²C 从机地址如何配置？地址相同会怎样？

从机地址可能来自：

- 芯片出厂固定地址。
- ADDR/SA0 等硬件引脚组合。
- 上电后写内部寄存器、OTP/EEPROM 配置。
- MCU 自己做 I²C 从机时，写控制器的 Own Address 寄存器。

同一条总线上两个从机地址相同时，主机无法区分它们：

- **写操作：** 两个从机都会 ACK，并同时接收、执行后续命令。
- **读操作：** 两个从机同时驱动 SDA；一个发送 `1`、另一个发送 `0` 时，低电平占优，主机将读到混合错误数据。

解决时按以下顺序考虑：优先通过 ADDR/SA0 等引脚设置不同地址；其次在只使能一个器件时，通过寄存器逐个修改软件地址；若地址完全固定，则用 RESET/EN 隔离器件、增加 I²C MUX，或将器件分配到不同 I²C 总线。软件改址是否掉电保存、何时生效必须查 Datasheet。

```text
                     ┌─ 通道 0 ─ 设备 A（0x68）
主机 ─ I²C MUX ─────┤
                     └─ 通道 1 ─ 设备 B（0x68）
```

不能依靠“两个器件不会同时响应”：地址相同就是协议层冲突，而不是偶发的时序问题。

### I²C 地址和后续数据会发给所有从机吗？

**不能简单说“所有从机都收到后续数据”。准确说法是：后续数据的电平会到达所有从机的 SDA/SCL 引脚，但只有地址匹配的从机在协议上接收和处理；其他从机的 I²C 状态机会忽略这些位。**

| 所谓“收到” | 地址匹配的从机 | 地址不匹配的从机 |
|---|---|---|
| 引脚上能否看到 SCL/SDA 电平变化 | 能 | 能，因为连接在同一物理总线上 |
| I²C 状态机是否把后续位当成本次数据 | 是 | 否，进入忽略/等待状态 |
| 是否写入接收数据寄存器或 FIFO | 是 | 通常不会 |
| 是否产生正常接收中断、交给软件 | 是 | 通常不会 |
| 是否对后续数据回复 ACK | 是，由当前接收方决定 | 否，保持释放 SDA |

```text
主机：START → 地址+W → 数据1 → 数据2 → STOP
                  ↓
       所有从机采样并比较地址
                  ↓
       地址匹配者 ACK 并继续收发
       地址不匹配者释放 SDA，忽略到 STOP/下一次 START
```

因此，“总线把数据广播到所有管脚”和“所有从机的软件都收到数据”是两回事。I²C 没有独立数据线，物理信号必然经过每个器件；地址过滤通常由从机硬件外设完成，CPU 不需要逐字节读取后再由软件判断是不是自己的数据。

主机写时，被选中的从机接收每个数据字节，并在能够继续接收时逐字节回复 ACK；缓冲区满、不接受命令或发生错误时可以回复 NACK。主机读时，只有地址匹配的从机驱动 SDA 发送数据，其他从机保持释放；主机对需要继续读取的字节回复 ACK，对最后一个字节回复 NACK 后结束读取。

收到 STOP 后，未匹配从机回到空闲监听；收到 Repeated START 后，所有从机重新进入地址判断阶段，主机可以更换目标或切换读写方向。

例外情况包括：启用 General Call 的器件可能共同响应广播地址；两个从机地址相同时会同时认为自己被选中，写时一起接收，读时一起驱动 SDA；某些具有多地址或地址掩码功能的从机也可能响应多个地址。具体行为由从机硬件和 Datasheet 决定。

#### 从机怎样知道当前字节是地址还是数据？

从机不是根据字节的数值判断，而是根据 **START 后的位置和内部协议状态机** 判断：

```text
空闲监听
  ↓ 检测到 START：SCL 高时 SDA 由高变低
地址阶段：接收 7 位地址 + R/W 位
  ├─ 地址匹配 → 第 9 个时钟 ACK → 进入数据阶段
  └─ 地址不匹配 → 不 ACK → 忽略本次事务
数据阶段：每 8 bit 作为一个数据字节
  ↓
STOP → 回到空闲；Repeated START → 重新进入地址阶段
```

硬件 I²C 外设通常自动检测 START、比较本机地址并维护这个状态。地址匹配后，后续字节才会进入接收寄存器/FIFO 并产生接收事件；因此某个值是“地址”还是“数据”，由它在事务中的位置决定，而不是由数值本身决定。

#### 更换从机是否必须重新 START？

**是。切换到另一个从机时，必须发送新的 START 或 Repeated START，然后重新发送目标从机地址。**

```text
先结束旧事务：
START → 从机 A 地址 → 数据 → STOP
START → 从机 B 地址 → 数据 → STOP

保持总线控制权：
START → 从机 A 地址 → 数据
Repeated START → 从机 B 地址 → 数据 → STOP
```

如果还处于从机 A 的数据阶段，即使主机发送的下一个字节数值恰好等于从机 B 的地址，从机 A 仍会把它当作普通数据，从机 B 也不会因此被选中。

> [!tip] 切换从机口诀
> START 决定进入地址阶段；没有新的 START/Repeated START，就不会重新寻址，也不能切换从机。

> [!tip] 面试短答
> I²C 是共享总线，所以后续数据的电平会到达所有从机管脚；但这不等于所有从机都“收到数据”。只有地址匹配者会 ACK，并把后续字节送入接收寄存器或软件；未匹配者释放 SDA 并忽略本次事务，直到 STOP 或下一次 START。

### 项目实例：I²C 主从 GPIO 和硬件如何配置？

工程 `spi_jetson_stm32` 中，Jetson Orin Nano 是主机，STM32F407ZG 的 I2C1 是地址 `0x42` 的从机。

```text
Jetson 主机                         STM32 从机
J12 Pin 5 / SCL  ────────────────  PB6 / I2C1_SCL / AF4
J12 Pin 3 / SDA  ────────────────  PB7 / I2C1_SDA / AF4
J12 Pin 6 / GND  ────────────────  GND
```

#### 主从 GPIO 的配置原则

| 端点 | SCL | SDA | GPIO 模式 |
|---|---|---|---|
| 主机 | 产生时钟，输出高时实际是释放；还要读取真实线电平 | 写时发送，读时接收 | SCL、SDA 都配置为 I²C 复用开漏 |
| 从机 | 通常接收时钟，需要时可拉低做时钟拉伸 | 地址/写阶段接收，读数据和 ACK 时发送 | SCL、SDA 也都配置为 I²C 复用开漏 |

**不能把主机 SCL/SDA 配成普通推挽输出，也不能把从机两根线简单配置成普通输入。** 硬件 I²C 外设会根据主从角色和收发阶段自动控制开漏管、读取总线并切换 SDA 方向。

STM32 从机的 GPIO 配置为：

```c
__HAL_RCC_GPIOB_CLK_ENABLE();
__HAL_RCC_I2C1_CLK_ENABLE();

gpio.Pin       = GPIO_PIN_6 | GPIO_PIN_7;
gpio.Mode      = GPIO_MODE_AF_OD;      // 复用开漏
gpio.Pull      = GPIO_NOPULL;          // 使用板上外部上拉
gpio.Speed     = GPIO_SPEED_FREQ_LOW;
gpio.Alternate = GPIO_AF4_I2C1;        // PB6/PB7 连接到 I2C1
HAL_GPIO_Init(GPIOB, &gpio);
```

Jetson 主机侧由系统 pinmux/设备树将 J12 Pin 5、Pin 3 配给 I²C 控制器，应用通过 `/dev/i2c-7` 使用总线，不应再把这两个管脚当普通 GPIO 手动翻转。

#### 硬件连接重点

- SCL 和 SDA 各需要一只到总线电源的上拉电阻，整条总线一组即可，不是每个设备各加一组。
- 本项目两端都是 3.3 V，Jetson 载板已有约 `2.2 kΩ` 上拉，因此 STM32 使用 `GPIO_NOPULL`。
- 主从必须共地；若 IO 电压不同，需要适合开漏总线的双向电平转换。
- 空闲时 SCL、SDA 都应接近 3.3 V；长期为低说明被器件、错误配置或接线拉住。
- 管脚必须查芯片 AF 表。本项目使用 PB6/PB7 的 AF4；PC6 不支持 I2C1，不能仅靠软件指定 AF 变成 I²C 管脚。

#### STM32 从机外设的最小配置

```c
I2C1->CR1  = 0;
I2C1->CR2  = 42u;                       // APB1 外设时钟为 42 MHz
I2C1->OAR1 = (1u << 14) | (0x42u << 1); // 7 位从机地址 0x42
I2C1->OAR2 = 0;                         // 不使用第二地址
I2C1->CCR  = 210u;
I2C1->TRISE = 43u;
I2C1->CR1  = I2C_CR1_ACK | I2C_CR1_PE;  // 允许 ACK，使能 I2C1
```

主从外设配置的主要区别是：**主机要配置目标从机地址并产生 SCL；从机要配置自己的地址 `OAR1`，等待地址匹配。** 当前 STM32 是从机，所以实际 SCL 频率由 Jetson 主机决定，不能把 STM32 的 `CCR/TRISE` 直接当作实测总线频率。

> [!tip] 面试短答
> I²C 主机和从机的 SCL、SDA 都配置为硬件 I²C 复用开漏，并通过外部电阻上拉；主机负责产生时钟，从机可做时钟拉伸，SDA 由硬件按收发阶段自动切换。硬件上还要共地、保证 IO 电压一致，并按芯片 AF 表选择合法管脚。

### SPI 模式参数配错会出现什么现象？

- **CPHA 配反**：接收端在数据正在变化的边沿采样，常表现为整体左/右移一位、bit0/bit7 错、数据随频率/温度不稳定，或者完全无法识别命令。
- **CPOL 配反**：时钟空闲电平错误，CS 有效或释放时可能产生器件眼中的额外边沿；采样边沿也随之错位。
- **CPOL、CPHA 都与从机不匹配**：读到 `0x00/0xFF`、固定错码、位移或无响应都有可能，不能只靠错误值反推是哪一项。

所谓“SPI clock 正负电平翻了”通常就是 CPOL 反了。它不一定只让每位取反，而是改变空闲态和边沿顺序；有的设备可能偶尔可用，有的会多采/漏采第一位。正确方法是对照从机时序图，用逻辑分析仪同时观察 CS、SCK、MOSI、MISO，而不是盲试四种模式。

### SPI、I²C 各引脚应该配置成什么 GPIO 模式？

**短答：** I²C 的 SCL/SDA 都按开漏总线理解，输出高电平本质是释放总线，输入时直接读总线电平；SPI 的 SCK/MOSI/CS 通常由主机推挽输出，MISO 是被选中从机推挽输出、主机输入，未选中的从机 MISO 必须高阻。

主从方向和 GPIO 配置并列如下（“硬件配置”指使用片上外设，“软件配置”指 GPIO 模拟协议）：

| 协议引脚       | 主机方向                | 主机硬件配置                  | 主机软件配置                    | 从机方向                            | 从机硬件配置                  | 从机软件配置          | 说明                              |
| ---------- | ------------------- | ----------------------- | ------------------------- | ------------------------------- | ----------------------- | --------------- | ------------------------------- |
| I²C SCL    | 输出时钟；也要能读取总线并检测从机拉低 | AF 开漏 + 外部上拉            | 开漏输出；发送高时释放，必要时切输入读取      | 输入时钟；支持 clock stretching 时可主动拉低 | AF 开漏 + 外部上拉            | 开漏输出/释放，需拉低时再驱动 | 高电平不是主动推高，而是释放后由上拉恢复；主从都不能用推挽共线 |
| I²C SDA    | 写时输出，读/ACK/仲裁时释放并读取 | AF 开漏 + 外部上拉            | 开漏输出；发送 1 释放、发送 0 拉低，同时读线 | 接收时读取，发送数据或 ACK 时拉低/释放          | AF 开漏 + 外部上拉            | 开漏输出与输入读取配合     | 支持 ACK/NACK、仲裁和线与；SDA 高电平由上拉形成  |
| SPI SCK    | 输出时钟                | AF 推挽输出；空闲电平由 CPOL 决定   | 推挽输出                      | 输入主机时钟                          | AF 输入/外设输入              | 普通输入            | 只有主机产生 SCK；从机不能自行输出时钟           |
| SPI MOSI   | 输出主机数据              | AF 推挽输出                 | 推挽输出                      | 输入主机数据                          | AF 输入/外设输入              | 普通输入            | 主机按 CPHA 约定在采样边沿前稳定数据           |
| SPI MISO   | 输入从机数据              | AF 输入/外设输入              | 普通输入                      | 输出从机数据；未选中时高阻                   | AF 推挽/三态输出，由 NSS 控制是否驱动 | 推挽输出；未选中时切输入或高阻 | 多从机共用 MISO 时，未选中的从机必须释放总线       |
| SPI CS/NSS | 输出片选；通常低有效          | 普通 GPIO 推挽输出，或硬件 NSS 输出 | 推挽 GPIO 输出                | 输入片选                            | AF/外部中断输入，由 SPI 外设检测    | 普通输入，可配外部中断     | 通常空闲高、选中低；复位期间建议上拉，防止误选从机       |

从机模式时方向要反过来看：SCK、MOSI、CS 是输入，MISO 是输出；但 MISO 只有在本从机被 CS 选中时才允许驱动，否则会和其他从机冲突。不同 MCU 的 “Alternate Function 输入/输出” 写法可能不同，本质是把引脚复用给外设，并由外设控制方向。

### SPI 接线时是否必须共地？

**必须共地。** `GND` 虽然不是 SPI 协议里的逻辑管脚，却是 SCK、MOSI、MISO、CS 电平判断的共同参考，也是信号电流的回流路径。两块板没有可靠共地时，即使示波器看起来偶尔有翻转，接收端也无法稳定判断高低电平，常表现为随机错码、只在低速短线下偶尔可用，或者完全没有响应。

以 MCU 主机连接一个 SPI 从机为例，最小接线是：

```text
MCU 主机                         SPI 从机
---------                       ---------
SCK   ------------------------> SCK
MOSI  ------------------------> SDI / MOSI
MISO  <------------------------ SDO / MISO
CS    ------------------------> CS / NSS
GND   ------------------------- GND      <- 必须共地
VCC   ------------------------- VCC      <- 仅在由主机供电且电压兼容时连接
```

接线和电气配置要点：

- **GND 至少一根且必须可靠。** 短距离单从机通常一根地线足够；排线较长、频率较高或同时有多根高速信号时，应在信号旁安排地线或地平面，缩短回流路径、降低串扰和地弹。
- **VCC 与 GND 不是一回事。** 从机可由独立电源供电，但两侧仍必须共地；只有在确认电压、供电能力和上电时序兼容时，才连接 VCC。不能因为已各自供电就省掉 GND。
- **先确认 IO 电平兼容。** 例如主机为 3.3 V、从机只容许 1.8 V 时，直接连线可能损坏从机；需要电平转换器。GND 共地不等于电平一定兼容。
- **CS 默认保持未选中。** 常见低有效 CS 在复位、MCU 下载和初始化前应保持高电平，必要时加外部上拉，避免从机误把毛刺当作一帧传输开始。
- **SCK/MOSI 不要无依据加上拉或下拉。** 空闲电平由 CPOL 和从机数据手册决定；复位阶段若器件要求确定状态，才按要求加弱上拉/下拉。MISO 在从机未选中时应为高阻，多从机总线可在主机侧加合适弱上拉/下拉避免输入悬空，但必须确认不会影响被选从机驱动。
- **多从机连接。** SCK、MOSI、GND 可以共享；每个从机独立一根 CS；MISO 可以共享，但所有未选中从机都必须三态输出。若器件 MISO 不能释放，需要外部三态缓冲或不要直接并联。
- **长线/高速场景。** 降低 SCK、缩短线缆、使用连续地平面；必要时在主机端给 SCK/MOSI/CS 串联小电阻抑制反射。SPI 本身不适合直接跑很长的板间线缆，恶劣环境应考虑差分收发器或更适合的物理层。

面试短答可以直接说：

> SPI 主机的 SCK、MOSI、CS 通常配置为复用推挽输出，MISO 配置为复用输入；从机方向相反，且未选中时 MISO 必须高阻。除了四根逻辑线，主从必须共地，因为 GND 是信号电平参考和回流路径；若不共地，电平没有共同基准，通信会不稳定。VCC 是否连接取决于供电方案，但共地不能省；还要确认两侧 IO 电平兼容。

> [!warning] 常见坑
> I²C 配成推挽输出可能导致两个器件一个拉高、一个拉低而短路；SPI 多从机若 MISO 不能高阻，会出现读数互相干扰；CS 初始电平没先拉高就初始化 SPI，可能让从机误收一帧。

### NACK 什么时候收到？

题目里的 “NACT” 通常是 **NACK**。地址阶段 NACK 可能是无设备、地址错、未上电或设备忙；写数据阶段 NACK 表示从机不接受；主机读取时，对最后一个字节主动回 NACK，通知从机结束读取。

### 为什么需要上拉？

I²C 是开漏结构，设备只能主动拉低，释放后由上拉电阻恢复高电平，这也支持线与和仲裁。阻值过大导致 RC 上升慢，过小导致灌电流/功耗大。应结合 VDD、总线电容、上升时间和器件灌电流计算；内部上拉往往太弱，不能代替合适的外部上拉。

### 最多挂几个设备？

不能简单答 127 个。7 位地址含保留地址，地址相同的设备会冲突；实际还受总线电容、走线、上拉、速率和驱动能力限制。可改地址或用 I²C 多路复用器扩展。

### I²C 现场算时间

每字节通常需 9 个时钟（8 bit + ACK/NACK）。400 kHz 写 1 字节寄存器地址和 4 字节数据，粗算地址+W、寄存器地址、4 数据共 6 字节：`6 × 9 / 400 kHz = 135 μs`。还需考虑 START/STOP、时钟拉伸和软件间隙。
## 4. UART 与 USART

**短答：** UART 是通用异步收发器；USART 还支持同步模式。USART 配成异步模式时通常就按 UART 使用。

帧格式：`空闲高 → 起始位低 → 5~9 数据位 → 可选校验 → 停止位高`。双方必须约定波特率、数据位、停止位和校验。

### 什么是同步和异步？UART 加一根时钟线就会变成同步吗？

- **同步通信**：收发双方共享或恢复出一个连续/成帧的时钟，接收端按明确的时钟边沿采样，例如 SPI、I²C。
- **异步通信**：不传输独立时钟，双方各用本地时钟；UART 接收端检测起始位后按约定波特率进行过采样，并用停止位重新校验帧边界。

给 TX/RX 随便并联一根 GPIO 时钟线，不会自动把 UART 变成同步协议。必须让两端硬件都支持相同的同步模式，并约定时钟源、极性、相位、数据方向和帧格式。USART 的同步模式会由 CK 引脚输出或接收串行时钟，管脚要配置为相应 Alternate Function；具体支持能力和接线看该 MCU 的 USART 章节。若自行用定时器输出时钟、再用 GPIO/UART 传数据，本质是在设计新协议，接收外设也必须按该时钟采样。

### 波特率及配错的后果

波特率是每秒符号数；普通二进制 UART 可近似看成 bit/s。误差小时接收端还能在位中间正确采样；误差累积过大会导致数据错、帧错误或无法接收。配置时要核对外设时钟、分频、过采样和晶振误差。

`8N1` 每字节占 10 bit：

```text
发送时间 = 字节数 × 10 / 波特率
```

115200 baud 发 100 字节约 `8.68 ms`，有效数据吞吐约 `11.52 KB/s`。

### UART 如何保证可靠性？

- 物理层：共地、电平匹配；长线/干扰环境用 RS-485/隔离/屏蔽等。
- 协议层：帧头、长度、命令、序号、CRC、转义。
- 机制层：ACK/NACK、超时、重传、去重、流控。
- 实现层：中断或 DMA + 环形缓冲；IDLE 中断处理不定长帧；处理 ORE/FE/NE/PE。
- ISR 只搬数据/通知任务，解析放到任务中，并检测缓冲溢出。

### UART 的 TX 和 RX 应配置成什么 GPIO 模式？

**TX 通常配置为 UART/USART 复用推挽输出，RX 配置为复用输入；两端按 TX 接 RX、RX 接 TX，并且必须共地。**

```text
设备 A                              设备 B
TX：复用推挽输出 ────────────────→ RX：复用输入
RX：复用输入     ←──────────────── TX：复用推挽输出
GND              ───────────────── GND
```

| 管脚 | 常用配置 | 原因 |
|---|---|---|
| TX | Alternate Function + Push-Pull | 由 UART 外设主动产生起始位、数据位和停止位，能够主动拉高/拉低 |
| RX | Alternate Function Input；无上下拉或弱上拉 | 只采样对端 TX；弱上拉可在断线或对端未上电时保持空闲高，减少假起始位 |

UART 空闲电平通常为高，发送起始位时 TX 由高变低。它通常是点对点连接，不需要 I²C 的线与和仲裁，因此 TX 一般不用开漏。

新系列 STM32 常将 TX、RX 一起写成 `GPIO_MODE_AF_PP`：

```c
gpio.Pin       = GPIO_PIN_9 | GPIO_PIN_10;  // USART1 TX/RX 示例
gpio.Mode      = GPIO_MODE_AF_PP;
gpio.Pull      = GPIO_NOPULL;
gpio.Speed     = GPIO_SPEED_FREQ_HIGH;
gpio.Alternate = GPIO_AF7_USART1;
HAL_GPIO_Init(GPIOA, &gpio);
```

这不代表 RX 会向外推挽输出。AF 只是把两个管脚交给 USART1，外设仍将 TX 作为输出、RX 作为输入；`PP` 只对需要输出的 TX 驱动级有意义。STM32F1 的旧式写法通常更直观：TX 配复用推挽输出，RX 配浮空输入或上拉输入。

硬件还要确认双方使用同一种电气标准。3.3 V TTL/CMOS UART 不能直接连接真正的正负电压 RS-232；与 RS-485 通信还需要收发器和方向控制。只发送时可只连接 TX+GND，只接收时可只连接 RX+GND。

> [!tip] 面试短答
> UART TX 是外设控制的复用推挽输出，RX 是复用输入；新系列 MCU 可能把两者统一配置成 AF 模式，但最终方向仍由 TX/RX 功能决定。两端需要 TX/RX 交叉、共地、电平标准一致，并保持波特率和帧格式一致。

### UART 的基本配置是什么？参数都正确仍读错怎么办？

基本配置至少包括：外设时钟源和分频、波特率、数据位、停止位、奇偶校验、收发方向、过采样、bit order；需要时再配 RTS/CTS、反相、半双工、DMA、中断和 FIFO。GPIO 上 TX 通常为复用推挽且空闲高，RX 为复用输入，两端 TX/RX 交叉并共地；还必须确认双方使用同一种 TTL/CMOS、RS-232 或 RS-485 电气标准。

**波特率不匹配的现象：** 少量误差时可能偶发乱码；误差大时出现帧错误 FE、校验错误 PE、持续乱码或完全收不到。误差会在一帧内累计，因此字节较长、停止位较少时裕量更紧。

波特率和共地正确仍不代表一定正常，继续检查：

1. 数据位、校验位、停止位不一致；例如一端 8N1、另一端 8E1。
2. 电平标准错误：TTL 不能直接接 RS-232，3.3 V/5 V 容限不匹配，RS-485 A/B 或方向控制错误。
3. TX/RX 接反、引脚复用选错、RX 浮空、线长/噪声/地弹导致边沿失真。
4. 实际外设时钟不是以为的频率，波特率寄存器虽相同但真实波特率不同；用示波器量一个 bit 的宽度。
5. RX 过载产生 ORE，DMA 长度/缓存一致性错误，环形缓冲覆盖，ISR 不及时。
6. 字节序、协议转义、帧长、CRC 或结构体对齐错误——这时 UART 字节本身可能完全正确，是上层解析错。
7. 回显、换行符、文本编码或二进制数据显示方式造成“看起来乱码”。

定位时先用逻辑分析仪确认线上的原始字节和帧格式，再判断问题在物理层、UART 外设层还是协议解析层。

## 5. 硬件实现与软件模拟

| 维度 | 硬件外设 | GPIO 软件模拟 |
|---|---|---|
| 时序 | 稳定、速率高 | 受中断/调度抖动影响 |
| CPU | 占用低，可配 DMA | 占用高，常忙等 |
| 引脚 | 受复用限制 | 灵活 |
| 用途 | 正式、高速、低功耗 | 引脚受限、低速或特殊协议 |

- 硬件 I²C：复用开漏 + 外部上拉；软件 I²C：GPIO 开漏，输出高实质是释放线路。
- 硬件 SPI：SCK/MOSI 通常复用推挽，MISO 输入，CS 可硬件或 GPIO；软件 SPI 对应 GPIO 推挽/输入。
- UART：TX 通常复用推挽，RX 为输入/复用输入。

---

## 6. EXMC 和 LocalBus

**短答：** HC32F4A0 的 EXMC 是外部存储器控制器，用来把片内 AHB 访问转换成 SRAM、PSRAM、NOR Flash、NAND Flash、SDRAM 等片外存储器的并行总线时序。LocalBus 通常指这种本地并行外部总线：MCU 像访问一段地址空间一样访问片外器件，硬件自动产生地址线、数据线、片选、读写控制和等待信号。

```text
CPU / DMA 发起 AHB 访问
  ↓
地址落入外部存储器映射区
  ↓
EXMC 根据地址选择 SMC / DMC / NFC 和对应片选
  ↓
输出地址、数据、CS、OE、WE、ADV、WAIT 等总线信号
  ↓
片外 SRAM / PSRAM / NOR / SDRAM / NAND 完成读写
```

HC32F4A0 参考手册中 EXMC 主要分为三个子控制器：

| 子模块 | 含义 | 典型外设 |
|---|---|---|
| SMC | Static Memory Controller | SRAM、PSRAM、NOR Flash |
| DMC | Dynamic Memory Controller | SDRAM |
| NFC | NAND Flash Controller | NAND Flash |

EXMC 的价值是让外部并行存储器进入 MCU 的统一地址空间。软件侧可以用指针或结构体访问映射地址，硬件侧由 EXMC 负责把一次 AHB 读写拆成外部器件需要的总线周期。AHB 访问宽度和外部存储器位宽不一致时，EXMC 可以做自动分割；例如 CPU 发起 32 bit 访问，而外部数据总线只有 16 bit，就会拆成两个外部总线操作。

### EXMC 和普通 GPIO 模拟有什么区别？

| 维度 | EXMC / LocalBus | GPIO 软件模拟 |
|---|---|---|
| 地址访问 | 映射到固定地址区，可像内存一样读写 | 需要手动翻转地址、数据、控制线 |
| 时序 | 控制器硬件产生，可配置建立/保持/等待周期 | 受中断、编译优化和延时函数影响 |
| 吞吐 | 高，适合大容量并行存储器 | 低，只适合调试或低速简单器件 |
| CPU 占用 | 低，可由 CPU/DMA 发起块访问 | 高，通常忙等 |
| 复杂度 | 引脚多、时序和 PCB 要求高 | 硬件简单但软件开销大 |

### 配置 EXMC 要关注什么？

1. **存储器类型**：先判断是 SRAM/PSRAM/NOR、SDRAM 还是 NAND，对应 SMC、DMC、NFC。
2. **地址映射和片选**：确认访问地址落在哪个外部存储区，片选 CS 是否和硬件连接一致。
3. **数据位宽**：8/16/32 bit 必须和外部芯片、PCB 连接、软件访问宽度匹配。
4. **同步/异步时序**：SMC 可配置同步或异步访问；异步 SRAM/NOR 常看地址建立、数据建立、OE/WE 脉宽和保持时间。
5. **地址数据复用**：部分 NOR Flash、PSRAM 可复用地址线和数据线，需要 ADV 等锁存控制信号。
6. **WAIT/Ready 信号**：外部器件较慢或同步访问时，可用 WAIT 拉长总线周期。
7. **GPIO 复用和电气**：EXMC 引脚多，必须核对 AF、驱动能力、上电状态、走线长度、阻抗、串扰和时钟边沿。
8. **Cache/DMA 一致性**：如果用 DMA 或带 Cache 的内核访问外部存储，要明确缓冲区属性、Cache clean/invalidate 和内存屏障。

### 面试怎么说？

可以这样答：

> 我理解的 LocalBus 是 MCU 片外并行扩展总线，HC32F4A0 通过 EXMC 实现。EXMC 挂在 AHB 侧，内部有 SMC、DMC、NFC，分别面向 SRAM/PSRAM/NOR、SDRAM、NAND。软件访问外部映射地址时，EXMC 自动输出地址、数据、片选和读写控制信号，所以比 GPIO 模拟快得多、CPU 占用也低。实际调试时重点看地址映射、片选、位宽、时序参数和 PCB 信号质量。

> [!warning] 常见坑
> EXMC 不是“更快的 SPI”，它通常要占用大量并行引脚，对时序和 PCB 更敏感；也不能只看 MCU 支持 EXMC，还要确认当前封装是否引出了足够的地址线、数据线和控制线。

# 三、Cortex-M4 内核

## 1. 常用寄存器

| 寄存器 | 作用 |
|---|---|
| R0~R3 | 参数、返回值、临时寄存器 |
| R4~R11 | 被调用者保存寄存器 |
| R12 | 临时寄存器 IP |
| R13/SP | 栈指针，实际为 MSP 或 PSP |
| R14/LR | 返回信息；异常中可保存 EXC_RETURN |
| R15/PC | 程序计数器 |
| xPSR | 条件标志、当前异常号、执行状态 |
| PRIMASK | 屏蔽可配置优先级异常 |
| BASEPRI | 按优先级阈值屏蔽，RTOS 临界区常用 |
| CONTROL | Thread 模式特权级和 MSP/PSP 选择 |

常用系统寄存器：`VTOR` 向量表基址；`AIRCR` 优先级分组/复位请求；`ICSR` 异常状态；`CFSR/HFSR/MMFAR/BFAR` 定位 Fault；NVIC 的 ISER/ICER、ISPR/ICPR、IABR、IPR 分别管理使能、挂起、活动和优先级。

> [!warning] 架构混淆
> Cortex-M 主要区分 Thread mode 与 Handler mode，并用 MSP/PSP。不要把经典 ARM7/ARM9 的 CPSR/SPSR、多工作模式和 FIQ 银行寄存器答案直接套到 Cortex-M4。

## 2. 异常及处理流程

**短答：** 异常是打断顺序执行、让 CPU 进入处理程序的事件总称；Reset、NMI、Fault、SVC、PendSV、SysTick 和外部中断都属于异常。

1. 异常变成 Pending，内核按使能、屏蔽和优先级仲裁。
2. 硬件把 `R0~R3、R12、LR、PC、xPSR` 压入当前栈（FPU 时可能有扩展栈帧）。
3. 从向量表取处理函数地址，进入 Handler mode；Handler mode 使用 MSP。
4. ISR 执行，软件保存其他必要寄存器。
5. 根据 LR 中 `EXC_RETURN` 恢复现场并返回。

尾链和迟到机制可以减少连续异常的出入栈开销。

## 3. 中断及处理流程

**短答：** 中断是外设或外部事件向 CPU 发出的异步处理请求，本质上属于异常。CPU 不需要反复轮询设备，而是在事件发生后暂停当前代码，转去执行中断服务函数 ISR，处理完成后再恢复原程序。

常见中断源包括 GPIO 边沿、定时器更新、UART 收发、ADC 转换完成、DMA 传输完成和通信错误等。一个中断能真正进入 CPU，通常要同时满足：**事件标志置位、外设中断源使能、NVIC 通道使能、没有被屏蔽，并且优先级满足响应条件。**

### 中断处理流程

```text
外设事件发生
    ↓
外设状态位置位，并向 NVIC 提交中断请求
    ↓
NVIC 将中断置为 Pending，按使能、屏蔽状态和优先级仲裁
    ↓
CPU 完成当前指令，硬件自动压入基础现场
R0~R3、R12、LR、PC、xPSR
    ↓
从向量表取得 ISR 地址，进入 Handler mode 执行 ISR
    ↓
判断中断来源，读取必要数据，按手册清除中断标志
    ↓
通知主循环或任务继续处理
    ↓
通过 EXC_RETURN 硬件恢复现场，从被打断处继续运行
```

ISR 应遵循“短、快、确定”的原则：只做清标志、取数据、写缓冲区、释放信号量或发送任务通知等必要工作，复杂计算、阻塞等待、延时和大量日志放到主循环或任务中处理。

要同时检查外设标志、外设中断使能、NVIC 使能三层。清标志可能是写 0、写 1、读寄存器后再写寄存器，必须查 Reference Manual；清除方式错误会导致中断退出后立即再次进入。

### 中断函数编写的注意事项

**短答：** ISR 只处理必须立即完成且执行时间可控的工作，核心是**确认来源、保存数据、清除标志、通知后续处理**。不能阻塞，不能执行耗时或时间不可预测的操作，也不能直接调用不支持中断上下文的接口。

| ISR 中可以做 | 说明 |
|---|---|
| 读取并判断中断状态 | 一个 IRQ 可能对应多个中断源，必须判断真正来源 |
| 按手册清除中断标志 | 防止退出后立刻再次进入；注意写 0 清、写 1 清或特定读写顺序 |
| 读取接收寄存器、保存采样值 | 及时取走 UART、ADC 等数据，避免溢出或覆盖 |
| 向预分配的环形缓冲区写入少量数据 | 只搬运数据，解析协议放到主循环或任务中 |
| 设置事件标志或计数器 | 通知主循环稍后处理，操作要保证原子性 |
| 使用 RTOS 的 `...FromISR()` 接口 | 可发送队列、信号量或任务通知，并按返回值请求任务切换 |
| 执行少量、时间确定的寄存器操作 | 例如更新 PWM 比较值、启动下一次 DMA 传输 |

| ISR 中不应该做 | 原因与替代方案 |
|---|---|
| 延时或忙等待 | 占住 CPU，增加其他中断延迟；改为定时器、状态机或任务延时 |
| 等待锁、信号量、队列或事件 | ISR 不能睡眠，容易死锁；只用非阻塞的 FromISR 接口通知任务 |
| 执行复杂算法、协议解析和大循环 | 执行时间长且不确定；只保存原始数据，在线程上下文处理 |
| 大量 `printf`、日志输出 | 格式化和串口发送很慢，还可能加锁；记录简短事件码，后台统一输出 |
| `malloc/free` 或动态创建对象 | 时间不可预测、可能加锁并造成碎片；使用静态或预分配缓冲区 |
| 调用普通 RTOS API | 普通 API 可能阻塞或操作调度器；使用明确允许的 `...FromISR()` 版本 |
| 调用不可重入函数 | 若主程序或嵌套 ISR 同时调用，会破坏内部状态；改用可重入接口或移到任务中 |
| 递归、大数组或大量局部变量 | 快速消耗 MSP，中断嵌套时更容易栈溢出 |
| 无必要地进行浮点运算 | 可能触发额外 FPU 上下文保存，增加延迟和栈占用；确认编译器及 RTOS 的 FPU 策略 |
| 长时间关闭全部中断 | 破坏实时性，可能丢事件；临界区应尽量短，并优先使用原子操作或优先级屏蔽 |

编写 ISR 还要注意以下问题：

1. **先处理数据还是先清标志，要看外设机制。** 对可能覆盖的数据先读数据；对持续触发的标志要尽快按手册清除，不能机械地规定一律先清或后清。
2. **共享变量不等于加了 `volatile` 就安全。** `volatile` 只保证编译器真实访问内存，不保证 `count++`、读改写和多字节访问具有原子性；必要时使用原子操作或极短临界区。
3. **处理同一 IRQ 下的所有来源。** 例如 UART IRQ 可能同时包含 RX、TX、空闲和错误标志，ISR 应逐项判断，避免遗漏后持续进中断。
4. **防止事件丢失。** 布尔标志只能表达“至少发生一次”，高频事件应使用计数器、队列、环形缓冲区或 DMA。
5. **控制最坏执行时间。** 评估 ISR 最大耗时、触发频率、嵌套深度和 MSP 峰值，而不只是看平均执行时间。
6. **正确处理 RTOS 唤醒。** `...FromISR()` 唤醒更高优先级任务后，应按端口要求在退出 ISR 前请求一次上下文切换。

一个常见写法是让 ISR 只完成“上半部”，把耗时业务留给“下半部”：

```c
void UART_IRQHandler(void)
{
    BaseType_t task_woken = pdFALSE;

    if (uart_rx_ready()) {
        uint8_t data = uart_read_data();
        ring_buffer_push_from_isr(&rx_buffer, data);
        vTaskNotifyGiveFromISR(rx_task_handle, &task_woken);
    }

    if (uart_error_pending()) {
        uart_clear_error_by_manual();
    }

    portYIELD_FROM_ISR(task_woken);
}
```

上例只表达结构，实际寄存器读取顺序、清标志方式和函数名必须以芯片手册及所用 RTOS 端口为准。

### 中断的嵌套

**短答：** 中断嵌套是 CPU 正在执行某个 ISR 时，又响应了更高抢占优先级的中断。高优先级 ISR 执行完后，CPU 恢复低优先级 ISR 的现场并继续执行，最后再返回原来的线程代码。

```text
主程序运行
  └─ 中断 A 到来：主程序现场压栈，进入低优先级 ISR A
       └─ 更高抢占优先级中断 B 到来：ISR A 现场再次压栈
            └─ ISR B 执行完成，恢复 ISR A 现场
       └─ ISR A 从被打断处继续，执行完成后恢复主程序现场
  └─ 主程序从被打断处继续运行
```

能否嵌套主要看以下条件：

1. 新中断已经使能且处于 Pending 状态，没有被 `PRIMASK`、`BASEPRI` 等屏蔽。
2. 新中断的**抢占优先级必须高于**当前正在执行的异常；Cortex-M 中优先级数值越小，优先级越高。
3. 抢占优先级相同的中断不能互相打断，子优先级只决定多个 Pending 中断的先后响应顺序。
4. 进入嵌套中断时，硬件再次保存基础现场。Handler mode 使用 MSP，因此嵌套层数越深，中断栈占用越大。
5. 高优先级 ISR 返回后先恢复低优先级 ISR，不会直接跳回主程序或任务。

例如 A 的抢占优先级数值为 3，B 为 1，则 B 可以打断 A；若 B 为 3、仅子优先级更高，B 只能等待 A 结束；若 B 为 5，则优先级更低，也必须等待。

嵌套能降低关键事件的响应延迟，但会增加栈占用、共享数据竞争和时序分析难度。关键共享数据可用极短临界区、原子操作或无锁缓冲区保护，不能为了省事长时间关闭全部中断。

**关系：中断是一类异常，异常不只有中断。**

### 面试怎么说？

> 中断是外设或外部事件触发的一类异步异常。事件发生后，外设置位标志并向 NVIC 请求，NVIC 根据使能、屏蔽和优先级仲裁；CPU 自动保存基础现场，从向量表进入 ISR。ISR 中先确认来源并按手册清标志，只做必要的快速处理，再通过 EXC_RETURN 恢复现场。若 ISR 执行期间来了抢占优先级更高的中断，就会形成嵌套；同抢占优先级只能排队，子优先级不决定抢占。嵌套越深，MSP 栈占用和共享资源风险越大。

> [!warning] 常见坑
> 把“子优先级高”误认为可以抢占；忘记清外设标志导致反复进入；在 ISR 中延时、阻塞或大量打印；临界区关闭中断时间过长；嵌套较深却没有评估 MSP 栈空间；多个中断共享变量却没有使用 `volatile` 和必要的同步保护。`volatile` 只能保证实际读写，不能保证复合操作的原子性。

## 4. NVIC 与中断优先级

NVIC 是内核集成的嵌套向量中断控制器，负责使能、挂起、优先级仲裁、抢占和向量化入口。

**优先级数值越小，逻辑优先级越高，0 最高。**

- 抢占优先级决定能否打断当前 ISR。
- 子优先级只决定同抢占级且同时 Pending 时谁先响应。
- `PRIGROUP` 决定优先级位如何分配；实际实现位数看 `__NVIC_PRIO_BITS`。
- 是否抢占还受屏蔽寄存器和当前异常状态影响。

> [!warning] FreeRTOS 高频坑
> 能调用 `...FromISR()` 的中断，逻辑优先级不能高于 FreeRTOS 允许系统调用的阈值；优先级 0 通常绝不能调用 FreeRTOS API。

## 5. 复位种类、流程和备份域

常见来源：POR/PDR、BOR 欠压、NRST 外部复位、`SYSRESETREQ` 软件复位、IWDG/WWDG、低功耗退出和 Option Byte 相关复位。启动后应尽早读取并记录 RCC 复位原因，再清除标志。

多种复位是为了区分电源异常、软件跑飞、时钟异常和主动升级等故障，并限定复位范围。RTC/备份寄存器需在主系统复位时保持，因此位于可由 VBAT 供电的备份域；主系统复位通常不清空备份域，精确行为查具体型号手册。

## 6. 大小端

小端把最低有效字节放在最低地址，Cortex-M 通常用小端。例如 `0x12345678` 从低地址到高地址为 `78 56 34 12`。协议/文件格式可能指定大端，应显式序列化，不能直接发送结构体内存。

# 四、C 语言与内存

## 1. 字节对齐

**短答：** 对齐让对象地址满足类型/ABI 要求，保证合法高效访问；结构体还会补齐为其最大对齐要求的整数倍，以保证数组中每个元素对齐。

```c
typedef struct {
    char a;       // offset 0，随后通常填充 3 字节
    int32_t b;    // offset 4
    int16_t c;    // offset 8，末尾通常再填充 2 字节
} Example;        // 常见 ABI 下 sizeof 为 12
```

把成员按对齐要求从大到小排列常可减少填充。实际布局由编译器、ABI 和选项决定，用 `sizeof`、`offsetof` 验证。

对齐访问通常只需一次总线事务；非对齐访问可能变慢，某些指令、总线或外设访问会 Fault。`packed` 可消除填充，但可能导致非对齐访问、性能下降甚至 Fault；线上格式最好显式编解码。

## 2. `volatile` 能保证线程安全吗？

不能。它主要要求编译器每次实际访问对象，适合外设寄存器和异步变化标志；不保证原子性、互斥或内存顺序，不能代替锁、临界区或原子操作。

## 3. 栈和堆

- 栈自动分配释放、快但容量固定；递归、大数组、深调用可导致溢出。
- 堆生命周期灵活，但会失败、碎片化且耗时不确定。
- RTOS 每个任务有独立任务栈，中断通常用 MSP 对应的栈。
- 实时系统常用静态对象/内存池，或只在初始化阶段分配。

## 4. `const`、`static`

- `const` 表示不能通过该左值修改，不等于必然存放在 Flash。
- 函数内 `static` 具有静态存储期，只初始化一次。
- 文件级 `static` 是内部链接，只在当前编译单元可见。

## 5. 函数指针

**短答：** 函数指针是保存函数入口地址的指针。通过它可以间接调用签名匹配的函数，常用于回调函数、中断向量表、驱动接口、协议分发表和状态机。函数指针让调用方依赖统一接口，而不依赖某个具体实现。

### 如何声明和调用？

```c
int add(int a, int b)
{
    return a + b;
}

int (*operation)(int, int) = add;

int result1 = operation(2, 3);
int result2 = (*operation)(2, 3);  // 与上一行等价
```

`int (*operation)(int, int)` 的含义是：`operation` 是一个指针，指向“接收两个 `int` 参数并返回 `int`”的函数。阅读复杂声明时先看变量名，再根据括号向外读。

| 声明 | 含义 |
|---|---|
| `int (*fp)(int)` | `fp` 是函数指针，指向参数为 `int`、返回 `int` 的函数 |
| `int *fp(int)` | `fp` 是函数，参数为 `int`、返回 `int *` |
| `void (*handlers[4])(void)` | `handlers` 是含 4 个元素的数组，每个元素都是函数指针 |
| `void (**fp)(void)` | `fp` 是二级指针，指向一个函数指针 |

`()` 的优先级高于 `*`，所以声明函数指针时 `(*fp)` 外面的括号不能省略。实际工程中通常使用 `typedef` 简化：

```c
typedef int (*binary_operation_t)(int left, int right);

binary_operation_t operation = add;
int result = operation(10, 20);
```

函数名在大多数表达式中会转换成函数地址，因此 `operation = add` 和 `operation = &add` 都可以；调用时 `operation()` 和 `(*operation)()` 等价。

### 函数指针有什么用途？

#### 1. 回调函数

调用方完成某件事后，通过函数指针反向通知注册方：

```c
typedef void (*transfer_done_cb_t)(int status, void *context);

typedef struct {
    transfer_done_cb_t callback;
    void *context;
} transfer_t;

void transfer_complete(transfer_t *transfer, int status)
{
    if (transfer->callback != NULL) {
        transfer->callback(status, transfer->context);
    }
}
```

同时保存 `void *context` 可以把对象实例或用户数据传回回调，避免依赖全局变量。回调在哪个上下文执行必须写清楚：如果由 ISR 调用，回调也必须遵守 ISR 的限制，不能阻塞或调用普通 RTOS API。

#### 2. 驱动接口与硬件抽象

```c
typedef struct {
    int  (*init)(void);
    int  (*read)(uint8_t *data, size_t length);
    int  (*write)(const uint8_t *data, size_t length);
    void (*deinit)(void);
} device_ops_t;
```

不同的 SPI、I²C 或模拟设备提供各自实现，上层只持有 `device_ops_t`，不需要知道底层硬件细节。这种方式常用于 BIOS/BSP、设备驱动框架和单元测试中的 mock。

#### 3. 查表分发

```c
typedef void (*command_handler_t)(const uint8_t *data, size_t length);

#define ARRAY_SIZE(array) (sizeof(array) / sizeof((array)[0]))

static const command_handler_t command_table[] = {
    handle_start,
    handle_stop,
    handle_query,
};

void dispatch_command(uint8_t command, const uint8_t *data, size_t length)
{
    if (command < ARRAY_SIZE(command_table) && command_table[command] != NULL) {
        command_table[command](data, length);
    }
}
```

函数表可以减少很长的 `switch`，也适合协议命令和表驱动状态机。但命令值不连续或表较稀疏时，使用“命令 ID + 函数指针”的结构体表通常更节省空间。

### 函数指针使用注意事项

1. **调用前检查是否为 `NULL`。** 未注册的回调不能直接调用。
2. **函数签名必须完全兼容。** 参数个数、参数类型、返回类型和调用约定不匹配会产生未定义行为；不要靠强制类型转换掩盖编译器警告。
3. **保证指针来源可信。** 越界写、栈溢出或对象生命周期结束都可能破坏函数指针，使 PC 跳到非法地址并触发 HardFault。
4. **表索引必须检查边界。** 外部协议提供的命令字不能未经校验直接作为函数表下标。
5. **并发注册要同步。** 一个任务修改回调、另一个任务或 ISR 同时调用时可能产生竞态；应在初始化期固定，或使用临界区和明确的生命周期管理。
6. **不要保存无效上下文。** 回调的 `context` 不能指向已经返回的局部变量或已释放对象。
7. **明确执行上下文和耗时限制。** ISR 回调、定时器回调和任务回调能调用的 API 不同，接口文档应明确说明。
8. **安全系统可校验地址范围。** 调用前可检查函数地址是否位于合法代码区，并结合 MPU、栈保护和控制流完整性降低损坏风险。

### 面试怎么说？

> 函数指针保存函数入口地址，声明时关键是 `(*fp)` 的括号，例如 `int (*fp)(int)` 表示指向参数和返回值都是 `int` 的函数。它常用于回调、驱动接口和查表分发，能让上层依赖统一接口，实现解耦。工程上我会用 `typedef` 简化签名，并检查空指针、表索引和生命周期；函数签名不匹配、越界写破坏函数指针或调用已经失效的回调，都可能让 PC 跳到非法地址并触发 HardFault。

> [!warning] 常见坑
> 混淆“函数指针”和“返回指针的函数”；调用空回调；把不兼容函数强制转换后塞进函数表；未检查外部命令索引；回调保存了局部变量地址；在 ISR 回调里执行阻塞操作；多个上下文同时修改和调用同一个函数指针。

# 五、常用外设

## 1. PWM 与 Timer

PWM 用定时器 ARR 决定周期、CCR 决定占空比。向上计数常见公式：

```text
PWM 频率 = f_tim / ((PSC + 1) × (ARR + 1))
占空比 ≈ CCR / (ARR + 1)
```

APB 分频可能影响定时器时钟，中心对齐公式也不同。Timer 还可做更新中断、输出比较、输入捕获、编码器、单脉冲、触发 ADC/DMA。输入捕获测频：`f_input = 计数时钟 / 相邻同类边沿计数差`，注意溢出和滤波。

## 2. 看门狗：IWDG 与 WWDG

### 看门狗是不是一个倒数定时器？

**可以这样理解。** 看门狗是专门监督系统健康状态的硬件计数器：启动后不断计数，软件必须在超时前执行规定的刷新操作（喂狗）；如果计数到达超时条件仍未刷新，看门狗就产生复位或中断。

```text
正常：装载计数值 → 倒计时 → 健康检查通过 → 喂狗并重新装载 → 倒计时……
异常：装载计数值 → 倒计时 → 程序卡死、未喂狗 → 超时 → MCU 复位
```

它和普通定时器的主要区别不是“能否计时”，而是设计目的和可靠性：普通定时器负责定时、PWM、捕获等功能；硬件看门狗有专用寄存器和复位通路，通常不依赖业务软件正常运行。IWDG 还常使用独立低速时钟，因此主时钟或程序异常时仍可能继续工作。

一般应使用 MCU 自带的 IWDG/WWDG，而不是随便选择 TIMx 模拟。普通定时器可以实现软件超时监控，但若其中断无法执行、时钟停止或软件复位路径损坏，就可能失去兜底能力。

| 项目 | IWDG | WWDG |
|---|---|---|
| 时钟 | 独立低速时钟 | 通常来自 APB |
| 条件 | 超时前喂 | 只能在窗口内喂，过早/过晚都异常 |
| 用途 | 卡死、主时钟异常 | 执行过快/过慢、时序异常 |

### 超时时间和喂狗周期如何确定？

看门狗超时时间由系统的最坏执行时间决定，而不是固定的经验值：

```text
看门狗超时时间 > 两次健康检查之间的最坏间隔 + 调度抖动 + 安全余量
```

配置值通常由看门狗时钟、预分频器和重装载值共同决定；具体公式和计数方向以芯片参考手册为准。独立低速时钟误差可能较大，设计时应按其最慢/最快边界校核，不能只使用典型频率计算。

- 设置过短：Flash 擦除、通信超时、临界区过长或中断突发时可能误复位。
- 设置过长：真正卡死后恢复太慢。
- 喂狗周期应明显小于超时时间，但不能在任意高频路径中无条件刷新。

一般设备常取几百毫秒到数秒，但最终要测量启动、自检、Flash 操作、通信等待和主循环/任务调度的最坏时间。若某个合法操作本身长于看门狗周期，应将它拆成可验证的小步骤，或为该工作模式重新设计超时策略，不能简单在阻塞循环里不断喂狗。

### 裸机项目应该在哪里喂狗？

裸机系统通常在一轮关键功能全部正常完成后喂狗，让一次喂狗表达“系统健康”，而不只是“CPU 还在执行指令”。

```c
for (;;) {
    bool healthy = true;

    healthy &= (read_sensor() == OK);
    healthy &= (run_control() == OK);
    healthy &= (update_output() == OK);

    if (healthy) {
        watchdog_refresh();
    }
}
```

每个可能阻塞的外设等待都应有**软件超时**，否则程序可能永远卡在到不了喂狗点的位置。不要在等待循环中无条件喂狗：

```c
while (!device_ready()) {
    if (deadline_expired()) {
        return ERROR;
    }
    /* 此处不无条件喂狗 */
}
```

耗时操作结束后也不能机械地喂狗，应先确认操作确实成功。异常时偶然误喂一次通常只会把复位推迟一个周期；真正危险的是异常路径仍能持续喂狗。对于已确认且无法恢复的故障，工程上也可在保存必要现场后主动触发受控复位，不必刻意等待看门狗超时。

### RTOS 下应该怎样喂狗？

RTOS 下推荐采用“关键任务报到，监控任务统一喂硬件狗”的结构：

```text
采集任务 ──健康上报──┐
控制任务 ──健康上报──┼→ WatchdogTask 检查全部关键任务
通信任务 ──健康上报──┘          ├─ 全部按期运行 → 喂硬件狗
                                └─ 任一超时/异常 → 记录故障，不喂狗
```

各业务任务只有在完成本周期的关键工作后才能上报健康。监控任务可使用 Event Group、Task Notification、位图或“最后成功时间戳”收集状态，但不能自己无条件定时喂狗，否则即使控制、采集任务都已卡死，只要 WatchdogTask 还能运行，系统就永远不会复位。

简单系统可以用位图：每个关键任务成功完成一轮后设置自己的 bit，监控任务看到本轮所有 bit 齐全才喂狗并清零。任务周期不同时，更适合为每个任务保存独立的最后成功时间和允许截止时间：

```c
bool system_healthy(uint32_t now)
{
    return elapsed(now, sensor_last_ok)  <= SENSOR_DEADLINE &&
           elapsed(now, control_last_ok) <= CONTROL_DEADLINE &&
           elapsed(now, comm_last_ok)    <= COMM_DEADLINE;
}
```

并非所有任务都必须纳入硬件看门狗。控制、采集、安全通信等关键任务应监控；LED、普通日志等非关键任务可只记录故障或单独恢复，避免一个非关键功能导致整机复位。若任务只是在循环中报到，却没有验证输出、队列推进或状态机进展，仍可能出现“任务活着但业务已死”的假健康，因此健康条件应尽量对应实际功能进展。

### RTOS 下如何判断周期任务和事件任务是否健康？

**不能要求所有任务在每个看门狗窗口内都执行一次。** 正确做法是由 `WatchdogTask` 按任务类型检查健康状态，再决定是否统一喂硬件狗。

#### 周期任务：检查最后一次成功完成时间

周期任务有明确的执行周期，可以在每次完成关键工作后更新时间戳。监控任务每 500 ms 检查一次，但检查的是“距离上一次成功完成是否超过该任务自己的允许间隔”，而不是简单检查这 500 ms 内有没有运行：

```c
temp_last_ok = xTaskGetTickCount();
bool temp_ok = elapsed(now, temp_last_ok) <= pdMS_TO_TICKS(12000);
```

例如硬件看门狗超时 2 s、`WatchdogTask` 每 500 ms 检查一次，而 `TempTask` 是 10 s 周期、允许最大间隔 12 s，硬件狗仍然可以正常工作。硬件狗不需要大于所有业务任务周期，只要负责喂狗的监控任务能及时运行，并按每个任务的最大允许静默时间判断即可。

#### 事件任务：检查“有事件后是否及时完成”

事件任务平时阻塞等待消息是正常状态，不能因为它很久没有被唤醒就判定异常：

```text
没有命令 → ControlTask = Blocked/IDLE → 正常
收到命令 → ControlTask = RUNNING → 记录开始时间
处理完成 → ControlTask = IDLE → 正常
```

可以为事件任务维护 `IDLE/RUNNING/ERROR` 状态和 `start_tick`。监控任务只在状态为 `RUNNING` 时检查处理时长；例如一次 WSS 控制动作最多允许 300 ms，运行 100 ms、250 ms 都正常，持续 2 s 未回到 `IDLE` 才判定超时。

```c
if (control_state == TASK_RUNNING &&
    elapsed(now, control_start_tick) > CONTROL_MAX_TIME) {
    control_ok = false;
}
```

#### 事件任务还应检查消息积压

通信任务没有数据时处于 Blocked 是正常的；但 RX Queue 从 1 条持续增长到 100 条，说明任务可能卡住、处理太慢或消费者没有运行。健康检查应结合任务状态、处理持续时间、队列/环形缓冲积压和实际业务进展，而不是只看任务是否被调度。

| 任务类型 | 健康判断 |
|---|---|
| 温度任务、状态巡检任务 | 最后成功完成时间是否在自己的允许窗口内 |
| WSS/控制任务 | 有任务时是否在最大处理时间内回到 IDLE；无任务时 Blocked 正常 |
| 通信接收任务 | 无数据时 Blocked 正常；有数据后是否及时消费队列 |
| 快速切换/故障处理任务 | 平时 Blocked 正常；触发后是否按时完成 |
| 日志任务 | 日志队列是否持续增长、丢弃或停止消费 |

#### WSS 示例

```text
TempTask       100 ms 周期  → 更新 temp_last_ok
MonitorTask    200 ms 周期  → 更新 monitor_last_ok
CommTask       事件触发     → 检查队列消费和处理超时
ControlTask    事件触发     → 检查 IDLE/RUNNING 和最大处理时长
WatchdogTask   500 ms 检查  → 汇总健康条件后决定是否喂狗
硬件看门狗    2 s 超时
```

健康检查窗口不是“等所有任务刚好跑一圈”，而是：周期任务按各自截止时间仍然活跃，事件任务没有超时或积压，关键业务确实取得进展，全部满足后才喂狗并开始下一轮检查。

> [!tip] 判断口诀
> **周期任务看“最后一次成功完成距今多久”；事件任务看“有事情后多久完成”；没有活干时，Blocked 是健康状态，长期 Running 或队列持续积压才可能是异常。**

### 喂狗有哪些注意事项？什么时候不能喂？

喂狗必须表示“系统在规定时间内完成了关键工作并仍然健康”，不能只表示“某段代码或某个任务还在运行”。建议让硬件看门狗只有一个统一刷新入口，所有关键模块通过状态、心跳计数或最后成功时间参与健康判断，避免多个位置随意喂狗而掩盖故障。

**可以喂狗的条件：**

- 裸机主循环的一轮关键采集、控制、输出都成功完成。
- RTOS 中所有关键任务都在各自截止时间内完成有效工作并上报健康。
- 可恢复错误已经真正恢复，并重新验证外设或业务状态正常。
- 长耗时操作按可验证的小块推进，当前块成功且整体仍在规定超时范围内。

**以下情况不能无条件喂狗：**

| 场景 | 为什么不能喂 |
|---|---|
| 高频定时器/SysTick/普通中断 | 业务任务即使已经死锁，中断仍可能持续运行并一直喂狗 |
| `while (!ready)` 等阻塞等待循环 | 外设永久不响应时会形成“卡死但一直喂狗” |
| 独立 WatchdogTask 只按固定周期刷新 | 只能证明喂狗任务被调度，不能证明采集、控制、通信正常 |
| 函数返回后不检查结果就刷新 | 函数可能以错误、超时或部分完成状态返回 |
| 已检测到关键故障但尚未恢复 | 喂狗会延迟或阻止系统进入预期复位恢复流程 |
| 只收到一次陈旧心跳标志 | 任务可能上报后立刻卡死，应按周期清零或检查最后成功时间 |
| WWDG 不在允许窗口内 | 过早和过晚刷新都可能触发窗口看门狗复位 |

错误示例：

```c
while (!device_ready()) {
    watchdog_refresh();  // 错：设备永久故障时系统永远不会复位
}
```

更合理的写法是先设置软件截止时间，成功后才更新健康状态；超时后退出等待、记录错误并尝试有限次数恢复。确认关键故障无法恢复时，可以保存最小故障现场后主动软件复位，也可以停止喂狗等待硬件复位，但不能继续执行一条会周期性刷新看门狗的异常路径。

Flash 擦除、固件升级、自检等合法长操作不能简单关闭看门狗或在循环里盲目喂狗。应提前测量最坏时间，将工作拆成小块，并在每块写入和校验成功后刷新；升级过程中还要保证掉电恢复和回滚。若看门狗由 Option Byte 等方式硬件启动，Bootloader 和 App 都必须遵守同一套超时策略。

调试器可能配置为暂停 CPU 时同时冻结看门狗，这只适合调试，不能据此判断量产程序不会超时。量产前应在不依赖调试冻结的条件下验证看门狗复位、复位原因记录和故障恢复路径。

> [!tip] 判断口诀
> 不是“代码走到这里就喂”，而是“关键功能确认健康才喂”；不能在与业务健康无关、即使系统故障仍会持续执行的路径中喂狗。

> [!warning] 常见错误
> 在高频中断里无条件喂狗；独立喂狗任务不检查业务状态；阻塞等待时循环喂狗；把“函数返回”直接等同于“操作成功”；所有任务共用同一截止时间；启动或 Flash 擦写的最坏时间未计入超时。

复位后应尽早读取并保存复位原因；若确认由看门狗复位，可结合持久化错误码、任务状态和关键寄存器定位故障，再清除复位标志，避免只看到“设备重启”却没有现场。

## 3. ADC

ADC 把模拟电压量化为数字值：

```text
数字码 ≈ Vin / Vref × (2^N - 1)
```

精度受 Vref、分辨率、采样时间、源阻抗、噪声、线性度和校准影响。源阻抗高时要加采样时间或缓冲。定时器触发 + DMA 循环采样能提供稳定周期；平均能减随机噪声，不能消除偏置。

## 4. DMA

DMA 在外设与内存或内存之间搬运数据，降低 CPU 占用。配置包括源/目标、方向、宽度、长度、自增、请求、优先级和普通/循环模式。常用于 UART/SPI、ADC 循环采样和双缓冲。

仍需处理半传输/全传输/错误、缓冲区所有权、竞态和总线争用；带 D-Cache 的芯片还要维护 Cache 一致性。

### DMA 的完整工作过程是什么？

1. CPU 配置 DMA 请求源、源/目标地址、传输数量、数据宽度、自增方式、方向、优先级和模式。
2. 外设事件（例如 UART RX 非空、ADC 转换完成）向 DMA 控制器发出请求；内存到内存模式也可由软件启动。
3. DMA 取得总线控制权，从源地址读数据、向目标地址写数据，并更新地址和剩余计数。
4. 达到一半、全部完成或发生错误时设置标志，可产生中断通知 CPU。
5. Normal 模式停止；Circular 模式自动重新装载数量并继续。

DMA 的价值是把“每个字节一次 CPU 中断/搬运”变成“每半块或一整块处理一次”，提升吞吐并减少抖动，但它不会理解协议内容。

### 关键配置项怎么理解？

- **方向**：Peripheral-to-Memory、Memory-to-Peripheral、Memory-to-Memory。
- **地址自增**：外设数据寄存器地址通常固定；内存缓冲地址通常递增。
- **数据宽度**：外设与内存可分别选 byte/half-word/word，必须与寄存器和缓冲类型匹配，否则会截断、填充或错位。
- **Normal/Circular**：一次性报文用 Normal；ADC 连续采样、音频流常用 Circular。
- **优先级**：多个 DMA 请求冲突时决定仲裁顺序，不代表一定能抢占已经开始的总线传输。
- **Burst/FIFO/双缓冲**：高性能 DMA 可能支持，可减少总线事务或让两个缓冲交替工作，具体依 MCU。

### DMA 双缓冲如何避免数据被覆盖？

最常见的是 ping-pong：DMA 写缓冲 A 时 CPU 处理 B，随后交换。Circular 单缓冲也可用 Half-Transfer/Transfer-Complete 把数组分成前后两半。

```text
DMA 写前半 → HT 中断：CPU 处理前半，同时 DMA 写后半
DMA 写后半 → TC 中断：CPU 处理后半，同时 DMA 回到前半
```

CPU 必须在 DMA 再次写到该区域前处理完成；若最坏处理时间大于半缓冲填充时间，就要增大缓冲、降低数据率或优化处理。ISR 中只交接缓冲所有权，耗时处理放任务中。

### DMA 常见故障有哪些？

- 请求通道/触发源映射选错，DMA 根本不启动。
- 先开外设请求后配 DMA，首个数据丢失；停止时顺序错误造成尾数据问题。
- 地址、自增、宽度或长度错误导致越界和内存破坏。
- 未清旧标志、未处理 TE/FE/DME 等错误。
- CPU 与 DMA 同时读写同一缓冲，没有所有权协议或内存屏障。
- DMA 和 CPU/其他主机争用总线，实时延迟增大。
- 带 D-Cache 时，发送前未 clean 导致 DMA 读到旧数据；接收后未 invalidate 导致 CPU 仍读 Cache 旧副本。还要满足 cache line 对齐，避免破坏相邻数据。

## 5. Flash 与 SRAM

| 项目 | Flash | SRAM |
|---|---|---|
| 掉电 | 保留 | 丢失 |
| 读写 | 读可能有等待；擦写慢 | 快 |
| 写入 | 按页/扇区擦除后编程 | 直接读写 |
| 寿命 | 擦写次数有限 | 无 Flash 式寿命问题 |
| 用途 | 代码、常量、参数 | 变量、栈、堆、缓冲 |

参数保存要考虑掉电保护、版本、CRC、擦写寿命和磨损均衡。

## 6. EEPROM 与 Flash 有什么区别？如何选择？

EEPROM（不是 “E2PROM” 的另一种器件，E²PROM 就是 EEPROM 的写法）和 Flash 都属于掉电保持的非易失存储器，但擦写粒度和使用方式不同：

| 项目 | EEPROM | NOR Flash（MCU 常见） |
|---|---|---|
| 擦写粒度 | 常可按字节或小页更新 | 通常按页/扇区擦除、按字/双字/页编程 |
| 擦写寿命 | 通常高于普通 Flash，具体看器件 | 通常较低，必须看 Datasheet |
| 容量/成本 | 容量较小、单位容量成本高 | 容量大、单位容量成本低 |
| 速度 | 写入较慢，常有内部写周期 | 读取快；擦除慢且粒度大 |
| 典型接口 | I²C/SPI 或 MCU 片内 EEPROM | MCU 片内 Flash、SPI/QSPI NOR |
| 典型用途 | 少量且经常更新的参数、计数器 | 程序、资源、大块日志、较少更新的配置 |

**选择方法：**

- 几十字节到几 KB 的配置，更新频繁且希望按小粒度写：优先 EEPROM、FRAM 或专用 NVM。
- 固件、字库、图片、大块数据和 OTA 镜像：选 Flash。
- 芯片没有 EEPROM 时，可用 Flash 模拟 EEPROM，但必须做双页/日志式更新、掉电恢复、CRC、序号和磨损均衡，不能每改一个参数就反复擦同一扇区。
- 更新极频繁、掉电一致性要求高时，FRAM/MRAM 可能比两者更合适。

不要只背“EEPROM 寿命 100 万、Flash 1 万次”这类固定数字；不同工艺和型号差异很大，必须用实际器件的 endurance、retention、页写时间和工作温度规格计算寿命。

## 7. GPIO 与硬件基础

### 7.1 GPIO“八种模式”

**短答：** STM32F1 常说的 GPIO 八种模式是：浮空输入、上拉输入、下拉输入、模拟输入、通用推挽输出、通用开漏输出、复用推挽输出、复用开漏输出。新系列通常拆成 Mode、Output Type、Pull、Speed、Alternate Function 几个字段，但本质仍是在描述输入/输出类型、默认电平、驱动方式和是否交给外设。

| 模式 | 输入/输出特征 | 典型使用场景 | 注意点 |
|---|---|---|---|
| 浮空输入 | 高阻输入，无内部上下拉 | 外部电路已经提供确定电平的信号输入，如外部比较器、推挽输出传感器 | 不可悬空，否则容易受噪声影响抖动 |
| 上拉输入 | 输入 + 内部弱上拉，默认高电平 | 按键低有效、开漏输出信号的低速检测、需要默认高的输入 | 内部上拉阻值大，抗干扰和时序要求高时用外部上拉 |
| 下拉输入 | 输入 + 内部弱下拉，默认低电平 | 按键高有效、需要默认低的使能/检测信号 | 内部下拉较弱，长线或干扰环境要加外部电阻 |
| 模拟输入 | 关闭数字输入缓冲，接入模拟通道 | ADC 输入、DAC 输出相关引脚、未用引脚低功耗配置 | 数字输入关闭后不能按普通 GPIO 读电平 |
| 通用推挽输出 | MCU 主动拉高和主动拉低 | LED、片选 CS、继电器驱动前级、普通数字控制线 | 不允许两个推挽输出直接相连且输出相反电平 |
| 通用开漏输出 | 只能主动拉低，高电平靠上拉 | 线与、低速电平转换、多个器件共享中断线 | 必须有内部或外部上拉；速度受上拉电阻和总线电容影响 |
| 复用推挽输出 | 引脚交给片上外设，外设主动拉高/拉低 | UART TX、SPI SCK/MOSI、定时器 PWM、USART CK | 需要选对 AF/重映射、速度和空闲电平 |
| 复用开漏输出 | 引脚交给片上外设，外设按开漏方式驱动 | I²C SCL/SDA、SMBus | 需要上拉；多设备共享总线时不能配置成推挽 |

### GPIO 的输入模式如何理解？

**你说的四种：浮空输入、上拉输入、下拉输入、模拟输入，确实是常见的 GPIO 输入配置分类。** 但要注意，不同资料里的“四种模式”可能指不同层级：

| 层级 | “四种”具体指什么 |
|---|---|
| STM32F1 的经典模式说法 | 直接把浮空输入、上拉输入、下拉输入、模拟输入列为四种输入模式；再加 4 种输出/复用输出，合计常说 GPIO 八种模式 |
| STM32F4 等新系列的 `MODER` | `Input / Output / Alternate Function / Analog` 四种基础模式；上拉、下拉通过 `PUPDR` 单独选择 |
| 输入配置的实际组合 | `Input + No Pull`（浮空）、`Input + Pull-Up`、`Input + Pull-Down`，以及 `Analog`；所以工程上仍常把它们总结成四类输入状态 |

对应关系可以记成：

```text
浮空输入 = Input + No Pull
上拉输入 = Input + Pull-Up
下拉输入 = Input + Pull-Down
模拟输入 = Analog（通常关闭数字输入缓冲）
```

因此“AF 输入/外设输入”不在这四种输入类型里：它不是普通 GPIO 输入配置，而是 `MODER = Alternate Function` 后，由 UART、SPI、Timer 等外设从该管脚采样。比如 UART RX 是外设输入、SPI 从机 SCK/MOSI 是外设输入，但 GPIO 的基础模式仍然叫 **AF**，不是“AF 输入”这个额外模式。

面试时可以这样回答：

> STM32F1 常把 GPIO 直接描述成八种模式，其中输入有浮空、上拉、下拉、模拟四种；新系列则把 Mode 和 Pull 拆开，Mode 选择 Input/Output/AF/Analog，Input 下再用 Pull 选择无上下拉、上拉或下拉。AF 输入只是说明外设从管脚采样，不是 GPIO 的第五种模式。

**使用场景怎么总结：** 普通输入看外部有没有默认电平，悬空就加上拉/下拉；模拟信号用模拟模式；普通控制信号多用推挽输出；共享线、线与、电平转换和 I²C 用开漏；外设控制的引脚用复用模式。回答时先说明具体 MCU 系列，不能把 F1 的 CRL/CRH 寄存器模型套到所有 STM32 或 HC32。

### 普通输出与复用输出的本质区别是什么？

**本质区别是引脚输出数据由谁产生：不带“复用”的普通输出由 GPIO 控制器产生，带“复用”的输出由 UART、SPI、Timer、I²C 等片上外设产生。** “推挽/开漏”是后一级的电气驱动方式，与“普通/复用”是两个不同维度。

```text
                    ┌─ GPIO ODR/BSRR：软件写 0 或 1 ─────┐
输出数据来源选择 MUX ┤                                    ├→ 推挽/开漏输出级 → 物理管脚
                    └─ 外设信号：UART_TX/PWM/SPI_SCK… ───┘
                         ↑
                    Mode 和 AF 选择
```

| 模式 | 信号来源 | 软件直接控制方式 | 管脚电气效果 | 典型用途 |
|---|---|---|---|---|
| 通用推挽输出 | GPIO 控制器 | 写 `ODR/BSRR` 或 `HAL_GPIO_WritePin()` | 主动拉高、主动拉低 | LED、使能、普通 CS |
| 通用开漏输出 | GPIO 控制器 | 写 0 拉低，写 1 释放 | 只能主动拉低，高电平依赖上拉 | 软件 I²C、共享中断线 |
| 复用推挽输出 | 选定的片上外设 | 配置并启动外设，由外设改变电平 | 外设主动拉高、主动拉低 | UART TX、SPI SCK/MOSI、PWM |
| 复用开漏输出 | 选定的片上外设 | 配置并启动外设，由外设拉低或释放 | 只能主动拉低，高电平依赖上拉 | 硬件 I²C SCL/SDA |

例如同一个 PA5：

```c
/* 普通推挽输出：电平由软件写 GPIO 决定 */
gpio.Mode = GPIO_MODE_OUTPUT_PP;
HAL_GPIO_Init(GPIOA, &gpio);
HAL_GPIO_WritePin(GPIOA, GPIO_PIN_5, GPIO_PIN_SET);

/* 复用推挽输出：波形由 SPI1_SCK 外设决定 */
gpio.Mode      = GPIO_MODE_AF_PP;
gpio.Alternate = GPIO_AF5_SPI1;
HAL_GPIO_Init(GPIOA, &gpio);
```

切到复用模式后，继续写 GPIO 的 `ODR/BSRR` 通常不能直接改变管脚输出，因为输出 MUX 已选中外设信号；必须启动并操作对应外设。反过来，只设置 AF 也不会自动产生波形，还必须使能外设时钟并正确配置、使能 UART/SPI/Timer 等外设。

新系列 STM32 通常把配置拆成三个部分：`MODER` 选择普通输出还是复用功能，`AFR` 选择具体外设信号，`OTYPER` 选择推挽还是开漏。STM32F1 常把它们组合命名成“通用推挽输出、复用推挽输出”等八种模式，但内部思想相同。

> [!warning] 容易误解的地方
> `GPIO_MODE_AF_PP` 不表示这个管脚此刻一定是输出。例如 SPI 从机统一把 SCK、MOSI、MISO、NSS 配给 SPI 复用功能后，外设仍会把 SCK/MOSI/NSS 当输入，只在被选中时通过 MISO 输出。AF 决定管脚连接哪个外设，最终方向还取决于外设角色和当前工作阶段。

> [!tip] 面试短答
> 普通输出和复用输出的区别是数据源：普通输出由 CPU 通过 GPIO 的 ODR/BSRR 控制，复用输出由片上外设硬件控制；推挽或开漏只决定最终怎么驱动高低电平。复用模式还需要选择正确 AF 并使能对应外设，单独配置 GPIO 不会自动产生外设波形。

### AF（Alternate Function）复用是什么？

**短答：** AF 复用是通过芯片内部的引脚复用矩阵，把某个 GPIO 连接到 UART、SPI、I²C、Timer、ADC 等片上外设，由外设逻辑接管该引脚的输入/输出，而不是让 CPU 逐次读写 GPIO。

一个引脚通常有多个候选功能，例如同一个管脚可能既能做普通 GPIO，也能做 `USART_TX`、`SPI_SCK` 或 `TIM_CHx`；同一外设也可能有多个候选引脚。AF 编号不是通用常量，必须查具体 MCU 的 Datasheet 引脚复用表。

#### AF 到底要“复用成什么”？谁决定？

AF 要复用成的不是一个抽象的“SPI 模式”，而是一个**具体外设信号**，例如 `SPI1_SCK`、`SPI1_MOSI`、`SPI1_MISO`、`USART2_TX` 或 `TIM3_CH1`。可选组合完全由**具体芯片型号、封装和引脚复用矩阵**决定，软件只能从芯片预先提供的组合中选择，不能把任意 GPIO 连到任意外设。

例如某些 STM32F4 型号中，SPI1 可以使用：

```text
PA5  -- AF5 --> SPI1_SCK
PA6  -- AF5 --> SPI1_MISO
PA7  -- AF5 --> SPI1_MOSI
```

这里要配置的不是“PA5 设为 SPI”，而是：

```text
PA5: MODER = Alternate Function
PA5: AFR   = AF5
PA5: 输出类型/速度/上下拉按 SPI SCK 的电气要求配置
```

然后芯片内部的 mux 才把 `SPI1_SCK` 接到 PA5 的引脚驱动器。换成另一颗 MCU、另一种封装，或者改用 SPI2，同名管脚和 AF 编号都可能不同。F1 系列常通过 `AFIO` 的 remap 位选择整组备选引脚，不一定有 F4 这类 `AF0~AF15` 编号；HC32 等芯片也有自己的端口功能选择寄存器。因此，工程里应以 **Datasheet 的 pin definition / alternate function table** 和 **Reference Manual 的 GPIO/IO mux 寄存器说明** 为准。

#### AF 是时分复用吗？

**不是。** AF 是片内硬件多路选择器（mux）的**静态连接选择**：某一时刻，一个物理引脚通常只能连接到一个选定功能，或者作为普通 GPIO 使用。

```text
同一个 PA5 引脚的候选连接

GPIO 输出 ─┐
SPI1_SCK ──┼─[片内 mux，由 AF/重映射寄存器选择]─> PA5 引脚
TIM2_CH1 ──┤
USARTx_CK ─┘
```

它不是把一个引脚按时间片轮流分给 SPI、UART、Timer 使用。运行中当然可以重新写 AF/重映射寄存器，把引脚改接到另一个外设，但这是一次**配置切换**，不是协议运行期间的时分共享；切换前应停止传输、释放 CS、禁用或等待原外设不忙，再重新配置新外设，否则容易产生毛刺、半帧和总线冲突。

一句话记忆：

> AF 由芯片的引脚复用表限定；软件选择“这个脚现在接哪一个预定义外设信号”；它是空间上的硬件连线选择，不是时间上的轮流复用。

#### I²C 和 UART 能否共用一组 GPIO？为什么不建议频繁切换？

**可以，但必须满足两个条件：** 这组引脚的 AF 复用表同时支持目标 I²C 和 UART 信号，并且两个外设不会在同一时刻使用这组引脚。

例如某个引脚可以按工作阶段配置为：

```text
阶段 1：I2C_SCL / I2C_SDA
        ↓ I²C 事务结束，确认总线释放
停止 I²C 外设并重新配置 GPIO/AF
        ↓
阶段 2：USART_TX / USART_RX
```

这不是只把 `AF4` 改成 `AF7` 就结束了。切换时通常还要处理：

1. 等待 UART 发送完成，或等待 I²C 的 STOP/总线空闲，确认没有半帧数据。
2. 禁止对应外设请求和中断，必要时关闭 DMA，清除 Pending 标志。
3. 关闭原外设，按芯片要求释放/复位其状态机。
4. 将引脚切到安全状态，再重新设置 `MODER`、`AFR`、输出类型、上下拉和速度。
5. I²C 通常需要复用开漏 + 外部上拉；UART TX 通常是复用推挽，RX 是复用输入，电气属性不同。
6. 配置并使能新的 UART/I²C 外设，先检查空闲电平，再开始传输。

**为什么不建议频繁切换？**

- 切换窗口可能产生毛刺、伪起始位、额外 SPI 时钟或半帧。
- 原外设没有真正停止时，重新改 AF 可能造成丢字节、DMA 竞态或错误中断。
- I²C 器件和 UART 收发器若同时物理连接，可能互相驱动同一根线；I²C 的开漏上拉与 UART 的推挽电平也可能冲突。
- 频繁改寄存器、停启外设和恢复状态机会增加实时性、功耗和调试复杂度。

因此工程上通常按以下优先级选择：

- **引脚足够**：I²C 和 UART 使用独立引脚，最稳定、最好调试。
- **只在工作模式间切换**：可以，例如启动阶段 UART 下载配置，初始化完成后永久切换到 I²C。
- **每几十毫秒来回切换**：尽量避免；若无法避免，应由一个统一的 PinMux 管理器串行切换，并用状态机、互斥锁和超时保护。

一句话回答：

> AF 支持动态重新选择外设，但它解决的是“一个引脚可连接多个候选功能”，不代表引脚适合在多个通信协议之间高频跳转。

**典型配置顺序：**

1. 查引脚复用表，确认该管脚支持目标外设、AF 编号和是否与 SWD/JTAG、晶振或其他功能冲突。
2. 使能 GPIO 端口和目标外设的时钟。
3. 把 GPIO 的 Mode 设为 Alternate Function，而不是普通 Input/Output。
4. 设置 Output Type、Pull、Speed；例如 I²C 通常为开漏+上拉，SPI SCK/MOSI 通常为推挽。
5. 把 AFR/复用选择寄存器写成对应 AF 值（新系列常分 `AFRL` 与 `AFRH`；F1 常见的是重映射机制，寄存器模型不同）。
6. 初始化外设本身的波特率、时序、方向和中断/DMA，最后使能外设。
7. 用调试器读回 GPIO/AF 寄存器，再用示波器或逻辑分析仪确认引脚确实出现目标波形。

**AF 与 GPIO 的关系：** AF 只决定“谁控制引脚”，不自动决定电气属性。复用成功但推挽/开漏、上下拉、速度或空闲电平配置错误，仍会出现无波形、总线冲突或通信错误。外设输入脚通常需要配置为复用输入；外设输出脚需要复用输出；双向接口（如 I²C）由外设和开漏结构共同完成方向切换。

#### “AF 输入/外设输入”为什么不在 GPIO 四种模式里？

**因为“AF 输入”是信号方向的描述，不是第五种 GPIO 模式。** 新系列 STM32 的 GPIO `MODER` 通常只有四种基础选择：

```text
00：Input
01：General-purpose Output
10：Alternate Function
11：Analog
```

当 `MODER = 10` 时，GPIO 已经进入 **AF 模式**；之后由 `AFR` 选择具体外设信号。这个 AF 信号最终是输入还是输出，由外设角色和具体信号决定：

| 说法 | 真正含义 |
|---|---|
| AF 输入 / 外设输入 | 引脚处于 AF 模式，外设从该管脚采样；例如 SPI 从机的 SCK/MOSI、UART RX |
| AF 输出 / 外设输出 | 引脚处于 AF 模式，外设向该管脚驱动；例如 SPI 主机的 SCK/MOSI、UART TX |
| AF 双向 | 外设在不同阶段控制方向；例如 I²C 的 SCL/SDA |

**为什么 GPIO 表里又经常写 `GPIO_MODE_AF_PP`？** 在 STM32 HAL 中，`GPIO_MODE_AF_PP` 的 `AF` 表示“交给外设”，`PP` 表示输出级采用推挽；它不代表这个管脚在所有时刻都向外输出。比如 SPI 从机的 SCK、MOSI 虽然可以统一配置为 AF 相关模式，但外设实际把它们当输入；真正输出的只有被选中时的 MISO。

不同系列的表现略有区别：

- **STM32F4 等新系列**：通常配置 `MODER=AF`、`AFR=具体编号`，再配置 `OTYPER/PUPDR/OSPEEDR`；输入信号的“输入”方向主要由外设内部决定。
- **STM32F1**：常见“浮空输入、复用推挽输出、复用开漏输出”等组合名称。外设输入脚往往配置成浮空输入或上拉输入，未必存在单独叫“AF 输入”的选项。
- **SPI/I²C/UART**：不要只看 GPIO 模式名字，要结合主从角色和外设手册确认哪个脚由谁驱动。

所以表格中写“AF 输入/外设输入”，是为了说明**主从方向和外设数据流向**，不是要在 GPIO 四种 `MODER` 模式之外再增加一种模式。

**常见故障：**

- AF 编号或引脚选错，外设寄存器工作但目标管脚没有波形。
- 只配置了 GPIO，没有使能外设时钟或没有开启外设。
- 选中的引脚与 DMA、定时器通道或调试接口冲突。
- 复用推挽/开漏选错，I²C 没上拉，SPI 多从机 MISO 未高阻。
- F1 的 AFIO 重映射、F4/更新系列的 AFR 配置方式混用。
- 外设初始化前后又被其他模块重新初始化 GPIO，导致 AF 被改回普通 GPIO。

### 7.2 GPIO 原理和用途

- **浮空输入**：高阻，适合外部已有确定驱动；不可长期悬空。
- **上/下拉输入**：内部弱电阻提供默认态；关键场景用外部电阻。
- **模拟输入**：关闭数字输入缓冲，供 ADC 等使用；未用引脚设模拟常可降功耗。
- **推挽输出**：主动拉高/拉低，驱动强、速度快；两个相反电平的推挽输出不能直连。
- **开漏输出**：只能拉低，输出高是释放，需上拉；适合 I²C、线与和电平转换。
- **复用功能**：引脚交给片上外设。UART TX/SPI 常用复用推挽，I²C 用复用开漏。

#### GPIO Speed 控制什么？为什么不是越高越好？

GPIO 的 `Speed` 配置控制的是输出驱动器的**边沿速度、驱动能力和大致的输出切换能力**，不是让 GPIO 自动以某个频率翻转。它主要影响上升时间、下降时间、输出电流以及对负载电容的充放电速度；对普通输入脚通常没有实际意义，但对推挽输出和复用外设输出有效。

不同 STM32 系列的选项名称略有差异，常见形式如下：

| 常见选项 | 含义 | 典型用途 |
|---|---|---|
| Low | 较慢边沿、较小驱动 | LED、继电器控制、低速控制信号 |
| Medium | 中等边沿和驱动 | 普通 GPIO、低中速通信 |
| High | 较快边沿和驱动 | 较高速 UART、SPI、定时器输出 |
| Very High | 最快边沿和驱动 | 高速 SPI、外部时钟等，需结合 PCB 和负载使用 |

有些 STM32F1 直接用 2 MHz、10 MHz、50 MHz 等名称，有些 F4/新系列使用 Low、Medium、High、Very High。这里的“MHz”或档位主要是数据手册规定的输出性能等级，**不等于 GPIO 必然只能输出这个频率**，具体上限要查对应芯片的数据手册。

选择原则是：

1. 先根据协议时序和实际负载，确认上升/下降时间满足要求。
2. 在满足时序的前提下选择尽可能低的速度档位。
3. 走线长、负载电容大、频率高时，可能需要提高速度；必要时用示波器检查边沿。
4. 速度过高会带来更大的瞬态电流、EMI、串扰、振铃和功耗，甚至造成误触发。
5. I²C 是开漏输出：下降沿与 GPIO 速度有关，上升沿主要由外部上拉电阻和总线电容决定，不能只把 Speed 调到最高来解决上升沿慢。

例如普通 LED 不需要 `Very High`；SPI 的 SCK/MOSI 可以从 `High` 开始，若频率、线长或负载导致边沿不满足时序再提高；I²C 应优先按总线电容选择合适的上拉电阻和速度档位。

**面试短答：** GPIO Speed 是输出边沿/驱动能力配置，不是输出频率配置。应按信号速度、负载电容、走线和时序选择“够用的最低档位”，速度过高反而会增加 EMI、串扰、振铃和功耗。

#### 如何初始化一个 GPIO？

**短答：** 先开 GPIO 端口时钟，再确定引脚的模式、输出类型、上下拉、速度和复用功能，写入初始输出电平，最后启用相关中断；输出引脚应尽量先设安全电平再切到输出，避免毛刺。

通用步骤：

1. 根据原理图确认端口、引脚、电平、外部上下拉和上电安全状态。
2. 使能 GPIO 外设时钟；某些 MCU 还要解除保护或配置电源域。
3. 若为输出，先写安全初值到输出锁存寄存器，再切换输出模式。
4. 配置 Mode：Input / Output / Alternate Function / Analog。
5. 配置 Push-Pull/Open-Drain、Pull-Up/Pull-Down/No-Pull、Speed。
6. 若给外设使用，选择正确 Alternate Function，并先配置对应外设时钟。
7. 若为外部中断，配置 EXTI 映射、边沿、清 Pending，并设置 NVIC 优先级和使能。
8. 读取输入或翻转输出验证；关键高速信号用示波器检查电平和边沿。

以 STM32 HAL 的 LED 推挽输出为例（型号对应头文件和宏需按工程修改）：

```c
__HAL_RCC_GPIOA_CLK_ENABLE();

/* 先给安全初值，防止切成输出时短暂误动作 */
HAL_GPIO_WritePin(GPIOA, GPIO_PIN_5, GPIO_PIN_RESET);

GPIO_InitTypeDef gpio = {0};
gpio.Pin   = GPIO_PIN_5;
gpio.Mode  = GPIO_MODE_OUTPUT_PP;
gpio.Pull  = GPIO_NOPULL;
gpio.Speed = GPIO_SPEED_FREQ_LOW;
HAL_GPIO_Init(GPIOA, &gpio);
```

寄存器开发的本质也相同：使能 RCC 时钟，修改 MODER/CRL/CRH、OTYPER、PUPDR、OSPEEDR、AFR 等寄存器，再通过 BSRR 等原子置位/复位寄存器控制输出。寄存器名称随系列变化。

> [!warning] 初始化常见错误
> 忘开端口时钟、选错 AF、开漏无外部上拉、输入悬空、速度设得过高、5 V 信号接到非 5 V-tolerant 引脚、按键中断未消抖，以及配置输出后才写安全电平造成上电毛刺。

# 六、常用的模块设计

## 1. BIOS 的设计

**短答：** 嵌入式项目里说的 BIOS 通常不是 PC 上的 BIOS，而是板级基础初始化层，职责接近 BSP 或 Board Init：把时钟、电源、引脚复用、基础外设、外部存储、调试口和板级资源先初始化到可用状态，再向上层驱动和应用提供稳定接口。

```text
Reset_Handler
  ↓
SystemInit：FPU、向量表、基础时钟
  ↓
搬 .data、清 .bss、初始化运行库
  ↓
BIOS/BSP_Init：板级硬件基础初始化
  ↓
Driver_Init：外设驱动初始化
  ↓
App_Init / RTOS task create
  ↓
启动调度器或进入主循环
```

### BIOS 层应该负责什么？

| 模块 | BIOS 层职责 | 不应该放什么 |
|---|---|---|
| 时钟与电源 | 配置系统时钟、外设时钟、PLL、低功耗域、复位原因读取 | 业务策略和应用状态机 |
| GPIO/PinMux | 统一配置引脚复用、上下拉、速度、默认安全电平 | 到处散落的临时引脚初始化 |
| 基础通信 | 初始化调试串口、日志口、必要的 I²C/SPI 片选和总线恢复 | 具体传感器协议解析 |
| 存储资源 | 初始化片内 Flash 参数区、QSPI、EXMC/LocalBus 等板级存储接口 | 文件格式、业务数据结构 |
| 中断与优先级 | 配置 NVIC 优先级分组、关键中断优先级、系统 tick 基础 | 在 ISR 中处理复杂业务 |
| 板级服务 | 提供 LED、按键、蜂鸣器、电源使能、硬件版本读取等基础 API | 上层 UI、通信协议、产品逻辑 |

### BIOS、驱动层、应用层怎么分？

| 层级 | 关注点 | 例子 |
|---|---|---|
| BIOS/BSP | 这块板子“有什么硬件、怎么上电可用” | `BSP_ClockInit()`、`BSP_PinMuxInit()`、`BSP_DebugUartInit()` |
| Driver | 某个外设或器件“怎么操作” | `spi_transfer()`、`flash_read()`、`lcd_write_cmd()` |
| Service/Middleware | 多个驱动组合成通用服务 | 参数存储、日志系统、通信协议栈、OTA |
| Application | 产品业务流程 | 采集任务、控制算法、菜单逻辑、联网状态机 |

分层的核心是依赖方向清楚：应用可以调用服务，服务可以调用驱动，驱动可以依赖 BIOS 提供的底层资源；BIOS 不应该反过来依赖具体业务。这样换板、换芯片或改外设引脚时，改动主要集中在 BIOS/BSP 层。

### BIOS 初始化顺序怎么设计？

1. **先安全态**：复位后尽快把电机使能、片选、功率开关等危险输出放到安全电平。
2. **再基础时钟**：配置系统时钟、Flash wait state、PLL、总线分频，确认 `SystemCoreClock` 正确。
3. **再引脚复用**：按原理图统一配置 GPIO、AF、上下拉、速度，避免外设初始化时引脚还处于错误状态。
4. **再基础外设**：初始化调试串口、系统 tick、DMA、必要的 I²C/SPI/UART 基础总线。
5. **再板级器件**：初始化电源管理、外部 Flash、EXMC/LocalBus、传感器复位脚等板上资源。
6. **最后交给应用**：BIOS 只报告初始化结果，不直接进入业务循环。

### 错误处理怎么做？

- 初始化函数要有返回值或错误码，不能全部默认成功。
- 关键外设失败时要记录错误来源，例如时钟失败、外部晶振失败、Flash ID 错、I²C 总线被拉低。
- 调试阶段可 `assert` 或停在错误码；量产固件应能降级、重试或进入安全模式。
- 启动日志尽量输出芯片型号、时钟、复位原因、固件版本、硬件版本和关键外设自检结果。

### 面试怎么说？

可以这样答：

> 我会把 BIOS/BSP 层当成板级硬件适配层来设计。它负责时钟、电源、PinMux、基础外设、外部存储和板级资源初始化，对上提供稳定 API；具体器件读写放在 Driver 层，参数存储、日志、OTA 放在 Service 层，产品流程放在 Application 层。这样硬件改版时主要改 BIOS，业务代码不需要到处改引脚和寄存器。

> [!warning] 常见坑
> BIOS 层最容易变成“什么都往里塞”的杂物层。判断标准很简单：如果这段代码和产品业务强相关，就不该放 BIOS；如果它描述的是板子上电后硬件如何进入可用状态，才适合放 BIOS/BSP。

## 2. PID 温控设计

**短答：** PID 温控是根据目标温度和当前温度的误差，计算加热或制冷输出。P 负责按当前误差快速响应，I 负责消除长期静差，D 负责根据变化趋势提前抑制过冲。温控对象通常惯性大、延迟明显，所以工程上还要做输出限幅、积分限幅、死区、滤波、采样周期固定和安全保护。

```text
目标温度 setpoint
  ↓
误差 e = setpoint - current_temperature
  ↓
PID：P + I + D
  ↓
输出限幅 / PWM 占空比 / SSR 周期控制
  ↓
加热器或制冷器
  ↓
温度传感器采样反馈
```

### 参数含义是什么？

| 参数 | 含义 | 调大后的效果 | 过大风险 |
|---|---|---|---|
| `Kp` | 比例系数，误差越大输出越大 | 响应更快，升温更有力 | 过冲、振荡、目标附近来回跳 |
| `Ki` | 积分系数，累积历史误差 | 消除稳态误差，例如一直差 1~2 ℃ 上不去 | 积分饱和，过冲变大，恢复慢 |
| `Kd` | 微分系数，根据误差变化率提前刹车 | 抑制快速变化，减小过冲 | 放大温度噪声，输出抖动 |
| `Ts` | PID 采样周期 | 固定周期后参数才有意义 | 周期不稳会导致控制效果漂移 |
| `out_min/out_max` | 输出上下限 | 限制 PWM、功率或阀门开度 | 不限幅可能损坏执行器或积分失控 |
| `integral_min/integral_max` | 积分限幅 | 防止积分项长期累积过大 | 不限幅会出现 windup，超调后很久拉不回来 |
| `deadband` | 目标附近死区 | 减少继电器/PWM 在目标附近频繁动作 | 死区过大会留下明显温差 |

常见位置式 PID：

```text
u(k) = Kp * e(k) + Ki * sum(e) * Ts + Kd * (e(k) - e(k-1)) / Ts
```

嵌入式里不要只背公式。实际代码要明确温度单位、输出单位、采样周期、输出限幅、积分是否限幅、传感器滤波和执行器类型。继电器或 SSR 常用时间比例控制；MOS 管、风扇、半导体制冷片常用 PWM 或电流控制。

### PID 温控怎么调参？

**短答：** 先关掉 I、D，只调 P 到响应够快但不过度振荡；再逐步加 I 消除静差；最后少量加 D 抑制过冲。每次只改一个参数，并记录曲线：上升时间、超调量、稳定时间、稳态误差和输出占空比。

1. **确认方向**：加热系统中温度低于目标时输出应增大；制冷系统相反。方向错了会越控越远。
2. **固定采样周期**：例如 100 ms、500 ms 或 1 s，温控系统通常不需要很高频。
3. **只开 P**：`Ki = 0`、`Kd = 0`，从小到大调 `Kp`，直到升温速度合适但目标附近没有持续大振荡。
4. **加 I**：逐步增加 `Ki`，让长期偏差收敛到 0；同时加积分限幅和输出饱和时的 anti-windup。
5. **少量加 D**：如果过冲明显，再加一点 `Kd`；温度采样噪声大时优先对测量值滤波，不要盲目加 D。
6. **分段验证**：低温启动、接近目标、保温、开盖/风冷扰动、负载变化、断电重启都要测。

> [!tip] 面试回答重点
> 调参不是凭感觉改三个数，而是看曲线。先看控制方向和采样周期，再看 P 的响应速度、I 的静差消除、D 的过冲抑制，最后用限幅、死区、滤波和安全保护把系统做稳。

### 目标温度附近跳变过大怎么办？

目标附近跳变大，通常不是单纯“PID 不好”，要同时检查测量、控制参数和执行器。

| 可能原因 | 现象 | 处理方法 |
|---|---|---|
| `Kp` 过大 | 刚到目标附近就来回冲，输出在高低之间大幅变化 | 降低 `Kp`，或使用接近目标时的分段 `Kp` |
| `Ki` 过大或积分饱和 | 超过目标后仍继续加热，过一会又反向修正 | 降低 `Ki`，加积分限幅、积分分离、输出饱和时暂停积分 |
| `Kd` 放大噪声 | 温度读数小抖动，输出大幅抖动 | 降低 `Kd`，对温度做滑动平均/一阶低通，D 项对测量值微分 |
| 采样噪声大 | 温度曲线毛刺多，实际温度未必跳 | 检查 ADC、传感器接线、滤波电容、参考电压、数字滤波 |
| 执行器粒度太粗 | 继电器/加热片一开就过量 | 降低最小输出功率，缩短 SSR 控制周期，改 PWM 或分级功率 |
| 热惯性和延迟大 | 关加热后温度还继续上冲 | 提前降功率，增加前馈或接近目标时限功率 |

常用工程处理：

- **死区控制**：例如目标 `60 ℃`，`59.8~60.2 ℃` 内保持输出不变或输出为低功率。
- **积分分离**：误差很大时不用 I，只在接近目标时启用积分，避免升温阶段积分堆太多。
- **输出斜率限制**：限制 PWM 占空比每秒变化量，避免功率突变。
- **分段 PID**：离目标远时用较大输出快速升温，接近目标时降低 `Kp/Ki`。
- **滤波但不拖太慢**：温度可以低通滤波，但滤波太重会增加延迟，反而更容易过冲。

### 温度一直上升，距目标温度越来越远，再收敛是什么原因？

这种现象要分两种看：如果目标是加热到某温度，温度在接近目标后继续上升、偏差越来越大，然后慢慢回落收敛，常见原因是 **热惯性、控制延迟或积分 windup**；如果温度一开始就朝反方向跑，优先怀疑 **控制方向错**。

| 场景 | 判断方法 | 常见原因 | 处理方法 |
|---|---|---|---|
| 接近目标后继续上冲，之后回落 | 输出已经降低或关断，但温度还在升 | 加热器余热、热传导延迟、传感器离热源远 | 接近目标提前限功率，加 D 或前馈，优化传感器位置 |
| 输出长时间打满，到目标后仍不收 | 查看 I 项是否很大 | 积分 windup，升温阶段误差累积过多 | 积分限幅、积分分离、输出饱和时停止积分 |
| 温度越控越远，输出方向也越来越大 | 加热时温度高于目标仍继续加热，或制冷方向相反 | 正负号写反、执行器方向配置错、传感器映射错 | 先做开环测试，确认输出增大到底会让温度升还是降 |
| 先远离再收敛但周期很长 | 输出变化滞后于温度变化 | 采样周期太长、滤波太重、D 项缺失 | 缩短采样周期，降低滤波滞后，增加预测/微分抑制 |

定位时建议先画四条曲线：目标温度、实际温度、PID 输出、P/I/D 三项。只看温度曲线容易误判；看到输出和积分项后，基本能区分是参数问题、方向问题、传感器问题还是热惯性问题。

### 面试怎么说？

可以这样答：

> 我做 PID 温控会先确认控制方向和采样周期，再从 P 开始调。P 决定响应速度，I 消除稳态误差，D 抑制快速变化和过冲。温控系统惯性大，所以必须做输出限幅、积分限幅和 anti-windup。目标附近跳变大时，我会先看温度曲线和输出曲线，通常从降低 Kp/Ki、加死区、积分分离、滤波和输出斜率限制入手。如果温度到目标后还继续上升再收敛，多半是热惯性或积分饱和，需要提前降功率和限制积分；如果温度一开始朝反方向跑，就先查控制方向和传感器映射。

> [!warning] 常见坑
> PID 参数不能脱离采样周期和输出单位讨论。同一组 `Kp/Ki/Kd`，采样周期变了，控制效果也会变；温控对象延迟大，盲目加大 `Kp` 或 `Ki` 往往只会让目标附近振荡更严重。

## 3. 状态机设计

**短答：** 状态机是把系统行为拆成有限个状态，系统根据当前状态和收到的事件决定执行什么动作、转移到哪个状态。它适合描述通信流程、设备启停、按键交互、升级流程和故障恢复，能替代大量相互嵌套的 `if/else` 和阻塞式流程。

状态机通常包含以下要素：

| 要素 | 含义 | 示例 |
|---|---|---|
| 状态 State | 系统当前所处阶段 | 空闲、启动、运行、故障 |
| 事件 Event | 触发判断的输入 | 启动命令、超时、数据到达、传感器异常 |
| 条件 Guard | 是否允许转移的附加条件 | 电压正常、温度未超限、权限校验通过 |
| 动作 Action | 转移时要执行的操作 | 开启电机、发送报文、保存参数 |
| 转移 Transition | 当前状态收到事件后的下一状态 | 空闲 + 启动命令 -> 启动 |

```text
Idle ──启动命令──→ Starting ──启动成功──→ Running
 ↑                    │                       │
 │                    │启动失败/超时          │停止命令
 │                    ↓                       ↓
 └──故障清除/复位── Fault             Stopping
                      ↑                       │
                      └────任意状态故障        └──停止完成──→ Idle
```

设计前先列状态转移表，比直接写代码更容易发现遗漏：

| 当前状态 | 事件 | 条件 | 动作 | 下一状态 |
|---|---|---|---|---|
| `IDLE` | `EV_START` | 自检正常 | 启动硬件，记录开始时间 | `STARTING` |
| `STARTING` | `EV_READY` | 无 | 允许正常输出 | `RUNNING` |
| `STARTING` | `EV_TIMEOUT` | 无 | 关闭输出，记录故障 | `FAULT` |
| `RUNNING` | `EV_STOP` | 无 | 发起停止 | `STOPPING` |
| 任意非故障状态 | `EV_FAULT` | 无 | 立即进入安全输出 | `FAULT` |
| `FAULT` | `EV_RESET` | 故障已消除 | 清故障，重新初始化 | `IDLE` |

### 状态机如何实现？

状态较少时，使用 `enum + switch` 最直观；状态和事件很多、规则需要配置时，可以使用二维表或转移表驱动。无论哪种方式，都应把状态变量、事件入口和硬件动作的边界定义清楚。

```c
typedef enum {
    STATE_IDLE,
    STATE_STARTING,
    STATE_RUNNING,
    STATE_STOPPING,
    STATE_FAULT,
} state_t;

typedef enum {
    EVENT_NONE,
    EVENT_START,
    EVENT_READY,
    EVENT_STOP,
    EVENT_TIMEOUT,
    EVENT_FAULT,
    EVENT_RESET,
} event_t;

typedef struct {
    state_t state;
    uint32_t state_enter_tick;
    uint32_t fault_code;
} machine_t;

static void machine_transition(machine_t *machine, state_t next, uint32_t now)
{
    /* 统一处理旧状态退出动作。 */
    if (machine->state == STATE_RUNNING) {
        output_disable();
    }

    machine->state = next;
    machine->state_enter_tick = now;

    /* 统一处理新状态进入动作。 */
    if (next == STATE_STARTING) {
        hardware_start();
    } else if (next == STATE_RUNNING) {
        output_enable();
    } else if (next == STATE_STOPPING) {
        hardware_stop();
    } else if (next == STATE_FAULT) {
        output_enter_safe_state();
    }
}

void machine_handle(machine_t *machine, event_t event, uint32_t now)
{
    if (event == EVENT_FAULT && machine->state != STATE_FAULT) {
        machine_transition(machine, STATE_FAULT, now);
        return;
    }

    switch (machine->state) {
    case STATE_IDLE:
        if (event == EVENT_START && self_test_ok()) {
            machine_transition(machine, STATE_STARTING, now);
        }
        break;

    case STATE_STARTING:
        if (event == EVENT_READY) {
            machine_transition(machine, STATE_RUNNING, now);
        } else if ((uint32_t)(now - machine->state_enter_tick) >= START_TIMEOUT_MS) {
            machine->fault_code = FAULT_START_TIMEOUT;
            machine_transition(machine, STATE_FAULT, now);
        }
        break;

    case STATE_RUNNING:
        if (event == EVENT_STOP) {
            machine_transition(machine, STATE_STOPPING, now);
        }
        break;

    case STATE_STOPPING:
        if (hardware_stopped()) {
            machine_transition(machine, STATE_IDLE, now);
        }
        break;

    case STATE_FAULT:
        if (event == EVENT_RESET && fault_is_cleared()) {
            machine->fault_code = 0;
            machine_transition(machine, STATE_IDLE, now);
        }
        break;

    default:
        machine->fault_code = FAULT_INVALID_STATE;
        machine_transition(machine, STATE_FAULT, now);
        break;
    }
}
```

这段代码不使用 `delay` 等待，而是每次被主循环或任务调用时向前推进一步。`(uint32_t)(now - start)` 的写法在无符号 tick 正常回绕时仍能计算经过时间，前提是超时时间小于计数器量程的一半。

### 状态机设计的注意事项

1. **状态和事件要正交。** “运行中”是状态，“收到停止命令”是事件；不要把瞬时事件定义成长时间状态。
2. **禁止在状态处理中阻塞等待。** 等待设备、通信响应或时间到期都应转成状态和事件，用 tick、定时器或 RTOS 超时推进。
3. **中断只产生事件。** ISR 读取必要数据后写入队列、环形缓冲或事件标志，由主循环或任务驱动状态机，避免在中断里直接切换复杂业务状态。
4. **不能只用一个布尔标志承接高频事件。** 多次事件会被合并，应使用计数器或队列；队列满时要定义丢弃、覆盖或进入故障的策略。
5. **进入、运行、退出动作要分清。** 一次性初始化放进入动作，周期处理放状态内部，资源释放放退出动作，避免每次调度重复初始化。
6. **所有等待状态必须有超时。** 通信无响应、传感器未就绪或执行器卡住时，要能进入重试、降级或故障状态。
7. **非法状态和非法转移必须可控。** `default` 应进入安全状态并记录原因，不能静默继续运行。
8. **多个上下文不能无保护地修改状态。** 最好让单一任务拥有状态机，其他任务和 ISR 只投递事件，避免竞态和不可重现的转移。
9. **状态过多时要拆分。** 可以使用分层状态机，把通信、设备控制和系统模式拆成独立子状态机，避免一个 `switch` 膨胀到无法维护。
10. **测试要覆盖转移而不只是状态。** 至少验证正常路径、每个超时、故障恢复、重复事件、乱序事件、队列满和 tick 回绕。

### 面试怎么说？

> 状态机是用状态、事件、条件、动作和转移来描述系统行为。我一般先画状态图和状态转移表，再用 `enum + switch` 或表驱动实现。嵌入式状态机的关键是非阻塞：等待时间和外设响应都变成事件或超时，中断只采集数据并投递事件，业务状态由一个主循环或任务统一修改。每个等待状态都要有超时，故障和非法状态要进入安全态；状态很多时再拆成分层或多个子状态机。

> [!warning] 常见坑
> 在某个状态里使用 `delay` 等待，导致整个系统无法响应；多个中断和任务直接修改同一个状态变量；只设置布尔事件导致高频事件丢失；没有超时和故障状态；进入动作每次轮询都重复执行；只画状态图却没有定义非法事件如何处理。

## 4. 升级与 OTA

**短答：** 固件升级是把设备中的旧程序替换为新程序；OTA（Over-The-Air）是通过 Wi-Fi、蜂窝网络、蓝牙等无线链路远程完成升级。串口、USB、CAN 或本地存储升级不属于 OTA，但底层的镜像校验、Flash 写入、启动切换和失败恢复理念基本相同。

升级系统的目标不只是“把新固件写进去”，而是保证整个过程：

| 核心理念 | 要解决的问题 |
|---|---|
| 完整性 | 镜像在下载、存储和写入过程中是否损坏 |
| 真实性 | 镜像是否确实由可信发布方签发，而不是被伪造 |
| 可恢复性 | 下载中断、掉电或写入失败后，设备还能否启动和重试 |
| 可回滚性 | 新版本启动失败或运行异常时，能否回到可用旧版本 |
| 兼容性 | 镜像是否适配当前硬件型号、分区布局和 Bootloader 版本 |
| 可追踪性 | 能否知道设备当前版本、升级阶段、失败原因和重试次数 |

Bootloader 应尽量小、稳定、少修改，负责选择和校验可启动镜像；App 负责联网、检查版本和下载镜像。不要让“下载完成”直接等于“升级成功”，新镜像至少还要经历完整校验、启动验证和业务确认。

### 典型升级流程

```text
服务器发布版本和签名信息
        ↓
设备检查硬件型号、版本策略和升级条件
        ↓
分块下载到暂存区或非活动分区，支持超时与断点续传
        ↓
校验长度、版本、Hash/CRC 和数字签名
        ↓
原子地写入“待升级/待试运行”标志并重启
        ↓
Bootloader 再次校验镜像，切换到新 App
        ↓
新 App 在限定时间内完成自检并确认版本
        ↓
确认成功：固化新版本；确认失败：回滚旧版本
```

常见存储方案：

| 方案 | 优点 | 风险与适用场景 |
|---|---|---|
| 单分区覆盖升级 | 占用 Flash 少 | 擦写中掉电容易变砖，必须有不可破坏的恢复 Bootloader 或外部恢复通道 |
| A/B 双分区 | 新旧镜像同时保留，切换和回滚可靠 | Flash 占用大，适合空间充足、可靠性要求高的产品 |
| 内部 App + 外部 Flash 暂存 | MCU 内部 Flash 压力较小，可先完整下载再搬运 | 需要额外存储器，搬运阶段仍要处理掉电恢复 |

镜像通常带有头部元数据，例如魔数、产品/硬件型号、固件版本、镜像长度、入口或加载地址、构建信息、Hash、签名和头部版本。Bootloader 必须先验证边界和兼容性，再根据长度计算校验，不能信任镜像头中的任意地址和长度。

### 升级与 OTA 的常见问题

| 常见问题 | 可能后果 | 处理思路 |
|---|---|---|
| 下载断线、丢包、乱序或重复包 | 镜像不完整，反复重下 | 分块编号、长度检查、超时重传、断点续传，完整镜像最终校验 |
| 擦写 Flash 时突然掉电 | App 或升级标志处于半写状态 | A/B 分区、暂存区、双份元数据；状态更新使用带版本号和 CRC 的原子提交 |
| 只做 CRC，不做签名 | 能发现误码，但无法阻止恶意伪造 | CRC/Hash 检查完整性，数字签名验证真实性；密钥和信任根要受保护 |
| 新 App 启动后立即确认成功 | 潜在故障版本无法自动回滚 | 设置试运行状态，完成时钟、外设、通信和关键业务自检后再确认 |
| 新 App 反复复位 | 设备陷入启动循环 | Bootloader 记录启动次数和确认超时，超过阈值自动回滚或进入恢复模式 |
| 版本或硬件不匹配 | 外设异常，严重时无法启动 | 校验产品 ID、硬件版本、分区布局、最低 Bootloader 版本和升级路径 |
| Bootloader 与新镜像格式不兼容 | Bootloader 无法解析或跳转 | 镜像头和升级协议带版本；Bootloader 保持向后兼容，必要时设计分阶段升级 |
| 链接地址、向量表或栈顶错误 | 跳转后 HardFault | App 按分区地址链接；跳转前设置 `VTOR`、加载 MSP、取复位向量并清理相关外设状态 |
| 参数结构随版本变化 | 新程序读取旧参数异常 | 参数带版本和 CRC，提供迁移与默认值策略；升级失败时避免破坏旧版本所需参数 |
| 看门狗、Cache、中断或 DMA 未处理 | 搬运超时、数据不一致或跳转异常 | 分块擦写并合理喂狗；按芯片处理 Cache；跳转前关闭或复位相关中断、DMA 和外设 |
| Flash 空间不足或分区越界 | 覆盖 Bootloader、参数区或其他镜像 | 下载前检查镜像长度，写入时逐块检查地址范围，并锁定 Bootloader 区域 |
| 允许任意降级 | 已修复的漏洞重新出现，数据格式不兼容 | 设计防回滚版本计数；维修降级使用受控授权，不能只比较版本字符串 |

升级状态本身也应设计成状态机，例如 `IDLE -> DOWNLOADING -> VERIFYING -> PENDING -> TESTING -> CONFIRMED`，任一阶段失败转入 `FAILED` 或恢复状态。状态要持久化时，应考虑 Flash 擦写寿命、掉电一致性和重复执行的幂等性。

### 面试怎么说？

> 我理解升级系统的重点不是把固件传过去，而是保证镜像可信、过程可恢复、失败可回滚。一般由 App 下载到暂存区或非活动分区，先检查型号、版本、长度、Hash 和签名，再写待升级标志并重启；Bootloader 重新校验后启动新镜像，新 App 通过自检后才确认成功，否则按超时或启动次数回滚。常见问题主要是断网、掉电、Flash 越界、镜像不兼容、参数迁移失败和新版本启动循环，所以要用 A/B 或安全暂存、原子状态记录、试运行确认和恢复入口来避免变砖。

> [!warning] 常见坑
> 把 CRC 当成安全认证；边下载边覆盖唯一可启动 App；升级标志只写一个字节且不考虑掉电；新版本一启动就确认；只校验版本号不校验硬件型号；Bootloader 信任镜像提供的长度和地址；没有保留串口、USB、按键或网络恢复入口。

## 5. CRC 与 Hash 校验

**短答：** CRC 和 Hash 都能把一段任意长度的数据映射成固定长度的校验值，用于判断数据是否发生变化。CRC 主要针对通信和存储中的随机误码，计算快、硬件实现简单；密码学 Hash 更强调单向性、抗碰撞和雪崩效应，适合大文件指纹、固件完整性和安全协议，但单独使用仍不能证明数据来自谁。

常见校验方式可以先这样区分：

| 方法 | 基本思路 | 主要用途 |
|---|---|---|
| 奇偶校验 | 统计 1 的个数是奇数还是偶数 | 低成本发现部分单比特错误 |
| 累加和/Checksum | 对所有字节求和后截断或取反 | 简单协议、资源极少或兼容旧格式 |
| CRC | 对比特串做 GF(2) 多项式除法，取余数 | 通信帧、Flash 数据块和存储传输误码检测 |
| Hash | 通过多轮非线性压缩得到固定长度摘要 | 文件指纹、固件完整性、签名和 HMAC 的基础 |

### CRC 的基本原理

CRC（Cyclic Redundancy Check，循环冗余校验）把数据比特串看成二进制多项式，使用双方约定的生成多项式做模 2 除法，最后的余数就是 CRC。模 2 运算只有异或，没有进位和借位。

以宽度为 `r` 的 CRC 为例：

1. 发送方在原始数据末尾补 `r` 个 0。
2. 用生成多项式对补零后的数据做模 2 除法。
3. 取 `r` 位余数作为 CRC，随数据一起发送或保存。
4. 接收方使用完全相同的 CRC 模型重新计算，与收到的 CRC 比较；不一致说明数据发生了变化。

```text
原始数据 ──补零/逐位异或除法──→ CRC 余数
   │                                │
   └──────── 数据 + CRC ────────────┘
                    ↓
          接收端按同一模型重新计算
                    ↓
             相等：通过；否则：错误
```

CRC 不是只看“CRC-16”或“CRC-32”就能确定算法，双方必须统一全部参数：

| 参数 | 含义 |
|---|---|
| `width` | CRC 结果宽度，例如 16 位或 32 位 |
| `poly` | 生成多项式 |
| `init` | CRC 寄存器初始值 |
| `refin/refout` | 输入字节和输出结果是否按位反射 |
| `xorout` | 最终结果异或值 |
| 字节顺序 | 多字节 CRC 在线路或文件中的高低字节排列 |

CRC 对突发错误特别有效。设计合适的 `r` 阶生成多项式通常能发现长度不超过 `r` 位的全部突发错误，也能以很高概率发现更长的随机错误。但 CRC 位数有限，碰撞一定存在，而且攻击者可以修改数据后重新计算 CRC，因此它不是安全算法。

### Hash 的基本原理

Hash 将任意长度输入映射成固定长度摘要。密码学 Hash 通常先对输入填充并分块，再让每个数据块经过多轮非线性混合和压缩，前一块的内部状态参与后一块计算，最终输出摘要。例如 SHA-256 无论输入多长，都输出 256 bit，也就是 32 byte。

理想的密码学 Hash 具有以下特性：

- **确定性**：相同输入一定得到相同摘要。
- **单向性**：已知摘要，很难反推出原文。
- **抗第二原像**：给定一份数据，很难找到另一份具有相同摘要的数据。
- **抗碰撞**：很难主动找到两份摘要相同的不同数据。
- **雪崩效应**：输入只改变 1 bit，输出也会发生大范围、不可预测的变化。

Hash 不是加密：它没有“解密还原原文”的过程。Hash 也不是绝对不会碰撞，而是使用足够长且仍安全的算法后，在工程上很难找到可利用的碰撞。安全场景应优先使用 SHA-256、SHA-384 等当前适用的密码学 Hash，不应继续把 MD5、SHA-1 用于抗攻击的完整性判断。

### CRC 与 Hash 的区别

| 对比项 | CRC | 密码学 Hash |
|---|---|---|
| 主要目标 | 检测随机误码 | 生成难以伪造和碰撞的内容摘要 |
| 数学结构 | GF(2) 线性多项式运算 | 多轮非线性混合与压缩 |
| 常见长度 | 8、16、32、64 bit | 256、384、512 bit |
| 计算开销 | 很低，MCU 常带 CRC 硬件单元 | 较高，可用软件或密码硬件加速 |
| 随机错误检测 | 很适合，尤其是突发错误 | 能检测，但成本通常更高 |
| 抗恶意修改 | 不具备，修改后可轻易重算 | 摘要本身较难构造碰撞，但无密钥时仍可被整体替换 |
| 典型场景 | 通信帧、配置块、Flash 页、传感器数据 | 固件镜像、文件指纹、数字签名、HMAC |

选择原则：

- UART、RS-485、CAN 上的自定义短帧，需要快速发现链路误码：常用 CRC-16 或 CRC-32。
- Flash 参数、升级状态等小数据块，需要发现掉电或存储损坏：使用版本号、长度和 CRC，并配合双备份或原子提交。
- 大型固件下载，需要确认整份文件与服务器发布内容一致：使用 SHA-256 等 Hash；分块 CRC 可用于快速定位和重传坏块。
- 需要确认通信双方共享同一密钥且消息未被篡改：使用 HMAC，不是简单的 `Hash(key + data)`。
- 需要让设备验证固件确实由发布方签发：对固件 Hash 做数字签名，设备用内置公钥验签。

### CRC 或 Hash 能保证数据可信吗？

**不能单独保证。** CRC 只能有效发现随机错误；普通 Hash 虽然抗碰撞能力强，但没有秘密信息。攻击者如果能同时替换固件和旁边保存的 Hash，就可以给恶意固件重新计算一个正确 Hash。

```text
CRC / Hash                  → 数据有没有变化？
HMAC（双方共享密钥）         → 数据是否来自持有同一密钥的一方？
数字签名（私钥签名、公钥验证） → 数据是否来自可信发布方，且是否被修改？
```

OTA 中常见的组合是：传输分块用 CRC 快速发现误码，完整镜像用 SHA-256 生成摘要，再验证摘要的数字签名。这样同时覆盖传输可靠性、整体完整性和发布者真实性。

### 使用时的常见问题

1. **算法同名但参数不同。** 两端都说 CRC-16，`poly/init/refin/xorout` 不同仍会得到不同结果，必须给出完整 CRC 模型和测试向量。
2. **校验范围不一致。** 要明确是否包含包头、长度、填充字节和 CRC 字段本身，以及从哪个地址算到哪个地址。
3. **字节序或位反射不一致。** 线上的 CRC 高低字节顺序与 CPU 大小端不是一回事，必须按协议显式编码。
4. **硬件 CRC 与软件结果不同。** 检查硬件输入宽度、字节重排、初值、补零规则和最后异或，不能只比较多项式。
5. **只校验分块，不校验整体镜像。** 块顺序错误、重复块或元数据被替换仍可能漏检，最后必须对完整镜像和关键元数据统一校验。
6. **校验通过后数据又被修改。** 验证完成到实际使用之间仍要保护存储区域，安全启动时应在启动链中重新验证。
7. **把 CRC、Hash 和加密混为一谈。** 校验不提供保密性，Hash 不能解密，CRC/Hash 单独也不能认证来源。

### 面试怎么说？

> CRC 是把数据看成二进制多项式，用约定的生成多项式做模 2 除法并取余数，特点是速度快、擅长检测通信和存储中的随机及突发错误，但它是线性的，不能防恶意篡改。密码学 Hash 通过多轮非线性压缩，把任意长度数据变成固定长度摘要，具有单向、抗碰撞和雪崩特性，适合固件和文件的整体完整性校验。实际 OTA 中我会用分块 CRC 做快速重传，用 SHA-256 校验完整镜像，再用数字签名确认发布者身份；只有 CRC 或普通 Hash 都不能证明固件可信。

> [!warning] 常见坑
> 只说 CRC-16 却不说明完整参数；校验范围和字节序不一致；认为 CRC 位数更长就具备安全性；认为 Hash 完全不会碰撞；把 Hash 当成加密；固件和 Hash 放在一起却没有签名或 HMAC；只校验分块而不校验完整镜像。

# 七、RTOS 与 FreeRTOS

## FreeRTOS 迁移实践大纲

完整项目记录：[FreeRTOS 迁移配置笔记](E:/Coding/stm32/stm32/spi_jetson_stm32_freertos/spi_jetson_stm32/docs/FREERTOS_MIGRATION_NOTES.md)。该文档记录 STM32F407 I²C 从机从裸机迁移到 FreeRTOS 的配置、阶段验收、硬件回归和代码上下库流程。

| 阶段 | 核心内容 | 本项目关键点 |
|---|---|---|
| 1. 固定迁移边界 | 先保持协议、接线和业务行为不变 | 保持 I2C1、PB6/PB7、地址 `0x42`、BUSY 和帧格式不变 |
| 2. 确认裸机基线 | 记录 MCU、编译器、时钟、中断和已通过功能 | STM32F407ZG、Cortex-M4F、168 MHz、Keil AC6 |
| 3. 选择 RTOS 端口 | 端口必须匹配内核、FPU 和编译器 | AC6 使用已验证的 `GCC/ARM_CM4F` 风格端口，不能直接使用 AC5 RVDS 汇编 |
| 4. 建立最小配置 | 先配置 Tick、优先级、堆、栈和断言 | 1 kHz Tick、4 个任务优先级、16 KB heap、启用 `configASSERT` |
| 5. 接管异常入口 | FreeRTOS 接管 SVC、PendSV、SysTick | SVC/PendSV 必须直接映射端口处理函数；SysTick 同时维护 HAL 与 RTOS 1 ms 时基 |
| 6. 设计中断优先级 | 区分 NVIC 优先级和任务优先级 | NVIC 数值越小越高；调用 `FromISR` 的 IRQ 必须处于库优先级 5～15，本项目 I2C 使用 6 |
| 7. 选择 ISR 同步方式 | ISR 只收发和通知，任务处理业务 | I2C ISR 发布单帧 buffer 后使用直接任务通知唤醒服务任务 |
| 8. 分阶段迁移业务 | 一次只改变一个执行模型 | 内核编译 → 最小调度器 → I2C 轮询任务化 → ISR 通知 → 传感器/诊断任务化 |
| 9. 做资源与功能验收 | 每阶段检查构建、栈、堆、时基和原协议 | 观察栈高水位、最小剩余堆、断言、HardFault、I2C BUSY/CRC/最大帧 |
| 10. 建立上下库闭环 | 推送提交后从远端干净构建并烧录回归 | 提交号、AXF、构建尺寸、探针、测试响应必须能够对应 |

迁移时最重要的原则是：**先让 RTOS 承载原来的单执行流，再改变 ISR 与任务的同步方式，最后拆分业务。** 不要同时重构协议、驱动、中断和任务，否则回归失败时很难判断是哪一层引入问题。

```text
裸机基线
   ↓
内核能编译但暂不调度
   ↓
最小心跳任务验证调度器、Tick、栈和堆
   ↓
原 i2c_slave_poll() 整体迁入服务任务
   ↓
I2C ISR 用 FromISR 通知阻塞任务
   ↓
传感器、诊断等耗时业务逐步任务化
   ↓
远端干净构建、下载、硬件回归和长稳测试
```

## 1. 为什么用 RTOS？任务状态有哪些？

RTOS 用优先级任务和同步通信机制提高模块化与实时响应，代价是 RAM、切换开销和并发复杂度。简单顺序控制未必需要 RTOS。

任务状态：Running、Ready、Blocked、Suspended。单核同一时刻只有一个 Running；抢占式调度下，高优先级任务就绪后通常会抢占低优先级任务。

## 2. 上下文切换

常见 Cortex-M FreeRTOS 端口中：SysTick 提供节拍；PendSV 以最低异常优先级做切换；硬件保存基础异常栈帧，软件再把 R4~R11 等存入当前任务栈；调度器选择新任务并切换 PSP，恢复后异常返回。SVC 常用于启动第一个任务。

## 3. MSP 与 PSP

**短答：** MSP 是复位默认栈，Handler mode 始终用 MSP；PSP 只能用于 Thread mode。FreeRTOS 通常让任务各用自己的 PSP 栈，中断统一用 MSP，实现任务栈与中断栈分离。

裸机 `main()` 通常一直用 MSP。异常前线程现场压在哪个栈由当时的 SP 选择决定，可从 `EXC_RETURN` 判断。

## 4. 同步工具怎么选？

| 工具 | 用途 | 特点 |
|---|---|---|
| Queue | 传递数据 | 复制消息，可阻塞 |
| Binary Semaphore | 事件同步 | ISR 通知任务常用，无所有权 |
| Counting Semaphore | 资源/事件计数 | 可累计 |
| Mutex | 保护共享资源 | 有所有者和优先级继承，ISR 不可用 |
| Event Group | 多 bit 条件 | 等待多个事件组合 |
| Task Notification | 一对一通知 | 快、省 RAM，可传 bit/计数/值 |

大块数据可传指针，但必须明确缓冲区生命周期和所有权。

## 5. 优先级反转

低优先级任务持锁，高优先级任务等待该锁，而中优先级任务持续抢占低优先级任务，导致高优先级间接被阻塞。使用带优先级继承的 mutex、缩短临界区、禁止持锁做慢操作，必要时让专用任务独占资源。

## 6. ISR 为什么用 `FromISR` API？

ISR 不能像任务一样阻塞。`FromISR` 版本不会阻塞，并可返回是否唤醒更高优先级任务，再在退出 ISR 前请求切换。ISR 应只清标志、搬必要数据、通知任务；不应延时、大量打印、动态分配或做耗时算法。调用 API 的 ISR 还必须满足 FreeRTOS 中断优先级限制。

## 7. 如何排查任务栈？

- 开启 `configCHECK_FOR_STACK_OVERFLOW`。
- 用 `uxTaskGetStackHighWaterMark()` 看历史最小余量。
- 考虑最深调用、局部变量、库函数和 FPU；避免栈上大数组、递归和重格式化输出。
- 栈水位正常不代表不存在野指针等内存破坏。

## 7.1 FreeRTOS 任务的最大执行时间和栈空间怎么选？超了会怎样？

### 最大执行时间怎么定？

FreeRTOS 没有一个参数可以直接“设置任务最大执行时间”。它通常由任务的**周期、截止时间、优先级、系统响应要求和看门狗策略**共同确定。需要评估的是最坏执行时间（WCET），而不是平均执行时间。

例如一个 10 ms 周期、要求每次在下一个周期前完成的任务，应满足：

```text
最坏执行时间 + 可能的阻塞时间 + 抢占/中断开销 < 10 ms
```

选择方法：

1. 先明确任务周期或事件到来后的最大响应时间。
2. 在最坏输入、最长循环、缓存未命中、日志开启等条件下测量执行时间。
3. 把等待队列、互斥锁、SPI/I²C 通信和可能的抢占时间也算进去。
4. 让高优先级实时任务先满足截止时间，再检查所有任务的 CPU 利用率和调度余量。
5. 对事件任务设置“开始处理后最长允许持续时间”，而不是要求它必须周期性运行；没有事件时阻塞等待是正常状态。

任务执行时间超过预期时，FreeRTOS 不会自动把它“截断”。如果任务一直运行且不阻塞、没有被更高优先级任务抢占，可能导致低优先级任务得不到运行；如果同优先级任务依赖时间片，也会出现响应延迟。若超过通信协议、控制环或看门狗的允许时间，系统应记录超时、取消操作、上报错误，必要时停止喂狗让硬件复位。

### 栈空间怎么定？

任务栈大小应按**最深调用链 + 最大局部变量 + RTOS/库函数开销 + 中断或异常使用情况 + 安全余量**估算。`xTaskCreate()` 中的栈大小通常以 `StackType_t` 为单位，很多 Cortex-M 工程里一个栈单元是 4 字节，不能直接把参数当成字节数，必须看端口定义。

推荐流程：

1. 先按调用深度、局部数组、`printf`/格式化函数、协议解析和 FPU 使用情况给出初始值。
2. 开启 `configCHECK_FOR_STACK_OVERFLOW`，注册 `vApplicationStackOverflowHook()`。
3. 运行覆盖正常和最坏场景，用 `uxTaskGetStackHighWaterMark()` 查看历史最小剩余栈。
4. 保留项目规定的余量，不要把高水位刚好压到 0；任务升级后重新测量。
5. 大数组、帧缓冲和大对象尽量放到专用静态缓冲区或堆中，并明确生命周期，避免直接放在任务栈上。

栈空间不足时，轻则触发 FreeRTOS 的栈溢出检测，重则覆盖相邻内存、TCB 或返回地址，表现为变量被破坏、任务异常退出、随机 HardFault、调度器崩溃或系统跑飞。栈分配过大则会浪费有限的 RAM，任务过多时甚至导致创建失败或堆耗尽。

> [!tip] 面试短答
> 任务最大执行时间按最坏执行时间和截止时间设计，不是简单设置一个超时参数；超时会拖延其他任务，严重时触发业务超时或看门狗复位。任务栈按最深调用链和最大栈上对象估算，再用 `uxTaskGetStackHighWaterMark()` 实测并留余量；栈溢出可能导致内存破坏、HardFault 和系统崩溃。

## 8. SPI 命令如何用 IRQ 打断并调度快速命令？

**场景：** 系统原有普通命令任务和光功率上报任务。一次命令由完整的 SPI 写事务、命令处理和完整的 SPI 读事务组成。`DONE` 在 `CS` 拉低时同步拉低；写事务结束后，如果命令还在处理，虽然 `CS` 已拉高，`DONE` 仍保持低，主机不能发送新数据。响应准备完成后 `DONE` 拉高，主机才能开始读事务；读事务中 `CS` 和 `DONE` 再次拉低。

原有正常时序：

```text
空闲：CS=高，DONE=高
  → 主机写：CS=低，DONE=低
  → 完整写帧结束：CS=高，DONE继续为低
  → 普通命令任务处理
  → 响应准备完成：DONE=高
  → 主机读：CS=低，DONE=低
  → 完整读帧结束：CS=高，DONE=高
```

新增 `IRQ` 是主机发给从机的异步打断请求，本身不携带快速命令。IRQ 到来后，从机先终止当前写命令，准备 `status=err` 的读帧并拉高 `DONE`；主机完整读走错误帧后，再通过下一次完整写事务发送快速命令。

两种打断路径：

```text
1. IRQ发生在CS低、SPI正在收写帧
   IRQ ISR设置取消标志并通知协议任务
   → SPI ISR/DMA停止写当前接收缓冲区
   → 主机尽快拉高CS，终止本次不完整事务
   → 从机丢弃不完整帧，DONE保持低
   → 准备err读帧，完成后DONE拉高

2. IRQ发生在CS高、普通命令正在处理
   IRQ ISR设置取消标志并通知协议任务
   → 普通命令任务在取消点停止执行并清理资源
   → 协议任务准备err读帧
   → 响应可读后DONE拉高
```

推荐优先级：

```text
SPI/IRQ中断
    > SPI协议任务
    > 快速命令任务
    > 普通命令任务
    > 光功率上报任务
```

SPI 协议任务负责收发状态、`DONE` 和响应帧，应高于业务任务。快速命令完整写入后，协议任务将它投递给快速命令任务；快速命令任务应严格高于普通命令任务，才能在变为 Ready 后立即抢占。

为什么本方案需要提高快速命令任务的优先级：

`IRQ` 的目标是让快速命令尽快执行。快速命令完整写入后，正在执行的普通命令任务虽然被暂停，但仍处于 Ready 状态，因此普通任务和快速任务会同时竞争 CPU：

```text
普通命令任务：Ready，保留当前执行现场
快速命令任务：Ready，快速命令已经接收完成
```

FreeRTOS 总是调度最高优先级的 Ready 任务。快速任务只有严格高于普通任务，才能在接收完成后立即抢占 CPU，使“快速”具有确定的调度含义；同优先级只能依赖时间片、Tick 或普通任务主动阻塞，无法给出稳定的最坏响应时间。

只有在快速命令到达前，普通任务已经自然完成或进入 Blocked 状态，两者不会竞争 CPU 时，快速任务才可以不提高优先级。当前需求就是在普通命令执行过程中抢占，因此快速任务需要严格更高的优先级。

正在执行的普通命令采用“暂停后恢复”策略，不主动删除、挂起或取消：

```text
普通命令任务正在运行
    → 快速任务变为Ready
    → FreeRTOS保存普通任务的PC、寄存器和栈指针
    → 普通任务从Running变为Ready
    → 快速任务运行
    → 快速任务完成后重新进入Blocked
    → FreeRTOS恢复普通任务现场
    → 普通命令从被抢占的指令位置继续执行
```

这种策略不需要取消标志和取消检查点。快速任务必须是预先创建的永久任务，执行完一条快速命令后重新阻塞，不能从任务入口函数直接返回。

暂停后恢复只适用于快速命令与普通命令互不冲突的情况：快速命令不能复位普通命令正在使用的外设、修改它依赖的配置或业务状态，也不能导致普通命令恢复后覆盖快速命令的效果。任务暂停只会停止 CPU 代码，普通命令已经启动的 DMA、定时器和外设仍会继续运行。如果存在这些冲突，就不能恢复旧命令，必须改用取消检查点或重新执行普通命令。

如果快速命令没有更高优先级：

- 与普通命令同优先级且开启时间片时，只能等待 Tick 并与普通任务轮转，延迟不可控。
- 关闭时间片时，普通任务若不阻塞或不主动让出，快速任务可能长期得不到执行。
- 快速任务优先级更低时，只要普通任务持续处于 Ready 状态，快速任务就无法运行。
- 从 ISR 唤醒任务时，通常只有被唤醒任务优先级严格高于当前任务，才能通过 `portYIELD_FROM_ISR()` 立即切换。
- 主机会看到 `DONE` 长时间为低，可能触发通信超时，快速命令也就失去实时意义。

更高任务优先级只保证抢占 CPU，不能抢走普通任务占用的 mutex、DMA 和外设。如果快速命令需要相同资源，它仍会被阻塞，必须通过资源隔离、缩短普通任务持锁时间或重新设计硬件所有权解决。只有决定彻底取消普通命令时，才需要协作取消点、资源释放和硬件 abort 规则；不可使用 `vTaskDelete()` 或 `vTaskSuspend()` 强杀正在持锁或操作硬件的任务。

# 八、问题定位与 HardFault

## 1. 通用定位方法

**短答：** 先稳定复现、缩小范围，再用日志、寄存器和波形建立证据链，不随机改代码。

1. 写清预期、实际、概率、版本和复现步骤。
2. 区分硬件/软件、单板/批量、温度/电压/负载、启动/运行时。
3. 保留复位原因、错误码、PC/LR/SP、Fault 寄存器和最近日志。
4. 分层查：电源/复位/时钟 → 引脚波形 → 驱动寄存器 → 协议 → RTOS/业务。
5. 二分代码/配置，换板、降频、关闭 DMA 做 A/B 对照。
6. 修复能消失、恢复错误条件能重现，才算验证根因。
7. 增加断言、超时、错误恢复、监控和回归测试。

工具选择：示波器看电压/毛刺/模拟质量；逻辑分析仪看数字协议；调试器看寄存器/调用栈；map、反汇编和 Addr2line 把地址还原到源码。

## 2. HardFault 是什么？常见原因？

HardFault 是固定高优先级故障，可能是自身原因，也可能是未使能/无法处理的 MemManage、BusFault、UsageFault 升级而来。

常见原因：空/野指针、越界、栈溢出、返回地址或函数指针损坏、非法指令/状态、非对齐访问、访问不存在/无权限地址、异常返回栈帧损坏。

## 3. HardFault 定位步骤

HardFault 可能是自身故障，也可能是 MemManage、BusFault、UsageFault 未使能或无法处理后升级而来。定位时按“异常栈帧 → Fault 原因 → 故障地址 → 系统上下文”逐层分析。

### 第一步：保存异常栈帧

异常进入时，Cortex-M4 硬件自动将以下基础现场压入异常前使用的栈：

```c
typedef struct {
    uint32_t r0, r1, r2, r3, r12, lr, pc, xpsr;
} fault_stack_t;
```

| 栈帧字段 | 定位作用 |
|---|---|
| `R0~R3` | 参数和临时值，可判断故障函数收到的指针、长度等 |
| `R12` | 临时寄存器，结合反汇编分析 |
| stacked `LR` | 异常前函数原本准备返回的位置 |
| stacked `PC` | 最关键，异常发生时正在执行的位置 |
| stacked `xPSR` | Thumb 状态、条件标志、异常号和栈对齐信息 |

HardFault Handler 当前的 `LR` 通常是特殊值 `EXC_RETURN`，不是异常前代码的普通返回地址。根据其 bit 2 选择正确栈指针：bit 2 为 0 表示 MSP，为 1 表示 PSP；bit 4 为 1 表示基础栈帧，为 0 表示带浮点扩展现场。

```asm
tst   lr, #4
ite   eq
mrseq r0, msp
mrsne r0, psp
b     hardfault_analyze
```

`R4~R11` 不由异常硬件自动压入基础栈帧，需要完整现场时应在汇编入口尚未破坏它们之前另行保存。M4F 还可能启用浮点扩展栈帧和延迟压栈，不能始终假定所有字段具有固定偏移。若出现 `STKERR/UNSTKERR`，栈帧本身可能已经不可信。

### 第二步：读取 Fault 状态寄存器

应在清标志或复位前保存：

```c
SCB->HFSR;   // HardFault 总体原因
SCB->CFSR;   // MemManage + BusFault + UsageFault 详细原因
SCB->MMFAR;  // 仅 MMARVALID=1 时有效
SCB->BFAR;   // 仅 BFARVALID=1 时有效
SCB->SHCSR;
SCB->DFSR;
SCB->AFSR;
```

| 寄存器/标志 | 重点含义 |
|---|---|
| `HFSR.FORCED` | 其他可配置 Fault 升级为 HardFault，应继续解码 `CFSR` |
| `HFSR.VECTTBL` | 读取异常向量表失败，检查 `VTOR` 和向量表存储区域 |
| `HFSR.DEBUGEVT` | 调试事件导致故障，继续查看 `DFSR` |
| `SHCSR` | 三类可配置 Fault 的使能、Pending 和 Active 状态 |
| `DFSR` | 断点、DWT、Vector Catch 等调试事件 |
| `AFSR` | 实现相关的辅助故障信息，含义查具体 MCU 手册 |

`CFSR` 由三个状态区组成：

```text
CFSR[7:0]   = MMFSR：MemManage Fault
CFSR[15:8]  = BFSR：BusFault
CFSR[31:16] = UFSR：UsageFault
```

#### MemManage 常见标志

| 标志 | 含义 |
|---|---|
| `IACCVIOL` | 从禁止执行或无权限区域取指 |
| `DACCVIOL` | 访问受保护或无权限的数据地址 |
| `MSTKERR/MUNSTKERR` | 异常进入压栈/返回出栈时发生内存管理错误 |
| `MLSPERR` | 浮点延迟压栈时发生内存管理错误 |
| `MMARVALID` | `MMFAR` 保存了有效错误地址 |

#### BusFault 常见标志

| 标志 | 含义 |
|---|---|
| `IBUSERR` | 取指时发生总线错误 |
| `PRECISERR` | 精确数据访问错误，stacked PC 通常接近出错指令 |
| `IMPRECISERR` | 缓冲写等非精确错误，stacked PC 可能不是根因位置 |
| `STKERR/UNSTKERR` | 异常压栈/出栈时发生总线错误 |
| `LSPERR` | 浮点延迟现场保存时发生总线错误 |
| `BFARVALID` | `BFAR` 保存了有效错误地址 |

#### UsageFault 常见标志

| 标志 | 常见原因 |
|---|---|
| `UNDEFINSTR` | 跳入数据区、函数指针损坏或执行非法指令 |
| `INVSTATE` | Thumb 状态、函数地址最低位或返回地址错误 |
| `INVPC` | 非法异常返回，常见于栈帧或 `EXC_RETURN` 损坏 |
| `NOCP` | 使用了未启用的 FPU 或协处理器 |
| `UNALIGNED` | 非对齐访问触发陷阱 |
| `DIVBYZERO` | 除零触发陷阱 |

`UNALIGNED`、`DIVBYZERO` 是否主动产生 Fault 还取决于 `SCB->CCR` 的 `UNALIGN_TRP`、`DIV_0_TRP`。`CFSR` 状态位通常写 1 清除，因此必须先完整保存现场。

### 第三步：检查运行上下文

| 寄存器 | 作用 |
|---|---|
| `MSP/PSP` | 检查栈地址是否合法、是否越过栈边界 |
| `CONTROL` | 判断 Thread mode 的栈选择和特权状态 |
| `PRIMASK/BASEPRI/FAULTMASK` | 判断中断或 Fault 是否被错误屏蔽 |
| `ICSR` | 查看当前活动异常 `VECTACTIVE` 和 Pending 状态 |
| `NVIC->IABR/ISPR` | 查看哪些外部中断正在执行或等待处理 |
| `VTOR` | 检查向量表基址、对齐和存储区域 |
| 芯片 RCC 复位标志 | 区分上电、软件、看门狗、欠压等复位来源 |

裸机通常一直使用 MSP；FreeRTOS 任务通常使用 PSP，而所有异常 Handler 使用 MSP。因此 RTOS 中任务触发 Fault 时，不能默认从 MSP 提取异常前任务现场，还要检查当前任务、任务栈边界、水位和保护字。

### 实际排查顺序

1. 立即保存 Handler 的 `LR/EXC_RETURN`、MSP、PSP 和 Fault 寄存器，避免现场继续被覆盖。
2. 根据 `EXC_RETURN` 选择正确栈，取得 stacked `PC/LR/xPSR/R0~R3/R12`。
3. 先看 `HFSR`；若 `FORCED=1`，继续逐位解码 `CFSR`。
4. 只有 `MMARVALID/BFARVALID` 为 1 时，才相信 `MMFAR/BFAR` 中的地址。
5. 检查 SP 是否越界；若有 `STKERR/UNSTKERR`，栈帧内容可能已损坏。
6. `PRECISERR`、MemManage 和 UsageFault 通常从 stacked PC 附近查；`IMPRECISERR` 要向前追查最近的内存、外设或 DMA 写操作。
7. 查看 `SHCSR/ICSR/NVIC` 和中断屏蔽寄存器，确认故障发生时的异常状态。
8. 结合外设错误寄存器、DMA 状态、复位原因和最近日志建立证据链。
9. 使用带符号 ELF 将 PC/LR 地址映射到源码和反汇编。

用带符号 ELF 定位：

```bash
arm-none-eabi-addr2line -e firmware.elf -f -C 0x08001234
arm-none-eabi-objdump -d -S firmware.elf
```

> [!tip] 面试短答
> HardFault 先用 EXC_RETURN 判断异常前使用 MSP 还是 PSP，从栈中取出 PC、LR 和 xPSR；再看 HFSR 判断是否由其他 Fault 升级，用 CFSR 区分 MemManage、BusFault、UsageFault。只有有效位成立时才能使用 MMFAR/BFAR。最后结合栈边界、SHCSR、ICSR、NVIC、复位标志以及 ELF 反汇编定位根因。

## 4. 通信故障快速检查表

### I²C

空闲是否双高；上拉和上升时间；API 要 7 位还是已移位地址；NACK 在地址还是数据阶段；Repeated START/最后 NACK/STOP；是否有从机持续拉低总线。

### SPI

CPOL/CPHA、位序、位宽；CS 极性与建立/保持时间；实际 SCK；MOSI/MISO；多从机 MISO 冲突；对照数据手册和逻辑分析仪。

### UART

波特率/帧格式；TX/RX 交叉、共地和电平；实际时钟误差；ORE/FE/NE/PE；DMA/环形缓冲溢出；协议长度、CRC、超时和拆包状态机。
