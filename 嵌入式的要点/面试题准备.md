# 一、MCU 与启动流程

## 1. MCU、Cortex-M4、STM32 分别是什么？

**短答：** MCU 是把 CPU、存储器和外设集成在一颗芯片上的微控制器；Cortex-M4 是 Arm 设计的处理器内核；STM32 是 ST 公司基于 Cortex-M 等内核推出的一系列 MCU。

- Cortex-M4 规定指令集、核心寄存器、异常模型、NVIC、SysTick 等。
- STM32 在内核外围集成 Flash、SRAM、时钟树、GPIO、Timer、ADC、UART、SPI、I²C 等。
- 同样使用 Cortex-M4 的芯片可以来自不同厂商，内核机制相近，但外设寄存器不同。
- MCU 强调实时控制、低功耗和片上集成；MPU 通常算力更高，配外部 DDR/MMU 运行 Linux 等复杂系统。边界并非绝对。

## 2. MCU 上电启动流程

**短答：** 上电复位后，芯片锁存启动配置并映射启动存储器；CPU 从向量表第 0 项取 MSP 初值、第 1 项取 `Reset_Handler` 地址，随后完成 `.data` 搬运、`.bss` 清零、时钟和运行库初始化，最后进入 `main()`。

```text
上电/复位
  ↓
电源稳定、加载 Option Bytes、锁存 BOOT 配置
  ↓
选择用户 Flash / System Memory / SRAM（具体型号为准）
  ↓
[0x0000_0000] → MSP，[0x0000_0004] → Reset_Handler
  ↓
SystemInit（时钟、FPU、向量表等，依工程而定）
  ↓
.data：Flash → SRAM；.bss：清零；初始化 C/C++ 运行库
  ↓
main() → 外设初始化 → 裸机循环或启动 RTOS
```

### 为什么搬 `.data`、清 `.bss`？

- `.text/.rodata`：代码和只读常量，通常在 Flash。
- `.data`：有非零初值的全局/静态变量；初值存在 Flash，运行实体在 SRAM，所以要搬运。
- `.bss`：未初始化或初始化为 0 的全局/静态变量；C 语言要求初值为 0，启动时统一清零可节省 Flash。
- 栈保存局部变量、返回地址和现场；堆用于动态分配。

### Bootloader 和 `Reset_Handler` 一样吗？

不一样。System Memory Bootloader 是厂家固化的下载程序；用户 Bootloader 负责升级、校验、回滚和跳转；`Reset_Handler` 是当前镜像向量表中的复位入口。

用户 Bootloader 跳转 App 时通常要：关闭中断/SysTick 和已用外设，校验镜像，设置 `SCB->VTOR`，从 App 向量表装载 MSP，最后跳到 App 的复位向量。还要按具体芯片处理 Cache、MPU 等状态。

## 3. “你用的 MCU、主频、SRAM？”怎么答

> 项目使用 `完整型号`，内核为 `Cortex-Mx`，最高/实际主频 `__ MHz`，Flash `__ KB/MB`，SRAM `__ KB`。主要用了 `外设`。选择它是因为 `算力/存储/外设/功耗/成本/供货`。固件 Flash、RAM 占用约 `__%`，为升级预留 `__`。

从芯片丝印/工程宏核对型号，从 Datasheet 核对资源，从时钟树和 `SystemCoreClock` 核对实际主频，从 `.map` 文件核对真实存储占用。

### HC32F4A0 的基本规格是什么？

> [!warning] 先确认完整型号
> 以下按 **HC32F4A0** 系列整理。面试前必须根据芯片丝印、工程宏和 BOM 确认完整料号，因为不同容量、封装的 Flash、引脚和部分外设数量会变化。不要把系列最大值直接说成项目实际值。

根据小华半导体 HC32F4A0 产品页、数据手册和参考手册，该系列的核心规格为：

| 项目 | HC32F4A0 系列规格 |
|---|---|
| CPU | Arm Cortex-M4，ARMv7-M，带 FPU、MPU、DSP/SIMD、ETM/CoreSight |
| 最高主频 | 240 MHz |
| 性能标称 | 最高约 300 DMIPS / 825 CoreMark |
| Flash | 最大 2 MB，Dual Bank |
| SRAM | 最大 512 KB SRAM + 4 KB 备份 SRAM，其中包含 128 KB 单周期访问高速 RAM |
| 工作电压 | 1.8~3.6 V |
| DMA/总线 | 2 个 DMAC 单元、共 16 通道；USB HS、USB FS、Ethernet MAC 有专用 DMA；AHB 总线矩阵支持 CPU、DMA、USB DMA、ETH DMA 等主机访问 |
| 模拟外设 | 3 个 12 bit、2.5 MSPS ADC；4 个 12 bit、15 MSPS DAC；4 个 PGA；4 个高速比较器；温度传感器 |
| 通信外设 | 最多 10 USART、6 SPI、6 I²C、4 I²S、2 SDIO、1 QSPI、2 路 CAN，其中部分型号支持 CAN FD；USB HS/FS；10/100M Ethernet MAC |
| 外部存储 | EXMC 外部存储器控制器，包含 SMC、DMC、NFC，可接 SRAM/PSRAM/NOR Flash、SDRAM、NAND Flash |
| 低功耗/备份 | Sleep、Stop、Power-down；RTC、备份寄存器和 4 KB 备份 SRAM 可由 VBAT 供电 |
| 温度/封装 | -40~105 ℃；LQFP、BGA 等封装随料号变化 |

**怎么用于面试回答：** 可以说：“项目使用 HC32F4A0 的 `具体料号`，Cortex-M4F，实际跑 `__ MHz`，片上 Flash `__ KB/MB`、SRAM `__ KB`。我主要用了 `USART/SPI/I²C/ADC/DMA/EXMC/ETH/USB` 中的 `具体外设`。选它是因为主频、片上 RAM、外设数量和外部存储接口满足需求。”如果项目没有用到 EXMC、Ethernet、USB 等外设，不要主动展开，避免被追问到具体时序和 PCB 细节。

资料入口：[HC32F4A0 官方产品页及数据手册](https://www.xhsc.com.cn/product/1220.html)。

本地规格书/用户手册：[RM_HC32F4A0系列参考手册_Rev1.50.pdf](E:/HC32F4A0资料/RM_HC32F4A0系列参考手册_Rev1.50.pdf)

### MCU 应该如何选型？

**短答：** 先把需求量化，再按“硬性条件淘汰、性能与存储留余量、软件生态验证、成本和供应链收口”的顺序选型，不能只比较主频和价格。

1. **应用与实时性**：控制周期、最坏中断延迟、算法算力、是否需要 FPU/DSP、是否运行 RTOS/Linux。
2. **存储**：根据 map 文件或原型估算 Flash、静态 RAM、任务栈、通信缓冲和升级双分区，通常留出合理增长空间。
3. **外设**：接口种类、数量、引脚复用是否冲突；ADC 精度/采样率、Timer 通道、DMA 请求映射、USB/CAN/Ethernet 等必须逐项核对。
4. **电气与环境**：供电电压、IO 电平和 5 V 容忍、工作温度、EMC、低功耗电流、唤醒源、功能安全等级。
5. **封装和硬件**：GPIO 数量、PCB 层数、焊接能力、晶振/外部存储需求、调试接口是否保留。
6. **软件生态**：编译器、调试器、驱动库、RTOS/中间件、示例、勘误和社区成熟度；还要评估从旧平台迁移的工作量。
7. **量产因素**：单价只是其一，还要看供货周期、生命周期、第二来源、烧录测试、失效率和厂家技术支持。

> [!tip] 选型验证方法
> 建一张“必须满足/期望满足/可放弃”的选型表，用 Datasheet 做初筛，再用 Reference Manual 核对引脚复用、时钟、DMA 和外设细节，最后拿开发板验证最高风险项。不要在只看选型手册后直接定板。

## 4. 为什么有 I-Code、D-Code、System Bus？

**短答：** Cortex-M4 用分离的取指、代码区数据访问和系统访问通路，使取指与数据访问可并行，降低争用、提高吞吐率。

- I-Code：从代码区取指，也用于读取向量。
- D-Code：访问代码区中的数据，如 Flash 常量。
- System Bus：访问 SRAM、外设和系统资源。

这是改进型哈佛结构，但仍是统一地址空间。真实性能还受 Flash 等待周期、预取、总线矩阵和 DMA 争用影响。

# 二、通信与总线

## 1. SPI、I²C、UART 对比与选型

| 项目 | SPI | I²C | UART/USART 异步模式 |
|---|---|---|---|
| 信号 | SCK、MOSI、MISO、CS | SCL、SDA | TX、RX，可选流控 |
| 时钟 | 同步 | 同步 | 异步 |
| 双工 | 通常全双工 | 半双工 | 通常全双工 |
| 寻址 | 靠 CS | 7/10 位地址 | 无总线寻址 |
| 电气 | 通常推挽 | 开漏 + 上拉 | 通常推挽 |
| 特点 | 快、开销小、占引脚 | 少引脚、多设备 | 点对点、无需共享时钟 |

**选型：** 大数据量、低延迟、板内短线选 SPI；低速配置器件多且引脚少选 I²C；点对点、两端不共享时钟或搭配 RS-485/RS-232 收发器时常选 UART。

## 2. SPI 时序与四种模式

**短答：** 主机输出 SCK/CS，双方按 CPOL、CPHA 约定一个边沿采样、另一个边沿改变数据。CPOL 决定空闲电平，CPHA 决定第几个有效边沿采样。

| Mode | CPOL | CPHA | 空闲 | 采样边沿 |
|---|---:|---:|---|---|
| 0 | 0 | 0 | 低 | 第一个，即上升沿 |
| 1 | 0 | 1 | 低 | 第二个，即下降沿 |
| 2 | 1 | 0 | 高 | 第一个，即下降沿 |
| 3 | 1 | 1 | 高 | 第二个，即上升沿 |

判断时先由 CPOL 找空闲电平，再数第一/第二边沿；最终以从机 Datasheet 时序图为准。SPI 没有统一规定地址、命令和帧格式。

### SPI 多从机与数量

SCK/MOSI 共用，MISO 通常共用，每个从机独立 CS。理论数量受 CS 数量限制，可用译码器或菊花链扩展；实际还受 GPIO、负载电容、走线、频率和 MISO 高阻能力限制，没有统一最大值。同一时刻通常只选一个从机。

### SPI 现场算时间

```text
理想时间 ≈ 总位数 / SCK 频率
```

10 MHz 传 1000 字节：`1000 × 8 / 10 MHz = 0.8 ms`。实际还要加命令、地址、CS 建立/保持时间和软件/DMA 开销。

## 3. I²C 时序

**短答：** 空闲时 SCL/SDA 都为高；SCL 高时 SDA 高→低是 START、低→高是 STOP；数据在 SCL 高时稳定，每 8 位后第 9 位是 ACK/NACK。

- ACK：接收方在第 9 个时钟拉低 SDA。
- NACK：第 9 个时钟 SDA 保持高。
- Repeated START：不发 STOP 就再次 START，可保持总线控制权。

典型读寄存器：

```text
START → 地址+W → ACK → 寄存器地址 → ACK
→ Repeated START → 地址+R → ACK → 数据……
→ 主机对最后一字节 NACK → STOP
```

### I²C 完整的写过程和读过程是什么？

**写寄存器：**

```text
START → 7 位从机地址 + W(0) → 从机 ACK
→ 寄存器地址 → ACK
→ 数据 1 → ACK → 数据 2 → ACK……
→ STOP
```

**读寄存器：** 主机通常先用“写”告诉从机要读哪个寄存器，再切换方向读取：

```text
START → 从机地址 + W → ACK → 寄存器地址 → ACK
→ Repeated START → 从机地址 + R(1) → ACK
→ 从机发送数据；主机对需继续读取的字节回 ACK
→ 主机对最后一个字节回 NACK → STOP
```

纯接收型设备可能不需要先写寄存器地址；16 位寄存器地址、命令字节和自动地址递增也由从机协议决定。7 位地址与 R/W 位合成总线上的第一个字节，但不同驱动 API 可能要求传“原始 7 位地址”或“左移后的地址”，必须看 API 约定。

### I²C 和 SPI 常用速率是多少？为什么 I²C 通常更慢？

I²C 标准常见模式包括 Standard-mode 100 kbit/s、Fast-mode 400 kbit/s、Fast-mode Plus 1 Mbit/s；更高速模式必须由控制器、器件和电气设计共同支持。SPI 没有统一速率档位，常见从几百 kHz 到几十 MHz，高速 Flash/显示器可更高，最终看主从 Datasheet 和板级信号完整性。

I²C 通常更慢的原因：

- 开漏输出靠上拉电阻和总线电容形成 RC 上升沿，物理上限制速度；SPI 推挽能主动拉高/拉低。
- I²C 每字节还有 ACK、地址、START/STOP 等开销；SPI 每个 SCK 通常都在搬数据。
- I²C 是共享多设备总线，要支持仲裁、时钟同步/拉伸，时序更保守。

**提高 I²C 速率：**

- 硬件：主从都切换到支持的高速模式；按电容和灌电流重新计算上拉；缩短走线、减少支路/连接器和设备数量；合理布局地参考，必要时用 I²C buffer/repeater。
- 软件：优先硬件 I²C + 中断/DMA；减少逐字节函数和日志开销；合并连续寄存器访问，利用自动地址递增；避免无意义 STOP/重新寻址。
- 不能只提高外设分频：若上升时间已超标，频率越高错误越多。应使用示波器验证上升时间和电平。

### 为什么 I²C 是半双工，SPI 是全双工？

I²C 只有一根双向数据线 SDA，同一时刻数据只能朝一个方向传输，所以是半双工；R/W 位和 Repeated START 用来切换方向。

标准四线 SPI 有两条单向数据线：MOSI 和 MISO。主从内部各有移位寄存器，每个 SCK 边沿双方同时移出一位、同时移入一位，所以天然全双工。即使应用只想“读”，主机也要发送 dummy 字节来产生时钟；只想“写”时，MISO 上仍可能同时有返回数据，只是主机不使用。某些器件的三线/双向 SPI 会复用数据线，此时属于半双工变体。

### I²C 如何进行多主仲裁？什么是“线与”？

SCL/SDA 都是开漏 + 上拉：任何设备拉低，总线就是低；只有所有设备都释放，总线才为高。这种“低电平占优”的共享逻辑常称为 **wired-AND（线与）**；若以“低为真”的负逻辑看，也可描述成线或。

多主同时发送时，每个主机在释放 SDA 发送“1”的同时读取总线：

- 想发 1、实际读到 0，说明另一主机在发 0，本主机立即判定仲裁失败并停止驱动。
- 发 0 的主机继续，不会破坏获胜帧。
- 仲裁通常发生在地址和数据位；相同前缀的主机继续比较，直到出现不同位。

时钟线也通过开漏实现同步：SCL 被任一设备拉低就维持低电平。仲裁只解决总线所有权，软件仍需处理仲裁丢失标志、重试和超时；单主系统通常不会遇到多主仲裁。

### SPI 与 I²C 的硬件电气特征为什么这样设计？

| 特征 | I²C | SPI |
|---|---|---|
| 输出结构 | SCL/SDA 开漏，外部上拉 | SCK/MOSI/CS 通常推挽，MISO 由被选从机推挽输出 |
| 拓扑 | 多设备共享两根线，协议内寻址 | 主从结构，每从机通常独立 CS |
| 方向 | SDA 双向半双工 | MOSI/MISO 分离，全双工 |
| 设计目标 | 少引脚、可共享、支持仲裁 | 高速度、低协议开销、边沿明确 |

I²C 不能用多个普通推挽输出共线，否则一个拉高、另一个拉低会短路冲突；开漏让多设备安全共享并能边发送边检测仲裁。SPI 用 CS 保证同一时刻仅一个从机驱动 MISO，因此可用推挽获得更快边沿，但软件/硬件必须确保未选从机 MISO 真正高阻。

### I²C 从机地址如何配置？地址相同会怎样？

从机地址可能来自：

- 芯片出厂固定地址。
- ADDR/SA0 等硬件引脚组合。
- 上电后写内部寄存器、OTP/EEPROM 配置。
- MCU 自己做 I²C 从机时，写控制器的 Own Address 寄存器。

若同一总线上两个从机地址相同，它们会同时 ACK，并同时接收写数据。读时更危险：若两个从机返回的位不同，因开漏线与，总线上 0 会覆盖 1，主机得到混合错误数据，设备状态也可能同时被改变。解决方法是改地址引脚/寄存器、分别控制复位/使能后改址，或使用 I²C 多路复用器。不能依靠“它们大概不会同时响应”。

### SPI 模式参数配错会出现什么现象？

- **CPHA 配反**：接收端在数据正在变化的边沿采样，常表现为整体左/右移一位、bit0/bit7 错、数据随频率/温度不稳定，或者完全无法识别命令。
- **CPOL 配反**：时钟空闲电平错误，CS 有效或释放时可能产生器件眼中的额外边沿；采样边沿也随之错位。
- **CPOL、CPHA 都与从机不匹配**：读到 `0x00/0xFF`、固定错码、位移或无响应都有可能，不能只靠错误值反推是哪一项。

所谓“SPI clock 正负电平翻了”通常就是 CPOL 反了。它不一定只让每位取反，而是改变空闲态和边沿顺序；有的设备可能偶尔可用，有的会多采/漏采第一位。正确方法是对照从机时序图，用逻辑分析仪同时观察 CS、SCK、MOSI、MISO，而不是盲试四种模式。

### SPI、I²C 各引脚应该配置成什么 GPIO 模式？

**短答：** I²C 的 SCL/SDA 都按开漏总线理解，输出高电平本质是释放总线，输入时直接读总线电平；SPI 的 SCK/MOSI/CS 通常由主机推挽输出，MISO 是被选中从机推挽输出、主机输入，未选中的从机 MISO 必须高阻。

以 MCU 作为主机时，常见配置如下：

| 协议引脚 | 方向 | 硬件外设常见 GPIO 配置 | 软件模拟常见 GPIO 配置 | 说明 |
|---|---|---|---|---|
| I²C SCL | 双向，主机输出时钟，从机可拉低做 clock stretching | Alternate Function Open-Drain + 外部上拉 | Open-Drain 输出；释放后可读输入电平 | 主机输出高不是主动推高，而是释放，由上拉恢复高电平 |
| I²C SDA | 双向，发送方驱动，接收方在 ACK 位驱动 | Alternate Function Open-Drain + 外部上拉 | Open-Drain 输出；发送 1 时释放，发送 0 时拉低，同时可读线 | 支持 ACK/NACK、仲裁和线与，不能配置成推挽输出 |
| SPI SCK | 主机输出，从机输入 | Alternate Function Push-Pull 输出 | Push-Pull 输出 | 空闲电平由 CPOL 决定，复位期间可按器件要求上拉/下拉 |
| SPI MOSI | 主机输出，从机输入 | Alternate Function Push-Pull 输出 | Push-Pull 输出 | 主机在约定边沿前稳定数据 |
| SPI MISO | 主机输入，从机输出 | 主机侧 Alternate Function 输入；从机侧 Alternate Function Push-Pull/三态输出 | 主机侧输入；从机侧未选中时高阻 | 多从机共用 MISO 时，未选中从机必须释放总线 |
| SPI CS/NSS | 主机输出，从机输入 | 常用普通 GPIO Push-Pull 输出，也可用硬件 NSS | Push-Pull 输出 | 通常空闲高、选中低；建议上拉，防止复位期间误选从机 |

从机模式时方向要反过来看：SCK、MOSI、CS 是输入，MISO 是输出；但 MISO 只有在本从机被 CS 选中时才允许驱动，否则会和其他从机冲突。不同 MCU 的 “Alternate Function 输入/输出” 写法可能不同，本质是把引脚复用给外设，并由外设控制方向。

> [!warning] 常见坑
> I²C 配成推挽输出可能导致两个器件一个拉高、一个拉低而短路；SPI 多从机若 MISO 不能高阻，会出现读数互相干扰；CS 初始电平没先拉高就初始化 SPI，可能让从机误收一帧。

### NACK 什么时候收到？

题目里的 “NACT” 通常是 **NACK**。地址阶段 NACK 可能是无设备、地址错、未上电或设备忙；写数据阶段 NACK 表示从机不接受；主机读取时，对最后一个字节主动回 NACK，通知从机结束读取。

### 为什么需要上拉？

I²C 是开漏结构，设备只能主动拉低，释放后由上拉电阻恢复高电平，这也支持线与和仲裁。阻值过大导致 RC 上升慢，过小导致灌电流/功耗大。应结合 VDD、总线电容、上升时间和器件灌电流计算；内部上拉往往太弱，不能代替合适的外部上拉。

### 最多挂几个设备？

不能简单答 127 个。7 位地址含保留地址，地址相同的设备会冲突；实际还受总线电容、走线、上拉、速率和驱动能力限制。可改地址或用 I²C 多路复用器扩展。

### I²C 现场算时间

每字节通常需 9 个时钟（8 bit + ACK/NACK）。400 kHz 写 1 字节寄存器地址和 4 字节数据，粗算地址+W、寄存器地址、4 数据共 6 字节：`6 × 9 / 400 kHz = 135 μs`。还需考虑 START/STOP、时钟拉伸和软件间隙。
## 4. UART 与 USART

**短答：** UART 是通用异步收发器；USART 还支持同步模式。USART 配成异步模式时通常就按 UART 使用。

帧格式：`空闲高 → 起始位低 → 5~9 数据位 → 可选校验 → 停止位高`。双方必须约定波特率、数据位、停止位和校验。

### 什么是同步和异步？UART 加一根时钟线就会变成同步吗？

- **同步通信**：收发双方共享或恢复出一个连续/成帧的时钟，接收端按明确的时钟边沿采样，例如 SPI、I²C。
- **异步通信**：不传输独立时钟，双方各用本地时钟；UART 接收端检测起始位后按约定波特率进行过采样，并用停止位重新校验帧边界。

给 TX/RX 随便并联一根 GPIO 时钟线，不会自动把 UART 变成同步协议。必须让两端硬件都支持相同的同步模式，并约定时钟源、极性、相位、数据方向和帧格式。USART 的同步模式会由 CK 引脚输出或接收串行时钟，管脚要配置为相应 Alternate Function；具体支持能力和接线看该 MCU 的 USART 章节。若自行用定时器输出时钟、再用 GPIO/UART 传数据，本质是在设计新协议，接收外设也必须按该时钟采样。

### 波特率及配错的后果

波特率是每秒符号数；普通二进制 UART 可近似看成 bit/s。误差小时接收端还能在位中间正确采样；误差累积过大会导致数据错、帧错误或无法接收。配置时要核对外设时钟、分频、过采样和晶振误差。

`8N1` 每字节占 10 bit：

```text
发送时间 = 字节数 × 10 / 波特率
```

115200 baud 发 100 字节约 `8.68 ms`，有效数据吞吐约 `11.52 KB/s`。

### UART 如何保证可靠性？

- 物理层：共地、电平匹配；长线/干扰环境用 RS-485/隔离/屏蔽等。
- 协议层：帧头、长度、命令、序号、CRC、转义。
- 机制层：ACK/NACK、超时、重传、去重、流控。
- 实现层：中断或 DMA + 环形缓冲；IDLE 中断处理不定长帧；处理 ORE/FE/NE/PE。
- ISR 只搬数据/通知任务，解析放到任务中，并检测缓冲溢出。

### UART 的基本配置是什么？参数都正确仍读错怎么办？

基本配置至少包括：外设时钟源和分频、波特率、数据位、停止位、奇偶校验、收发方向、过采样、bit order；需要时再配 RTS/CTS、反相、半双工、DMA、中断和 FIFO。GPIO 上 TX 通常为复用推挽且空闲高，RX 为复用输入，两端 TX/RX 交叉并共地；还必须确认双方使用同一种 TTL/CMOS、RS-232 或 RS-485 电气标准。

**波特率不匹配的现象：** 少量误差时可能偶发乱码；误差大时出现帧错误 FE、校验错误 PE、持续乱码或完全收不到。误差会在一帧内累计，因此字节较长、停止位较少时裕量更紧。

波特率和共地正确仍不代表一定正常，继续检查：

1. 数据位、校验位、停止位不一致；例如一端 8N1、另一端 8E1。
2. 电平标准错误：TTL 不能直接接 RS-232，3.3 V/5 V 容限不匹配，RS-485 A/B 或方向控制错误。
3. TX/RX 接反、引脚复用选错、RX 浮空、线长/噪声/地弹导致边沿失真。
4. 实际外设时钟不是以为的频率，波特率寄存器虽相同但真实波特率不同；用示波器量一个 bit 的宽度。
5. RX 过载产生 ORE，DMA 长度/缓存一致性错误，环形缓冲覆盖，ISR 不及时。
6. 字节序、协议转义、帧长、CRC 或结构体对齐错误——这时 UART 字节本身可能完全正确，是上层解析错。
7. 回显、换行符、文本编码或二进制数据显示方式造成“看起来乱码”。

定位时先用逻辑分析仪确认线上的原始字节和帧格式，再判断问题在物理层、UART 外设层还是协议解析层。

## 5. 硬件实现与软件模拟

| 维度 | 硬件外设 | GPIO 软件模拟 |
|---|---|---|
| 时序 | 稳定、速率高 | 受中断/调度抖动影响 |
| CPU | 占用低，可配 DMA | 占用高，常忙等 |
| 引脚 | 受复用限制 | 灵活 |
| 用途 | 正式、高速、低功耗 | 引脚受限、低速或特殊协议 |

- 硬件 I²C：复用开漏 + 外部上拉；软件 I²C：GPIO 开漏，输出高实质是释放线路。
- 硬件 SPI：SCK/MOSI 通常复用推挽，MISO 输入，CS 可硬件或 GPIO；软件 SPI 对应 GPIO 推挽/输入。
- UART：TX 通常复用推挽，RX 为输入/复用输入。

## 6. EXMC 和 LocalBus

**短答：** HC32F4A0 的 EXMC 是外部存储器控制器，用来把片内 AHB 访问转换成 SRAM、PSRAM、NOR Flash、NAND Flash、SDRAM 等片外存储器的并行总线时序。LocalBus 通常指这种本地并行外部总线：MCU 像访问一段地址空间一样访问片外器件，硬件自动产生地址线、数据线、片选、读写控制和等待信号。

```text
CPU / DMA 发起 AHB 访问
  ↓
地址落入外部存储器映射区
  ↓
EXMC 根据地址选择 SMC / DMC / NFC 和对应片选
  ↓
输出地址、数据、CS、OE、WE、ADV、WAIT 等总线信号
  ↓
片外 SRAM / PSRAM / NOR / SDRAM / NAND 完成读写
```

HC32F4A0 参考手册中 EXMC 主要分为三个子控制器：

| 子模块 | 含义 | 典型外设 |
|---|---|---|
| SMC | Static Memory Controller | SRAM、PSRAM、NOR Flash |
| DMC | Dynamic Memory Controller | SDRAM |
| NFC | NAND Flash Controller | NAND Flash |

EXMC 的价值是让外部并行存储器进入 MCU 的统一地址空间。软件侧可以用指针或结构体访问映射地址，硬件侧由 EXMC 负责把一次 AHB 读写拆成外部器件需要的总线周期。AHB 访问宽度和外部存储器位宽不一致时，EXMC 可以做自动分割；例如 CPU 发起 32 bit 访问，而外部数据总线只有 16 bit，就会拆成两个外部总线操作。

### EXMC 和普通 GPIO 模拟有什么区别？

| 维度 | EXMC / LocalBus | GPIO 软件模拟 |
|---|---|---|
| 地址访问 | 映射到固定地址区，可像内存一样读写 | 需要手动翻转地址、数据、控制线 |
| 时序 | 控制器硬件产生，可配置建立/保持/等待周期 | 受中断、编译优化和延时函数影响 |
| 吞吐 | 高，适合大容量并行存储器 | 低，只适合调试或低速简单器件 |
| CPU 占用 | 低，可由 CPU/DMA 发起块访问 | 高，通常忙等 |
| 复杂度 | 引脚多、时序和 PCB 要求高 | 硬件简单但软件开销大 |

### 配置 EXMC 要关注什么？

1. **存储器类型**：先判断是 SRAM/PSRAM/NOR、SDRAM 还是 NAND，对应 SMC、DMC、NFC。
2. **地址映射和片选**：确认访问地址落在哪个外部存储区，片选 CS 是否和硬件连接一致。
3. **数据位宽**：8/16/32 bit 必须和外部芯片、PCB 连接、软件访问宽度匹配。
4. **同步/异步时序**：SMC 可配置同步或异步访问；异步 SRAM/NOR 常看地址建立、数据建立、OE/WE 脉宽和保持时间。
5. **地址数据复用**：部分 NOR Flash、PSRAM 可复用地址线和数据线，需要 ADV 等锁存控制信号。
6. **WAIT/Ready 信号**：外部器件较慢或同步访问时，可用 WAIT 拉长总线周期。
7. **GPIO 复用和电气**：EXMC 引脚多，必须核对 AF、驱动能力、上电状态、走线长度、阻抗、串扰和时钟边沿。
8. **Cache/DMA 一致性**：如果用 DMA 或带 Cache 的内核访问外部存储，要明确缓冲区属性、Cache clean/invalidate 和内存屏障。

### 面试怎么说？

可以这样答：

> 我理解的 LocalBus 是 MCU 片外并行扩展总线，HC32F4A0 通过 EXMC 实现。EXMC 挂在 AHB 侧，内部有 SMC、DMC、NFC，分别面向 SRAM/PSRAM/NOR、SDRAM、NAND。软件访问外部映射地址时，EXMC 自动输出地址、数据、片选和读写控制信号，所以比 GPIO 模拟快得多、CPU 占用也低。实际调试时重点看地址映射、片选、位宽、时序参数和 PCB 信号质量。

> [!warning] 常见坑
> EXMC 不是“更快的 SPI”，它通常要占用大量并行引脚，对时序和 PCB 更敏感；也不能只看 MCU 支持 EXMC，还要确认当前封装是否引出了足够的地址线、数据线和控制线。

# 三、Cortex-M4 内核

## 1. 常用寄存器

| 寄存器 | 作用 |
|---|---|
| R0~R3 | 参数、返回值、临时寄存器 |
| R4~R11 | 被调用者保存寄存器 |
| R12 | 临时寄存器 IP |
| R13/SP | 栈指针，实际为 MSP 或 PSP |
| R14/LR | 返回信息；异常中可保存 EXC_RETURN |
| R15/PC | 程序计数器 |
| xPSR | 条件标志、当前异常号、执行状态 |
| PRIMASK | 屏蔽可配置优先级异常 |
| BASEPRI | 按优先级阈值屏蔽，RTOS 临界区常用 |
| CONTROL | Thread 模式特权级和 MSP/PSP 选择 |

常用系统寄存器：`VTOR` 向量表基址；`AIRCR` 优先级分组/复位请求；`ICSR` 异常状态；`CFSR/HFSR/MMFAR/BFAR` 定位 Fault；NVIC 的 ISER/ICER、ISPR/ICPR、IABR、IPR 分别管理使能、挂起、活动和优先级。

> [!warning] 架构混淆
> Cortex-M 主要区分 Thread mode 与 Handler mode，并用 MSP/PSP。不要把经典 ARM7/ARM9 的 CPSR/SPSR、多工作模式和 FIQ 银行寄存器答案直接套到 Cortex-M4。

## 2. 异常及处理流程

**短答：** 异常是打断顺序执行、让 CPU 进入处理程序的事件总称；Reset、NMI、Fault、SVC、PendSV、SysTick 和外部中断都属于异常。

1. 异常变成 Pending，内核按使能、屏蔽和优先级仲裁。
2. 硬件把 `R0~R3、R12、LR、PC、xPSR` 压入当前栈（FPU 时可能有扩展栈帧）。
3. 从向量表取处理函数地址，进入 Handler mode；Handler mode 使用 MSP。
4. ISR 执行，软件保存其他必要寄存器。
5. 根据 LR 中 `EXC_RETURN` 恢复现场并返回。

尾链和迟到机制可以减少连续异常的出入栈开销。

## 3. 中断及处理流程

**短答：** 中断是外设或外部事件向 CPU 发出的异步处理请求，本质上属于异常。CPU 不需要反复轮询设备，而是在事件发生后暂停当前代码，转去执行中断服务函数 ISR，处理完成后再恢复原程序。

常见中断源包括 GPIO 边沿、定时器更新、UART 收发、ADC 转换完成、DMA 传输完成和通信错误等。一个中断能真正进入 CPU，通常要同时满足：**事件标志置位、外设中断源使能、NVIC 通道使能、没有被屏蔽，并且优先级满足响应条件。**

### 中断处理流程

```text
外设事件发生
    ↓
外设状态位置位，并向 NVIC 提交中断请求
    ↓
NVIC 将中断置为 Pending，按使能、屏蔽状态和优先级仲裁
    ↓
CPU 完成当前指令，硬件自动压入基础现场
R0~R3、R12、LR、PC、xPSR
    ↓
从向量表取得 ISR 地址，进入 Handler mode 执行 ISR
    ↓
判断中断来源，读取必要数据，按手册清除中断标志
    ↓
通知主循环或任务继续处理
    ↓
通过 EXC_RETURN 硬件恢复现场，从被打断处继续运行
```

ISR 应遵循“短、快、确定”的原则：只做清标志、取数据、写缓冲区、释放信号量或发送任务通知等必要工作，复杂计算、阻塞等待、延时和大量日志放到主循环或任务中处理。

要同时检查外设标志、外设中断使能、NVIC 使能三层。清标志可能是写 0、写 1、读寄存器后再写寄存器，必须查 Reference Manual；清除方式错误会导致中断退出后立即再次进入。

### 中断函数编写的注意事项

**短答：** ISR 只处理必须立即完成且执行时间可控的工作，核心是**确认来源、保存数据、清除标志、通知后续处理**。不能阻塞，不能执行耗时或时间不可预测的操作，也不能直接调用不支持中断上下文的接口。

| ISR 中可以做 | 说明 |
|---|---|
| 读取并判断中断状态 | 一个 IRQ 可能对应多个中断源，必须判断真正来源 |
| 按手册清除中断标志 | 防止退出后立刻再次进入；注意写 0 清、写 1 清或特定读写顺序 |
| 读取接收寄存器、保存采样值 | 及时取走 UART、ADC 等数据，避免溢出或覆盖 |
| 向预分配的环形缓冲区写入少量数据 | 只搬运数据，解析协议放到主循环或任务中 |
| 设置事件标志或计数器 | 通知主循环稍后处理，操作要保证原子性 |
| 使用 RTOS 的 `...FromISR()` 接口 | 可发送队列、信号量或任务通知，并按返回值请求任务切换 |
| 执行少量、时间确定的寄存器操作 | 例如更新 PWM 比较值、启动下一次 DMA 传输 |

| ISR 中不应该做 | 原因与替代方案 |
|---|---|
| 延时或忙等待 | 占住 CPU，增加其他中断延迟；改为定时器、状态机或任务延时 |
| 等待锁、信号量、队列或事件 | ISR 不能睡眠，容易死锁；只用非阻塞的 FromISR 接口通知任务 |
| 执行复杂算法、协议解析和大循环 | 执行时间长且不确定；只保存原始数据，在线程上下文处理 |
| 大量 `printf`、日志输出 | 格式化和串口发送很慢，还可能加锁；记录简短事件码，后台统一输出 |
| `malloc/free` 或动态创建对象 | 时间不可预测、可能加锁并造成碎片；使用静态或预分配缓冲区 |
| 调用普通 RTOS API | 普通 API 可能阻塞或操作调度器；使用明确允许的 `...FromISR()` 版本 |
| 调用不可重入函数 | 若主程序或嵌套 ISR 同时调用，会破坏内部状态；改用可重入接口或移到任务中 |
| 递归、大数组或大量局部变量 | 快速消耗 MSP，中断嵌套时更容易栈溢出 |
| 无必要地进行浮点运算 | 可能触发额外 FPU 上下文保存，增加延迟和栈占用；确认编译器及 RTOS 的 FPU 策略 |
| 长时间关闭全部中断 | 破坏实时性，可能丢事件；临界区应尽量短，并优先使用原子操作或优先级屏蔽 |

编写 ISR 还要注意以下问题：

1. **先处理数据还是先清标志，要看外设机制。** 对可能覆盖的数据先读数据；对持续触发的标志要尽快按手册清除，不能机械地规定一律先清或后清。
2. **共享变量不等于加了 `volatile` 就安全。** `volatile` 只保证编译器真实访问内存，不保证 `count++`、读改写和多字节访问具有原子性；必要时使用原子操作或极短临界区。
3. **处理同一 IRQ 下的所有来源。** 例如 UART IRQ 可能同时包含 RX、TX、空闲和错误标志，ISR 应逐项判断，避免遗漏后持续进中断。
4. **防止事件丢失。** 布尔标志只能表达“至少发生一次”，高频事件应使用计数器、队列、环形缓冲区或 DMA。
5. **控制最坏执行时间。** 评估 ISR 最大耗时、触发频率、嵌套深度和 MSP 峰值，而不只是看平均执行时间。
6. **正确处理 RTOS 唤醒。** `...FromISR()` 唤醒更高优先级任务后，应按端口要求在退出 ISR 前请求一次上下文切换。

一个常见写法是让 ISR 只完成“上半部”，把耗时业务留给“下半部”：

```c
void UART_IRQHandler(void)
{
    BaseType_t task_woken = pdFALSE;

    if (uart_rx_ready()) {
        uint8_t data = uart_read_data();
        ring_buffer_push_from_isr(&rx_buffer, data);
        vTaskNotifyGiveFromISR(rx_task_handle, &task_woken);
    }

    if (uart_error_pending()) {
        uart_clear_error_by_manual();
    }

    portYIELD_FROM_ISR(task_woken);
}
```

上例只表达结构，实际寄存器读取顺序、清标志方式和函数名必须以芯片手册及所用 RTOS 端口为准。

### 中断的嵌套

**短答：** 中断嵌套是 CPU 正在执行某个 ISR 时，又响应了更高抢占优先级的中断。高优先级 ISR 执行完后，CPU 恢复低优先级 ISR 的现场并继续执行，最后再返回原来的线程代码。

```text
主程序运行
  └─ 中断 A 到来：主程序现场压栈，进入低优先级 ISR A
       └─ 更高抢占优先级中断 B 到来：ISR A 现场再次压栈
            └─ ISR B 执行完成，恢复 ISR A 现场
       └─ ISR A 从被打断处继续，执行完成后恢复主程序现场
  └─ 主程序从被打断处继续运行
```

能否嵌套主要看以下条件：

1. 新中断已经使能且处于 Pending 状态，没有被 `PRIMASK`、`BASEPRI` 等屏蔽。
2. 新中断的**抢占优先级必须高于**当前正在执行的异常；Cortex-M 中优先级数值越小，优先级越高。
3. 抢占优先级相同的中断不能互相打断，子优先级只决定多个 Pending 中断的先后响应顺序。
4. 进入嵌套中断时，硬件再次保存基础现场。Handler mode 使用 MSP，因此嵌套层数越深，中断栈占用越大。
5. 高优先级 ISR 返回后先恢复低优先级 ISR，不会直接跳回主程序或任务。

例如 A 的抢占优先级数值为 3，B 为 1，则 B 可以打断 A；若 B 为 3、仅子优先级更高，B 只能等待 A 结束；若 B 为 5，则优先级更低，也必须等待。

嵌套能降低关键事件的响应延迟，但会增加栈占用、共享数据竞争和时序分析难度。关键共享数据可用极短临界区、原子操作或无锁缓冲区保护，不能为了省事长时间关闭全部中断。

**关系：中断是一类异常，异常不只有中断。**

### 面试怎么说？

> 中断是外设或外部事件触发的一类异步异常。事件发生后，外设置位标志并向 NVIC 请求，NVIC 根据使能、屏蔽和优先级仲裁；CPU 自动保存基础现场，从向量表进入 ISR。ISR 中先确认来源并按手册清标志，只做必要的快速处理，再通过 EXC_RETURN 恢复现场。若 ISR 执行期间来了抢占优先级更高的中断，就会形成嵌套；同抢占优先级只能排队，子优先级不决定抢占。嵌套越深，MSP 栈占用和共享资源风险越大。

> [!warning] 常见坑
> 把“子优先级高”误认为可以抢占；忘记清外设标志导致反复进入；在 ISR 中延时、阻塞或大量打印；临界区关闭中断时间过长；嵌套较深却没有评估 MSP 栈空间；多个中断共享变量却没有使用 `volatile` 和必要的同步保护。`volatile` 只能保证实际读写，不能保证复合操作的原子性。

## 4. NVIC 与中断优先级

NVIC 是内核集成的嵌套向量中断控制器，负责使能、挂起、优先级仲裁、抢占和向量化入口。

**优先级数值越小，逻辑优先级越高，0 最高。**

- 抢占优先级决定能否打断当前 ISR。
- 子优先级只决定同抢占级且同时 Pending 时谁先响应。
- `PRIGROUP` 决定优先级位如何分配；实际实现位数看 `__NVIC_PRIO_BITS`。
- 是否抢占还受屏蔽寄存器和当前异常状态影响。

> [!warning] FreeRTOS 高频坑
> 能调用 `...FromISR()` 的中断，逻辑优先级不能高于 FreeRTOS 允许系统调用的阈值；优先级 0 通常绝不能调用 FreeRTOS API。

## 5. 复位种类、流程和备份域

常见来源：POR/PDR、BOR 欠压、NRST 外部复位、`SYSRESETREQ` 软件复位、IWDG/WWDG、低功耗退出和 Option Byte 相关复位。启动后应尽早读取并记录 RCC 复位原因，再清除标志。

多种复位是为了区分电源异常、软件跑飞、时钟异常和主动升级等故障，并限定复位范围。RTC/备份寄存器需在主系统复位时保持，因此位于可由 VBAT 供电的备份域；主系统复位通常不清空备份域，精确行为查具体型号手册。

## 6. 大小端

小端把最低有效字节放在最低地址，Cortex-M 通常用小端。例如 `0x12345678` 从低地址到高地址为 `78 56 34 12`。协议/文件格式可能指定大端，应显式序列化，不能直接发送结构体内存。

# 四、C 语言与内存

## 1. 字节对齐

**短答：** 对齐让对象地址满足类型/ABI 要求，保证合法高效访问；结构体还会补齐为其最大对齐要求的整数倍，以保证数组中每个元素对齐。

```c
typedef struct {
    char a;       // offset 0，随后通常填充 3 字节
    int32_t b;    // offset 4
    int16_t c;    // offset 8，末尾通常再填充 2 字节
} Example;        // 常见 ABI 下 sizeof 为 12
```

把成员按对齐要求从大到小排列常可减少填充。实际布局由编译器、ABI 和选项决定，用 `sizeof`、`offsetof` 验证。

对齐访问通常只需一次总线事务；非对齐访问可能变慢，某些指令、总线或外设访问会 Fault。`packed` 可消除填充，但可能导致非对齐访问、性能下降甚至 Fault；线上格式最好显式编解码。

## 2. `volatile` 能保证线程安全吗？

不能。它主要要求编译器每次实际访问对象，适合外设寄存器和异步变化标志；不保证原子性、互斥或内存顺序，不能代替锁、临界区或原子操作。

## 3. 栈和堆

- 栈自动分配释放、快但容量固定；递归、大数组、深调用可导致溢出。
- 堆生命周期灵活，但会失败、碎片化且耗时不确定。
- RTOS 每个任务有独立任务栈，中断通常用 MSP 对应的栈。
- 实时系统常用静态对象/内存池，或只在初始化阶段分配。

## 4. `const`、`static`

- `const` 表示不能通过该左值修改，不等于必然存放在 Flash。
- 函数内 `static` 具有静态存储期，只初始化一次。
- 文件级 `static` 是内部链接，只在当前编译单元可见。

## 5. 函数指针

**短答：** 函数指针是保存函数入口地址的指针。通过它可以间接调用签名匹配的函数，常用于回调函数、中断向量表、驱动接口、协议分发表和状态机。函数指针让调用方依赖统一接口，而不依赖某个具体实现。

### 如何声明和调用？

```c
int add(int a, int b)
{
    return a + b;
}

int (*operation)(int, int) = add;

int result1 = operation(2, 3);
int result2 = (*operation)(2, 3);  // 与上一行等价
```

`int (*operation)(int, int)` 的含义是：`operation` 是一个指针，指向“接收两个 `int` 参数并返回 `int`”的函数。阅读复杂声明时先看变量名，再根据括号向外读。

| 声明 | 含义 |
|---|---|
| `int (*fp)(int)` | `fp` 是函数指针，指向参数为 `int`、返回 `int` 的函数 |
| `int *fp(int)` | `fp` 是函数，参数为 `int`、返回 `int *` |
| `void (*handlers[4])(void)` | `handlers` 是含 4 个元素的数组，每个元素都是函数指针 |
| `void (**fp)(void)` | `fp` 是二级指针，指向一个函数指针 |

`()` 的优先级高于 `*`，所以声明函数指针时 `(*fp)` 外面的括号不能省略。实际工程中通常使用 `typedef` 简化：

```c
typedef int (*binary_operation_t)(int left, int right);

binary_operation_t operation = add;
int result = operation(10, 20);
```

函数名在大多数表达式中会转换成函数地址，因此 `operation = add` 和 `operation = &add` 都可以；调用时 `operation()` 和 `(*operation)()` 等价。

### 函数指针有什么用途？

#### 1. 回调函数

调用方完成某件事后，通过函数指针反向通知注册方：

```c
typedef void (*transfer_done_cb_t)(int status, void *context);

typedef struct {
    transfer_done_cb_t callback;
    void *context;
} transfer_t;

void transfer_complete(transfer_t *transfer, int status)
{
    if (transfer->callback != NULL) {
        transfer->callback(status, transfer->context);
    }
}
```

同时保存 `void *context` 可以把对象实例或用户数据传回回调，避免依赖全局变量。回调在哪个上下文执行必须写清楚：如果由 ISR 调用，回调也必须遵守 ISR 的限制，不能阻塞或调用普通 RTOS API。

#### 2. 驱动接口与硬件抽象

```c
typedef struct {
    int  (*init)(void);
    int  (*read)(uint8_t *data, size_t length);
    int  (*write)(const uint8_t *data, size_t length);
    void (*deinit)(void);
} device_ops_t;
```

不同的 SPI、I²C 或模拟设备提供各自实现，上层只持有 `device_ops_t`，不需要知道底层硬件细节。这种方式常用于 BIOS/BSP、设备驱动框架和单元测试中的 mock。

#### 3. 查表分发

```c
typedef void (*command_handler_t)(const uint8_t *data, size_t length);

#define ARRAY_SIZE(array) (sizeof(array) / sizeof((array)[0]))

static const command_handler_t command_table[] = {
    handle_start,
    handle_stop,
    handle_query,
};

void dispatch_command(uint8_t command, const uint8_t *data, size_t length)
{
    if (command < ARRAY_SIZE(command_table) && command_table[command] != NULL) {
        command_table[command](data, length);
    }
}
```

函数表可以减少很长的 `switch`，也适合协议命令和表驱动状态机。但命令值不连续或表较稀疏时，使用“命令 ID + 函数指针”的结构体表通常更节省空间。

### 函数指针使用注意事项

1. **调用前检查是否为 `NULL`。** 未注册的回调不能直接调用。
2. **函数签名必须完全兼容。** 参数个数、参数类型、返回类型和调用约定不匹配会产生未定义行为；不要靠强制类型转换掩盖编译器警告。
3. **保证指针来源可信。** 越界写、栈溢出或对象生命周期结束都可能破坏函数指针，使 PC 跳到非法地址并触发 HardFault。
4. **表索引必须检查边界。** 外部协议提供的命令字不能未经校验直接作为函数表下标。
5. **并发注册要同步。** 一个任务修改回调、另一个任务或 ISR 同时调用时可能产生竞态；应在初始化期固定，或使用临界区和明确的生命周期管理。
6. **不要保存无效上下文。** 回调的 `context` 不能指向已经返回的局部变量或已释放对象。
7. **明确执行上下文和耗时限制。** ISR 回调、定时器回调和任务回调能调用的 API 不同，接口文档应明确说明。
8. **安全系统可校验地址范围。** 调用前可检查函数地址是否位于合法代码区，并结合 MPU、栈保护和控制流完整性降低损坏风险。

### 面试怎么说？

> 函数指针保存函数入口地址，声明时关键是 `(*fp)` 的括号，例如 `int (*fp)(int)` 表示指向参数和返回值都是 `int` 的函数。它常用于回调、驱动接口和查表分发，能让上层依赖统一接口，实现解耦。工程上我会用 `typedef` 简化签名，并检查空指针、表索引和生命周期；函数签名不匹配、越界写破坏函数指针或调用已经失效的回调，都可能让 PC 跳到非法地址并触发 HardFault。

> [!warning] 常见坑
> 混淆“函数指针”和“返回指针的函数”；调用空回调；把不兼容函数强制转换后塞进函数表；未检查外部命令索引；回调保存了局部变量地址；在 ISR 回调里执行阻塞操作；多个上下文同时修改和调用同一个函数指针。

# 五、常用外设

## 1. PWM 与 Timer

PWM 用定时器 ARR 决定周期、CCR 决定占空比。向上计数常见公式：

```text
PWM 频率 = f_tim / ((PSC + 1) × (ARR + 1))
占空比 ≈ CCR / (ARR + 1)
```

APB 分频可能影响定时器时钟，中心对齐公式也不同。Timer 还可做更新中断、输出比较、输入捕获、编码器、单脉冲、触发 ADC/DMA。输入捕获测频：`f_input = 计数时钟 / 相邻同类边沿计数差`，注意溢出和滤波。

## 2. 看门狗：IWDG 与 WWDG

| 项目 | IWDG | WWDG |
|---|---|---|
| 时钟 | 独立低速时钟 | 通常来自 APB |
| 条件 | 超时前喂 | 只能在窗口内喂，过早/过晚都异常 |
| 用途 | 卡死、主时钟异常 | 执行过快/过慢、时序异常 |

不要在无条件高频中断中喂狗。应由健康监控确认关键任务都在推进后统一喂狗，复位后记录看门狗复位原因和关键现场。

## 3. ADC

ADC 把模拟电压量化为数字值：

```text
数字码 ≈ Vin / Vref × (2^N - 1)
```

精度受 Vref、分辨率、采样时间、源阻抗、噪声、线性度和校准影响。源阻抗高时要加采样时间或缓冲。定时器触发 + DMA 循环采样能提供稳定周期；平均能减随机噪声，不能消除偏置。

## 4. DMA

DMA 在外设与内存或内存之间搬运数据，降低 CPU 占用。配置包括源/目标、方向、宽度、长度、自增、请求、优先级和普通/循环模式。常用于 UART/SPI、ADC 循环采样和双缓冲。

仍需处理半传输/全传输/错误、缓冲区所有权、竞态和总线争用；带 D-Cache 的芯片还要维护 Cache 一致性。

### DMA 的完整工作过程是什么？

1. CPU 配置 DMA 请求源、源/目标地址、传输数量、数据宽度、自增方式、方向、优先级和模式。
2. 外设事件（例如 UART RX 非空、ADC 转换完成）向 DMA 控制器发出请求；内存到内存模式也可由软件启动。
3. DMA 取得总线控制权，从源地址读数据、向目标地址写数据，并更新地址和剩余计数。
4. 达到一半、全部完成或发生错误时设置标志，可产生中断通知 CPU。
5. Normal 模式停止；Circular 模式自动重新装载数量并继续。

DMA 的价值是把“每个字节一次 CPU 中断/搬运”变成“每半块或一整块处理一次”，提升吞吐并减少抖动，但它不会理解协议内容。

### 关键配置项怎么理解？

- **方向**：Peripheral-to-Memory、Memory-to-Peripheral、Memory-to-Memory。
- **地址自增**：外设数据寄存器地址通常固定；内存缓冲地址通常递增。
- **数据宽度**：外设与内存可分别选 byte/half-word/word，必须与寄存器和缓冲类型匹配，否则会截断、填充或错位。
- **Normal/Circular**：一次性报文用 Normal；ADC 连续采样、音频流常用 Circular。
- **优先级**：多个 DMA 请求冲突时决定仲裁顺序，不代表一定能抢占已经开始的总线传输。
- **Burst/FIFO/双缓冲**：高性能 DMA 可能支持，可减少总线事务或让两个缓冲交替工作，具体依 MCU。

### DMA 双缓冲如何避免数据被覆盖？

最常见的是 ping-pong：DMA 写缓冲 A 时 CPU 处理 B，随后交换。Circular 单缓冲也可用 Half-Transfer/Transfer-Complete 把数组分成前后两半。

```text
DMA 写前半 → HT 中断：CPU 处理前半，同时 DMA 写后半
DMA 写后半 → TC 中断：CPU 处理后半，同时 DMA 回到前半
```

CPU 必须在 DMA 再次写到该区域前处理完成；若最坏处理时间大于半缓冲填充时间，就要增大缓冲、降低数据率或优化处理。ISR 中只交接缓冲所有权，耗时处理放任务中。

### DMA 常见故障有哪些？

- 请求通道/触发源映射选错，DMA 根本不启动。
- 先开外设请求后配 DMA，首个数据丢失；停止时顺序错误造成尾数据问题。
- 地址、自增、宽度或长度错误导致越界和内存破坏。
- 未清旧标志、未处理 TE/FE/DME 等错误。
- CPU 与 DMA 同时读写同一缓冲，没有所有权协议或内存屏障。
- DMA 和 CPU/其他主机争用总线，实时延迟增大。
- 带 D-Cache 时，发送前未 clean 导致 DMA 读到旧数据；接收后未 invalidate 导致 CPU 仍读 Cache 旧副本。还要满足 cache line 对齐，避免破坏相邻数据。

## 5. Flash 与 SRAM

| 项目 | Flash | SRAM |
|---|---|---|
| 掉电 | 保留 | 丢失 |
| 读写 | 读可能有等待；擦写慢 | 快 |
| 写入 | 按页/扇区擦除后编程 | 直接读写 |
| 寿命 | 擦写次数有限 | 无 Flash 式寿命问题 |
| 用途 | 代码、常量、参数 | 变量、栈、堆、缓冲 |

参数保存要考虑掉电保护、版本、CRC、擦写寿命和磨损均衡。

## 6. EEPROM 与 Flash 有什么区别？如何选择？

EEPROM（不是 “E2PROM” 的另一种器件，E²PROM 就是 EEPROM 的写法）和 Flash 都属于掉电保持的非易失存储器，但擦写粒度和使用方式不同：

| 项目 | EEPROM | NOR Flash（MCU 常见） |
|---|---|---|
| 擦写粒度 | 常可按字节或小页更新 | 通常按页/扇区擦除、按字/双字/页编程 |
| 擦写寿命 | 通常高于普通 Flash，具体看器件 | 通常较低，必须看 Datasheet |
| 容量/成本 | 容量较小、单位容量成本高 | 容量大、单位容量成本低 |
| 速度 | 写入较慢，常有内部写周期 | 读取快；擦除慢且粒度大 |
| 典型接口 | I²C/SPI 或 MCU 片内 EEPROM | MCU 片内 Flash、SPI/QSPI NOR |
| 典型用途 | 少量且经常更新的参数、计数器 | 程序、资源、大块日志、较少更新的配置 |

**选择方法：**

- 几十字节到几 KB 的配置，更新频繁且希望按小粒度写：优先 EEPROM、FRAM 或专用 NVM。
- 固件、字库、图片、大块数据和 OTA 镜像：选 Flash。
- 芯片没有 EEPROM 时，可用 Flash 模拟 EEPROM，但必须做双页/日志式更新、掉电恢复、CRC、序号和磨损均衡，不能每改一个参数就反复擦同一扇区。
- 更新极频繁、掉电一致性要求高时，FRAM/MRAM 可能比两者更合适。

不要只背“EEPROM 寿命 100 万、Flash 1 万次”这类固定数字；不同工艺和型号差异很大，必须用实际器件的 endurance、retention、页写时间和工作温度规格计算寿命。

## 7. GPIO 与硬件基础

### 7.1 GPIO“八种模式”

**短答：** STM32F1 常说的 GPIO 八种模式是：浮空输入、上拉输入、下拉输入、模拟输入、通用推挽输出、通用开漏输出、复用推挽输出、复用开漏输出。新系列通常拆成 Mode、Output Type、Pull、Speed、Alternate Function 几个字段，但本质仍是在描述输入/输出类型、默认电平、驱动方式和是否交给外设。

| 模式 | 输入/输出特征 | 典型使用场景 | 注意点 |
|---|---|---|---|
| 浮空输入 | 高阻输入，无内部上下拉 | 外部电路已经提供确定电平的信号输入，如外部比较器、推挽输出传感器 | 不可悬空，否则容易受噪声影响抖动 |
| 上拉输入 | 输入 + 内部弱上拉，默认高电平 | 按键低有效、开漏输出信号的低速检测、需要默认高的输入 | 内部上拉阻值大，抗干扰和时序要求高时用外部上拉 |
| 下拉输入 | 输入 + 内部弱下拉，默认低电平 | 按键高有效、需要默认低的使能/检测信号 | 内部下拉较弱，长线或干扰环境要加外部电阻 |
| 模拟输入 | 关闭数字输入缓冲，接入模拟通道 | ADC 输入、DAC 输出相关引脚、未用引脚低功耗配置 | 数字输入关闭后不能按普通 GPIO 读电平 |
| 通用推挽输出 | MCU 主动拉高和主动拉低 | LED、片选 CS、继电器驱动前级、普通数字控制线 | 不允许两个推挽输出直接相连且输出相反电平 |
| 通用开漏输出 | 只能主动拉低，高电平靠上拉 | 线与、低速电平转换、多个器件共享中断线 | 必须有内部或外部上拉；速度受上拉电阻和总线电容影响 |
| 复用推挽输出 | 引脚交给片上外设，外设主动拉高/拉低 | UART TX、SPI SCK/MOSI、定时器 PWM、USART CK | 需要选对 AF/重映射、速度和空闲电平 |
| 复用开漏输出 | 引脚交给片上外设，外设按开漏方式驱动 | I²C SCL/SDA、SMBus | 需要上拉；多设备共享总线时不能配置成推挽 |

**使用场景怎么总结：** 普通输入看外部有没有默认电平，悬空就加上拉/下拉；模拟信号用模拟模式；普通控制信号多用推挽输出；共享线、线与、电平转换和 I²C 用开漏；外设控制的引脚用复用模式。回答时先说明具体 MCU 系列，不能把 F1 的 CRL/CRH 寄存器模型套到所有 STM32 或 HC32。

### AF（Alternate Function）复用是什么？

**短答：** AF 复用是通过芯片内部的引脚复用矩阵，把某个 GPIO 连接到 UART、SPI、I²C、Timer、ADC 等片上外设，由外设逻辑接管该引脚的输入/输出，而不是让 CPU 逐次读写 GPIO。

一个引脚通常有多个候选功能，例如同一个管脚可能既能做普通 GPIO，也能做 `USART_TX`、`SPI_SCK` 或 `TIM_CHx`；同一外设也可能有多个候选引脚。AF 编号不是通用常量，必须查具体 MCU 的 Datasheet 引脚复用表。

**典型配置顺序：**

1. 查引脚复用表，确认该管脚支持目标外设、AF 编号和是否与 SWD/JTAG、晶振或其他功能冲突。
2. 使能 GPIO 端口和目标外设的时钟。
3. 把 GPIO 的 Mode 设为 Alternate Function，而不是普通 Input/Output。
4. 设置 Output Type、Pull、Speed；例如 I²C 通常为开漏+上拉，SPI SCK/MOSI 通常为推挽。
5. 把 AFR/复用选择寄存器写成对应 AF 值（新系列常分 `AFRL` 与 `AFRH`；F1 常见的是重映射机制，寄存器模型不同）。
6. 初始化外设本身的波特率、时序、方向和中断/DMA，最后使能外设。
7. 用调试器读回 GPIO/AF 寄存器，再用示波器或逻辑分析仪确认引脚确实出现目标波形。

**AF 与 GPIO 的关系：** AF 只决定“谁控制引脚”，不自动决定电气属性。复用成功但推挽/开漏、上下拉、速度或空闲电平配置错误，仍会出现无波形、总线冲突或通信错误。外设输入脚通常需要配置为复用输入；外设输出脚需要复用输出；双向接口（如 I²C）由外设和开漏结构共同完成方向切换。

**常见故障：**

- AF 编号或引脚选错，外设寄存器工作但目标管脚没有波形。
- 只配置了 GPIO，没有使能外设时钟或没有开启外设。
- 选中的引脚与 DMA、定时器通道或调试接口冲突。
- 复用推挽/开漏选错，I²C 没上拉，SPI 多从机 MISO 未高阻。
- F1 的 AFIO 重映射、F4/更新系列的 AFR 配置方式混用。
- 外设初始化前后又被其他模块重新初始化 GPIO，导致 AF 被改回普通 GPIO。

### 7.2 GPIO 原理和用途

- **浮空输入**：高阻，适合外部已有确定驱动；不可长期悬空。
- **上/下拉输入**：内部弱电阻提供默认态；关键场景用外部电阻。
- **模拟输入**：关闭数字输入缓冲，供 ADC 等使用；未用引脚设模拟常可降功耗。
- **推挽输出**：主动拉高/拉低，驱动强、速度快；两个相反电平的推挽输出不能直连。
- **开漏输出**：只能拉低，输出高是释放，需上拉；适合 I²C、线与和电平转换。
- **复用功能**：引脚交给片上外设。UART TX/SPI 常用复用推挽，I²C 用复用开漏。

GPIO Speed 控制的是输出边沿/驱动速度，不是自动翻转频率。满足时序即可，过高会增加 EMI、串扰和功耗。

#### 如何初始化一个 GPIO？

**短答：** 先开 GPIO 端口时钟，再确定引脚的模式、输出类型、上下拉、速度和复用功能，写入初始输出电平，最后启用相关中断；输出引脚应尽量先设安全电平再切到输出，避免毛刺。

通用步骤：

1. 根据原理图确认端口、引脚、电平、外部上下拉和上电安全状态。
2. 使能 GPIO 外设时钟；某些 MCU 还要解除保护或配置电源域。
3. 若为输出，先写安全初值到输出锁存寄存器，再切换输出模式。
4. 配置 Mode：Input / Output / Alternate Function / Analog。
5. 配置 Push-Pull/Open-Drain、Pull-Up/Pull-Down/No-Pull、Speed。
6. 若给外设使用，选择正确 Alternate Function，并先配置对应外设时钟。
7. 若为外部中断，配置 EXTI 映射、边沿、清 Pending，并设置 NVIC 优先级和使能。
8. 读取输入或翻转输出验证；关键高速信号用示波器检查电平和边沿。

以 STM32 HAL 的 LED 推挽输出为例（型号对应头文件和宏需按工程修改）：

```c
__HAL_RCC_GPIOA_CLK_ENABLE();

/* 先给安全初值，防止切成输出时短暂误动作 */
HAL_GPIO_WritePin(GPIOA, GPIO_PIN_5, GPIO_PIN_RESET);

GPIO_InitTypeDef gpio = {0};
gpio.Pin   = GPIO_PIN_5;
gpio.Mode  = GPIO_MODE_OUTPUT_PP;
gpio.Pull  = GPIO_NOPULL;
gpio.Speed = GPIO_SPEED_FREQ_LOW;
HAL_GPIO_Init(GPIOA, &gpio);
```

寄存器开发的本质也相同：使能 RCC 时钟，修改 MODER/CRL/CRH、OTYPER、PUPDR、OSPEEDR、AFR 等寄存器，再通过 BSRR 等原子置位/复位寄存器控制输出。寄存器名称随系列变化。

> [!warning] 初始化常见错误
> 忘开端口时钟、选错 AF、开漏无外部上拉、输入悬空、速度设得过高、5 V 信号接到非 5 V-tolerant 引脚、按键中断未消抖，以及配置输出后才写安全电平造成上电毛刺。

# 六、常用的模块设计

## 1. BIOS 的设计

**短答：** 嵌入式项目里说的 BIOS 通常不是 PC 上的 BIOS，而是板级基础初始化层，职责接近 BSP 或 Board Init：把时钟、电源、引脚复用、基础外设、外部存储、调试口和板级资源先初始化到可用状态，再向上层驱动和应用提供稳定接口。

```text
Reset_Handler
  ↓
SystemInit：FPU、向量表、基础时钟
  ↓
搬 .data、清 .bss、初始化运行库
  ↓
BIOS/BSP_Init：板级硬件基础初始化
  ↓
Driver_Init：外设驱动初始化
  ↓
App_Init / RTOS task create
  ↓
启动调度器或进入主循环
```

### BIOS 层应该负责什么？

| 模块 | BIOS 层职责 | 不应该放什么 |
|---|---|---|
| 时钟与电源 | 配置系统时钟、外设时钟、PLL、低功耗域、复位原因读取 | 业务策略和应用状态机 |
| GPIO/PinMux | 统一配置引脚复用、上下拉、速度、默认安全电平 | 到处散落的临时引脚初始化 |
| 基础通信 | 初始化调试串口、日志口、必要的 I²C/SPI 片选和总线恢复 | 具体传感器协议解析 |
| 存储资源 | 初始化片内 Flash 参数区、QSPI、EXMC/LocalBus 等板级存储接口 | 文件格式、业务数据结构 |
| 中断与优先级 | 配置 NVIC 优先级分组、关键中断优先级、系统 tick 基础 | 在 ISR 中处理复杂业务 |
| 板级服务 | 提供 LED、按键、蜂鸣器、电源使能、硬件版本读取等基础 API | 上层 UI、通信协议、产品逻辑 |

### BIOS、驱动层、应用层怎么分？

| 层级 | 关注点 | 例子 |
|---|---|---|
| BIOS/BSP | 这块板子“有什么硬件、怎么上电可用” | `BSP_ClockInit()`、`BSP_PinMuxInit()`、`BSP_DebugUartInit()` |
| Driver | 某个外设或器件“怎么操作” | `spi_transfer()`、`flash_read()`、`lcd_write_cmd()` |
| Service/Middleware | 多个驱动组合成通用服务 | 参数存储、日志系统、通信协议栈、OTA |
| Application | 产品业务流程 | 采集任务、控制算法、菜单逻辑、联网状态机 |

分层的核心是依赖方向清楚：应用可以调用服务，服务可以调用驱动，驱动可以依赖 BIOS 提供的底层资源；BIOS 不应该反过来依赖具体业务。这样换板、换芯片或改外设引脚时，改动主要集中在 BIOS/BSP 层。

### BIOS 初始化顺序怎么设计？

1. **先安全态**：复位后尽快把电机使能、片选、功率开关等危险输出放到安全电平。
2. **再基础时钟**：配置系统时钟、Flash wait state、PLL、总线分频，确认 `SystemCoreClock` 正确。
3. **再引脚复用**：按原理图统一配置 GPIO、AF、上下拉、速度，避免外设初始化时引脚还处于错误状态。
4. **再基础外设**：初始化调试串口、系统 tick、DMA、必要的 I²C/SPI/UART 基础总线。
5. **再板级器件**：初始化电源管理、外部 Flash、EXMC/LocalBus、传感器复位脚等板上资源。
6. **最后交给应用**：BIOS 只报告初始化结果，不直接进入业务循环。

### 错误处理怎么做？

- 初始化函数要有返回值或错误码，不能全部默认成功。
- 关键外设失败时要记录错误来源，例如时钟失败、外部晶振失败、Flash ID 错、I²C 总线被拉低。
- 调试阶段可 `assert` 或停在错误码；量产固件应能降级、重试或进入安全模式。
- 启动日志尽量输出芯片型号、时钟、复位原因、固件版本、硬件版本和关键外设自检结果。

### 面试怎么说？

可以这样答：

> 我会把 BIOS/BSP 层当成板级硬件适配层来设计。它负责时钟、电源、PinMux、基础外设、外部存储和板级资源初始化，对上提供稳定 API；具体器件读写放在 Driver 层，参数存储、日志、OTA 放在 Service 层，产品流程放在 Application 层。这样硬件改版时主要改 BIOS，业务代码不需要到处改引脚和寄存器。

> [!warning] 常见坑
> BIOS 层最容易变成“什么都往里塞”的杂物层。判断标准很简单：如果这段代码和产品业务强相关，就不该放 BIOS；如果它描述的是板子上电后硬件如何进入可用状态，才适合放 BIOS/BSP。

## 2. PID 温控设计

**短答：** PID 温控是根据目标温度和当前温度的误差，计算加热或制冷输出。P 负责按当前误差快速响应，I 负责消除长期静差，D 负责根据变化趋势提前抑制过冲。温控对象通常惯性大、延迟明显，所以工程上还要做输出限幅、积分限幅、死区、滤波、采样周期固定和安全保护。

```text
目标温度 setpoint
  ↓
误差 e = setpoint - current_temperature
  ↓
PID：P + I + D
  ↓
输出限幅 / PWM 占空比 / SSR 周期控制
  ↓
加热器或制冷器
  ↓
温度传感器采样反馈
```

### 参数含义是什么？

| 参数 | 含义 | 调大后的效果 | 过大风险 |
|---|---|---|---|
| `Kp` | 比例系数，误差越大输出越大 | 响应更快，升温更有力 | 过冲、振荡、目标附近来回跳 |
| `Ki` | 积分系数，累积历史误差 | 消除稳态误差，例如一直差 1~2 ℃ 上不去 | 积分饱和，过冲变大，恢复慢 |
| `Kd` | 微分系数，根据误差变化率提前刹车 | 抑制快速变化，减小过冲 | 放大温度噪声，输出抖动 |
| `Ts` | PID 采样周期 | 固定周期后参数才有意义 | 周期不稳会导致控制效果漂移 |
| `out_min/out_max` | 输出上下限 | 限制 PWM、功率或阀门开度 | 不限幅可能损坏执行器或积分失控 |
| `integral_min/integral_max` | 积分限幅 | 防止积分项长期累积过大 | 不限幅会出现 windup，超调后很久拉不回来 |
| `deadband` | 目标附近死区 | 减少继电器/PWM 在目标附近频繁动作 | 死区过大会留下明显温差 |

常见位置式 PID：

```text
u(k) = Kp * e(k) + Ki * sum(e) * Ts + Kd * (e(k) - e(k-1)) / Ts
```

嵌入式里不要只背公式。实际代码要明确温度单位、输出单位、采样周期、输出限幅、积分是否限幅、传感器滤波和执行器类型。继电器或 SSR 常用时间比例控制；MOS 管、风扇、半导体制冷片常用 PWM 或电流控制。

### PID 温控怎么调参？

**短答：** 先关掉 I、D，只调 P 到响应够快但不过度振荡；再逐步加 I 消除静差；最后少量加 D 抑制过冲。每次只改一个参数，并记录曲线：上升时间、超调量、稳定时间、稳态误差和输出占空比。

1. **确认方向**：加热系统中温度低于目标时输出应增大；制冷系统相反。方向错了会越控越远。
2. **固定采样周期**：例如 100 ms、500 ms 或 1 s，温控系统通常不需要很高频。
3. **只开 P**：`Ki = 0`、`Kd = 0`，从小到大调 `Kp`，直到升温速度合适但目标附近没有持续大振荡。
4. **加 I**：逐步增加 `Ki`，让长期偏差收敛到 0；同时加积分限幅和输出饱和时的 anti-windup。
5. **少量加 D**：如果过冲明显，再加一点 `Kd`；温度采样噪声大时优先对测量值滤波，不要盲目加 D。
6. **分段验证**：低温启动、接近目标、保温、开盖/风冷扰动、负载变化、断电重启都要测。

> [!tip] 面试回答重点
> 调参不是凭感觉改三个数，而是看曲线。先看控制方向和采样周期，再看 P 的响应速度、I 的静差消除、D 的过冲抑制，最后用限幅、死区、滤波和安全保护把系统做稳。

### 目标温度附近跳变过大怎么办？

目标附近跳变大，通常不是单纯“PID 不好”，要同时检查测量、控制参数和执行器。

| 可能原因 | 现象 | 处理方法 |
|---|---|---|
| `Kp` 过大 | 刚到目标附近就来回冲，输出在高低之间大幅变化 | 降低 `Kp`，或使用接近目标时的分段 `Kp` |
| `Ki` 过大或积分饱和 | 超过目标后仍继续加热，过一会又反向修正 | 降低 `Ki`，加积分限幅、积分分离、输出饱和时暂停积分 |
| `Kd` 放大噪声 | 温度读数小抖动，输出大幅抖动 | 降低 `Kd`，对温度做滑动平均/一阶低通，D 项对测量值微分 |
| 采样噪声大 | 温度曲线毛刺多，实际温度未必跳 | 检查 ADC、传感器接线、滤波电容、参考电压、数字滤波 |
| 执行器粒度太粗 | 继电器/加热片一开就过量 | 降低最小输出功率，缩短 SSR 控制周期，改 PWM 或分级功率 |
| 热惯性和延迟大 | 关加热后温度还继续上冲 | 提前降功率，增加前馈或接近目标时限功率 |

常用工程处理：

- **死区控制**：例如目标 `60 ℃`，`59.8~60.2 ℃` 内保持输出不变或输出为低功率。
- **积分分离**：误差很大时不用 I，只在接近目标时启用积分，避免升温阶段积分堆太多。
- **输出斜率限制**：限制 PWM 占空比每秒变化量，避免功率突变。
- **分段 PID**：离目标远时用较大输出快速升温，接近目标时降低 `Kp/Ki`。
- **滤波但不拖太慢**：温度可以低通滤波，但滤波太重会增加延迟，反而更容易过冲。

### 温度一直上升，距目标温度越来越远，再收敛是什么原因？

这种现象要分两种看：如果目标是加热到某温度，温度在接近目标后继续上升、偏差越来越大，然后慢慢回落收敛，常见原因是 **热惯性、控制延迟或积分 windup**；如果温度一开始就朝反方向跑，优先怀疑 **控制方向错**。

| 场景 | 判断方法 | 常见原因 | 处理方法 |
|---|---|---|---|
| 接近目标后继续上冲，之后回落 | 输出已经降低或关断，但温度还在升 | 加热器余热、热传导延迟、传感器离热源远 | 接近目标提前限功率，加 D 或前馈，优化传感器位置 |
| 输出长时间打满，到目标后仍不收 | 查看 I 项是否很大 | 积分 windup，升温阶段误差累积过多 | 积分限幅、积分分离、输出饱和时停止积分 |
| 温度越控越远，输出方向也越来越大 | 加热时温度高于目标仍继续加热，或制冷方向相反 | 正负号写反、执行器方向配置错、传感器映射错 | 先做开环测试，确认输出增大到底会让温度升还是降 |
| 先远离再收敛但周期很长 | 输出变化滞后于温度变化 | 采样周期太长、滤波太重、D 项缺失 | 缩短采样周期，降低滤波滞后，增加预测/微分抑制 |

定位时建议先画四条曲线：目标温度、实际温度、PID 输出、P/I/D 三项。只看温度曲线容易误判；看到输出和积分项后，基本能区分是参数问题、方向问题、传感器问题还是热惯性问题。

### 面试怎么说？

可以这样答：

> 我做 PID 温控会先确认控制方向和采样周期，再从 P 开始调。P 决定响应速度，I 消除稳态误差，D 抑制快速变化和过冲。温控系统惯性大，所以必须做输出限幅、积分限幅和 anti-windup。目标附近跳变大时，我会先看温度曲线和输出曲线，通常从降低 Kp/Ki、加死区、积分分离、滤波和输出斜率限制入手。如果温度到目标后还继续上升再收敛，多半是热惯性或积分饱和，需要提前降功率和限制积分；如果温度一开始朝反方向跑，就先查控制方向和传感器映射。

> [!warning] 常见坑
> PID 参数不能脱离采样周期和输出单位讨论。同一组 `Kp/Ki/Kd`，采样周期变了，控制效果也会变；温控对象延迟大，盲目加大 `Kp` 或 `Ki` 往往只会让目标附近振荡更严重。

## 3. 状态机设计

**短答：** 状态机是把系统行为拆成有限个状态，系统根据当前状态和收到的事件决定执行什么动作、转移到哪个状态。它适合描述通信流程、设备启停、按键交互、升级流程和故障恢复，能替代大量相互嵌套的 `if/else` 和阻塞式流程。

状态机通常包含以下要素：

| 要素 | 含义 | 示例 |
|---|---|---|
| 状态 State | 系统当前所处阶段 | 空闲、启动、运行、故障 |
| 事件 Event | 触发判断的输入 | 启动命令、超时、数据到达、传感器异常 |
| 条件 Guard | 是否允许转移的附加条件 | 电压正常、温度未超限、权限校验通过 |
| 动作 Action | 转移时要执行的操作 | 开启电机、发送报文、保存参数 |
| 转移 Transition | 当前状态收到事件后的下一状态 | 空闲 + 启动命令 -> 启动 |

```text
Idle ──启动命令──→ Starting ──启动成功──→ Running
 ↑                    │                       │
 │                    │启动失败/超时          │停止命令
 │                    ↓                       ↓
 └──故障清除/复位── Fault             Stopping
                      ↑                       │
                      └────任意状态故障        └──停止完成──→ Idle
```

设计前先列状态转移表，比直接写代码更容易发现遗漏：

| 当前状态 | 事件 | 条件 | 动作 | 下一状态 |
|---|---|---|---|---|
| `IDLE` | `EV_START` | 自检正常 | 启动硬件，记录开始时间 | `STARTING` |
| `STARTING` | `EV_READY` | 无 | 允许正常输出 | `RUNNING` |
| `STARTING` | `EV_TIMEOUT` | 无 | 关闭输出，记录故障 | `FAULT` |
| `RUNNING` | `EV_STOP` | 无 | 发起停止 | `STOPPING` |
| 任意非故障状态 | `EV_FAULT` | 无 | 立即进入安全输出 | `FAULT` |
| `FAULT` | `EV_RESET` | 故障已消除 | 清故障，重新初始化 | `IDLE` |

### 状态机如何实现？

状态较少时，使用 `enum + switch` 最直观；状态和事件很多、规则需要配置时，可以使用二维表或转移表驱动。无论哪种方式，都应把状态变量、事件入口和硬件动作的边界定义清楚。

```c
typedef enum {
    STATE_IDLE,
    STATE_STARTING,
    STATE_RUNNING,
    STATE_STOPPING,
    STATE_FAULT,
} state_t;

typedef enum {
    EVENT_NONE,
    EVENT_START,
    EVENT_READY,
    EVENT_STOP,
    EVENT_TIMEOUT,
    EVENT_FAULT,
    EVENT_RESET,
} event_t;

typedef struct {
    state_t state;
    uint32_t state_enter_tick;
    uint32_t fault_code;
} machine_t;

static void machine_transition(machine_t *machine, state_t next, uint32_t now)
{
    /* 统一处理旧状态退出动作。 */
    if (machine->state == STATE_RUNNING) {
        output_disable();
    }

    machine->state = next;
    machine->state_enter_tick = now;

    /* 统一处理新状态进入动作。 */
    if (next == STATE_STARTING) {
        hardware_start();
    } else if (next == STATE_RUNNING) {
        output_enable();
    } else if (next == STATE_STOPPING) {
        hardware_stop();
    } else if (next == STATE_FAULT) {
        output_enter_safe_state();
    }
}

void machine_handle(machine_t *machine, event_t event, uint32_t now)
{
    if (event == EVENT_FAULT && machine->state != STATE_FAULT) {
        machine_transition(machine, STATE_FAULT, now);
        return;
    }

    switch (machine->state) {
    case STATE_IDLE:
        if (event == EVENT_START && self_test_ok()) {
            machine_transition(machine, STATE_STARTING, now);
        }
        break;

    case STATE_STARTING:
        if (event == EVENT_READY) {
            machine_transition(machine, STATE_RUNNING, now);
        } else if ((uint32_t)(now - machine->state_enter_tick) >= START_TIMEOUT_MS) {
            machine->fault_code = FAULT_START_TIMEOUT;
            machine_transition(machine, STATE_FAULT, now);
        }
        break;

    case STATE_RUNNING:
        if (event == EVENT_STOP) {
            machine_transition(machine, STATE_STOPPING, now);
        }
        break;

    case STATE_STOPPING:
        if (hardware_stopped()) {
            machine_transition(machine, STATE_IDLE, now);
        }
        break;

    case STATE_FAULT:
        if (event == EVENT_RESET && fault_is_cleared()) {
            machine->fault_code = 0;
            machine_transition(machine, STATE_IDLE, now);
        }
        break;

    default:
        machine->fault_code = FAULT_INVALID_STATE;
        machine_transition(machine, STATE_FAULT, now);
        break;
    }
}
```

这段代码不使用 `delay` 等待，而是每次被主循环或任务调用时向前推进一步。`(uint32_t)(now - start)` 的写法在无符号 tick 正常回绕时仍能计算经过时间，前提是超时时间小于计数器量程的一半。

### 状态机设计的注意事项

1. **状态和事件要正交。** “运行中”是状态，“收到停止命令”是事件；不要把瞬时事件定义成长时间状态。
2. **禁止在状态处理中阻塞等待。** 等待设备、通信响应或时间到期都应转成状态和事件，用 tick、定时器或 RTOS 超时推进。
3. **中断只产生事件。** ISR 读取必要数据后写入队列、环形缓冲或事件标志，由主循环或任务驱动状态机，避免在中断里直接切换复杂业务状态。
4. **不能只用一个布尔标志承接高频事件。** 多次事件会被合并，应使用计数器或队列；队列满时要定义丢弃、覆盖或进入故障的策略。
5. **进入、运行、退出动作要分清。** 一次性初始化放进入动作，周期处理放状态内部，资源释放放退出动作，避免每次调度重复初始化。
6. **所有等待状态必须有超时。** 通信无响应、传感器未就绪或执行器卡住时，要能进入重试、降级或故障状态。
7. **非法状态和非法转移必须可控。** `default` 应进入安全状态并记录原因，不能静默继续运行。
8. **多个上下文不能无保护地修改状态。** 最好让单一任务拥有状态机，其他任务和 ISR 只投递事件，避免竞态和不可重现的转移。
9. **状态过多时要拆分。** 可以使用分层状态机，把通信、设备控制和系统模式拆成独立子状态机，避免一个 `switch` 膨胀到无法维护。
10. **测试要覆盖转移而不只是状态。** 至少验证正常路径、每个超时、故障恢复、重复事件、乱序事件、队列满和 tick 回绕。

### 面试怎么说？

> 状态机是用状态、事件、条件、动作和转移来描述系统行为。我一般先画状态图和状态转移表，再用 `enum + switch` 或表驱动实现。嵌入式状态机的关键是非阻塞：等待时间和外设响应都变成事件或超时，中断只采集数据并投递事件，业务状态由一个主循环或任务统一修改。每个等待状态都要有超时，故障和非法状态要进入安全态；状态很多时再拆成分层或多个子状态机。

> [!warning] 常见坑
> 在某个状态里使用 `delay` 等待，导致整个系统无法响应；多个中断和任务直接修改同一个状态变量；只设置布尔事件导致高频事件丢失；没有超时和故障状态；进入动作每次轮询都重复执行；只画状态图却没有定义非法事件如何处理。

## 4. 升级与 OTA

**短答：** 固件升级是把设备中的旧程序替换为新程序；OTA（Over-The-Air）是通过 Wi-Fi、蜂窝网络、蓝牙等无线链路远程完成升级。串口、USB、CAN 或本地存储升级不属于 OTA，但底层的镜像校验、Flash 写入、启动切换和失败恢复理念基本相同。

升级系统的目标不只是“把新固件写进去”，而是保证整个过程：

| 核心理念 | 要解决的问题 |
|---|---|
| 完整性 | 镜像在下载、存储和写入过程中是否损坏 |
| 真实性 | 镜像是否确实由可信发布方签发，而不是被伪造 |
| 可恢复性 | 下载中断、掉电或写入失败后，设备还能否启动和重试 |
| 可回滚性 | 新版本启动失败或运行异常时，能否回到可用旧版本 |
| 兼容性 | 镜像是否适配当前硬件型号、分区布局和 Bootloader 版本 |
| 可追踪性 | 能否知道设备当前版本、升级阶段、失败原因和重试次数 |

Bootloader 应尽量小、稳定、少修改，负责选择和校验可启动镜像；App 负责联网、检查版本和下载镜像。不要让“下载完成”直接等于“升级成功”，新镜像至少还要经历完整校验、启动验证和业务确认。

### 典型升级流程

```text
服务器发布版本和签名信息
        ↓
设备检查硬件型号、版本策略和升级条件
        ↓
分块下载到暂存区或非活动分区，支持超时与断点续传
        ↓
校验长度、版本、Hash/CRC 和数字签名
        ↓
原子地写入“待升级/待试运行”标志并重启
        ↓
Bootloader 再次校验镜像，切换到新 App
        ↓
新 App 在限定时间内完成自检并确认版本
        ↓
确认成功：固化新版本；确认失败：回滚旧版本
```

常见存储方案：

| 方案 | 优点 | 风险与适用场景 |
|---|---|---|
| 单分区覆盖升级 | 占用 Flash 少 | 擦写中掉电容易变砖，必须有不可破坏的恢复 Bootloader 或外部恢复通道 |
| A/B 双分区 | 新旧镜像同时保留，切换和回滚可靠 | Flash 占用大，适合空间充足、可靠性要求高的产品 |
| 内部 App + 外部 Flash 暂存 | MCU 内部 Flash 压力较小，可先完整下载再搬运 | 需要额外存储器，搬运阶段仍要处理掉电恢复 |

镜像通常带有头部元数据，例如魔数、产品/硬件型号、固件版本、镜像长度、入口或加载地址、构建信息、Hash、签名和头部版本。Bootloader 必须先验证边界和兼容性，再根据长度计算校验，不能信任镜像头中的任意地址和长度。

### 升级与 OTA 的常见问题

| 常见问题 | 可能后果 | 处理思路 |
|---|---|---|
| 下载断线、丢包、乱序或重复包 | 镜像不完整，反复重下 | 分块编号、长度检查、超时重传、断点续传，完整镜像最终校验 |
| 擦写 Flash 时突然掉电 | App 或升级标志处于半写状态 | A/B 分区、暂存区、双份元数据；状态更新使用带版本号和 CRC 的原子提交 |
| 只做 CRC，不做签名 | 能发现误码，但无法阻止恶意伪造 | CRC/Hash 检查完整性，数字签名验证真实性；密钥和信任根要受保护 |
| 新 App 启动后立即确认成功 | 潜在故障版本无法自动回滚 | 设置试运行状态，完成时钟、外设、通信和关键业务自检后再确认 |
| 新 App 反复复位 | 设备陷入启动循环 | Bootloader 记录启动次数和确认超时，超过阈值自动回滚或进入恢复模式 |
| 版本或硬件不匹配 | 外设异常，严重时无法启动 | 校验产品 ID、硬件版本、分区布局、最低 Bootloader 版本和升级路径 |
| Bootloader 与新镜像格式不兼容 | Bootloader 无法解析或跳转 | 镜像头和升级协议带版本；Bootloader 保持向后兼容，必要时设计分阶段升级 |
| 链接地址、向量表或栈顶错误 | 跳转后 HardFault | App 按分区地址链接；跳转前设置 `VTOR`、加载 MSP、取复位向量并清理相关外设状态 |
| 参数结构随版本变化 | 新程序读取旧参数异常 | 参数带版本和 CRC，提供迁移与默认值策略；升级失败时避免破坏旧版本所需参数 |
| 看门狗、Cache、中断或 DMA 未处理 | 搬运超时、数据不一致或跳转异常 | 分块擦写并合理喂狗；按芯片处理 Cache；跳转前关闭或复位相关中断、DMA 和外设 |
| Flash 空间不足或分区越界 | 覆盖 Bootloader、参数区或其他镜像 | 下载前检查镜像长度，写入时逐块检查地址范围，并锁定 Bootloader 区域 |
| 允许任意降级 | 已修复的漏洞重新出现，数据格式不兼容 | 设计防回滚版本计数；维修降级使用受控授权，不能只比较版本字符串 |

升级状态本身也应设计成状态机，例如 `IDLE -> DOWNLOADING -> VERIFYING -> PENDING -> TESTING -> CONFIRMED`，任一阶段失败转入 `FAILED` 或恢复状态。状态要持久化时，应考虑 Flash 擦写寿命、掉电一致性和重复执行的幂等性。

### 面试怎么说？

> 我理解升级系统的重点不是把固件传过去，而是保证镜像可信、过程可恢复、失败可回滚。一般由 App 下载到暂存区或非活动分区，先检查型号、版本、长度、Hash 和签名，再写待升级标志并重启；Bootloader 重新校验后启动新镜像，新 App 通过自检后才确认成功，否则按超时或启动次数回滚。常见问题主要是断网、掉电、Flash 越界、镜像不兼容、参数迁移失败和新版本启动循环，所以要用 A/B 或安全暂存、原子状态记录、试运行确认和恢复入口来避免变砖。

> [!warning] 常见坑
> 把 CRC 当成安全认证；边下载边覆盖唯一可启动 App；升级标志只写一个字节且不考虑掉电；新版本一启动就确认；只校验版本号不校验硬件型号；Bootloader 信任镜像提供的长度和地址；没有保留串口、USB、按键或网络恢复入口。

## 5. CRC 与 Hash 校验

**短答：** CRC 和 Hash 都能把一段任意长度的数据映射成固定长度的校验值，用于判断数据是否发生变化。CRC 主要针对通信和存储中的随机误码，计算快、硬件实现简单；密码学 Hash 更强调单向性、抗碰撞和雪崩效应，适合大文件指纹、固件完整性和安全协议，但单独使用仍不能证明数据来自谁。

常见校验方式可以先这样区分：

| 方法 | 基本思路 | 主要用途 |
|---|---|---|
| 奇偶校验 | 统计 1 的个数是奇数还是偶数 | 低成本发现部分单比特错误 |
| 累加和/Checksum | 对所有字节求和后截断或取反 | 简单协议、资源极少或兼容旧格式 |
| CRC | 对比特串做 GF(2) 多项式除法，取余数 | 通信帧、Flash 数据块和存储传输误码检测 |
| Hash | 通过多轮非线性压缩得到固定长度摘要 | 文件指纹、固件完整性、签名和 HMAC 的基础 |

### CRC 的基本原理

CRC（Cyclic Redundancy Check，循环冗余校验）把数据比特串看成二进制多项式，使用双方约定的生成多项式做模 2 除法，最后的余数就是 CRC。模 2 运算只有异或，没有进位和借位。

以宽度为 `r` 的 CRC 为例：

1. 发送方在原始数据末尾补 `r` 个 0。
2. 用生成多项式对补零后的数据做模 2 除法。
3. 取 `r` 位余数作为 CRC，随数据一起发送或保存。
4. 接收方使用完全相同的 CRC 模型重新计算，与收到的 CRC 比较；不一致说明数据发生了变化。

```text
原始数据 ──补零/逐位异或除法──→ CRC 余数
   │                                │
   └──────── 数据 + CRC ────────────┘
                    ↓
          接收端按同一模型重新计算
                    ↓
             相等：通过；否则：错误
```

CRC 不是只看“CRC-16”或“CRC-32”就能确定算法，双方必须统一全部参数：

| 参数 | 含义 |
|---|---|
| `width` | CRC 结果宽度，例如 16 位或 32 位 |
| `poly` | 生成多项式 |
| `init` | CRC 寄存器初始值 |
| `refin/refout` | 输入字节和输出结果是否按位反射 |
| `xorout` | 最终结果异或值 |
| 字节顺序 | 多字节 CRC 在线路或文件中的高低字节排列 |

CRC 对突发错误特别有效。设计合适的 `r` 阶生成多项式通常能发现长度不超过 `r` 位的全部突发错误，也能以很高概率发现更长的随机错误。但 CRC 位数有限，碰撞一定存在，而且攻击者可以修改数据后重新计算 CRC，因此它不是安全算法。

### Hash 的基本原理

Hash 将任意长度输入映射成固定长度摘要。密码学 Hash 通常先对输入填充并分块，再让每个数据块经过多轮非线性混合和压缩，前一块的内部状态参与后一块计算，最终输出摘要。例如 SHA-256 无论输入多长，都输出 256 bit，也就是 32 byte。

理想的密码学 Hash 具有以下特性：

- **确定性**：相同输入一定得到相同摘要。
- **单向性**：已知摘要，很难反推出原文。
- **抗第二原像**：给定一份数据，很难找到另一份具有相同摘要的数据。
- **抗碰撞**：很难主动找到两份摘要相同的不同数据。
- **雪崩效应**：输入只改变 1 bit，输出也会发生大范围、不可预测的变化。

Hash 不是加密：它没有“解密还原原文”的过程。Hash 也不是绝对不会碰撞，而是使用足够长且仍安全的算法后，在工程上很难找到可利用的碰撞。安全场景应优先使用 SHA-256、SHA-384 等当前适用的密码学 Hash，不应继续把 MD5、SHA-1 用于抗攻击的完整性判断。

### CRC 与 Hash 的区别

| 对比项 | CRC | 密码学 Hash |
|---|---|---|
| 主要目标 | 检测随机误码 | 生成难以伪造和碰撞的内容摘要 |
| 数学结构 | GF(2) 线性多项式运算 | 多轮非线性混合与压缩 |
| 常见长度 | 8、16、32、64 bit | 256、384、512 bit |
| 计算开销 | 很低，MCU 常带 CRC 硬件单元 | 较高，可用软件或密码硬件加速 |
| 随机错误检测 | 很适合，尤其是突发错误 | 能检测，但成本通常更高 |
| 抗恶意修改 | 不具备，修改后可轻易重算 | 摘要本身较难构造碰撞，但无密钥时仍可被整体替换 |
| 典型场景 | 通信帧、配置块、Flash 页、传感器数据 | 固件镜像、文件指纹、数字签名、HMAC |

选择原则：

- UART、RS-485、CAN 上的自定义短帧，需要快速发现链路误码：常用 CRC-16 或 CRC-32。
- Flash 参数、升级状态等小数据块，需要发现掉电或存储损坏：使用版本号、长度和 CRC，并配合双备份或原子提交。
- 大型固件下载，需要确认整份文件与服务器发布内容一致：使用 SHA-256 等 Hash；分块 CRC 可用于快速定位和重传坏块。
- 需要确认通信双方共享同一密钥且消息未被篡改：使用 HMAC，不是简单的 `Hash(key + data)`。
- 需要让设备验证固件确实由发布方签发：对固件 Hash 做数字签名，设备用内置公钥验签。

### CRC 或 Hash 能保证数据可信吗？

**不能单独保证。** CRC 只能有效发现随机错误；普通 Hash 虽然抗碰撞能力强，但没有秘密信息。攻击者如果能同时替换固件和旁边保存的 Hash，就可以给恶意固件重新计算一个正确 Hash。

```text
CRC / Hash                  → 数据有没有变化？
HMAC（双方共享密钥）         → 数据是否来自持有同一密钥的一方？
数字签名（私钥签名、公钥验证） → 数据是否来自可信发布方，且是否被修改？
```

OTA 中常见的组合是：传输分块用 CRC 快速发现误码，完整镜像用 SHA-256 生成摘要，再验证摘要的数字签名。这样同时覆盖传输可靠性、整体完整性和发布者真实性。

### 使用时的常见问题

1. **算法同名但参数不同。** 两端都说 CRC-16，`poly/init/refin/xorout` 不同仍会得到不同结果，必须给出完整 CRC 模型和测试向量。
2. **校验范围不一致。** 要明确是否包含包头、长度、填充字节和 CRC 字段本身，以及从哪个地址算到哪个地址。
3. **字节序或位反射不一致。** 线上的 CRC 高低字节顺序与 CPU 大小端不是一回事，必须按协议显式编码。
4. **硬件 CRC 与软件结果不同。** 检查硬件输入宽度、字节重排、初值、补零规则和最后异或，不能只比较多项式。
5. **只校验分块，不校验整体镜像。** 块顺序错误、重复块或元数据被替换仍可能漏检，最后必须对完整镜像和关键元数据统一校验。
6. **校验通过后数据又被修改。** 验证完成到实际使用之间仍要保护存储区域，安全启动时应在启动链中重新验证。
7. **把 CRC、Hash 和加密混为一谈。** 校验不提供保密性，Hash 不能解密，CRC/Hash 单独也不能认证来源。

### 面试怎么说？

> CRC 是把数据看成二进制多项式，用约定的生成多项式做模 2 除法并取余数，特点是速度快、擅长检测通信和存储中的随机及突发错误，但它是线性的，不能防恶意篡改。密码学 Hash 通过多轮非线性压缩，把任意长度数据变成固定长度摘要，具有单向、抗碰撞和雪崩特性，适合固件和文件的整体完整性校验。实际 OTA 中我会用分块 CRC 做快速重传，用 SHA-256 校验完整镜像，再用数字签名确认发布者身份；只有 CRC 或普通 Hash 都不能证明固件可信。

> [!warning] 常见坑
> 只说 CRC-16 却不说明完整参数；校验范围和字节序不一致；认为 CRC 位数更长就具备安全性；认为 Hash 完全不会碰撞；把 Hash 当成加密；固件和 Hash 放在一起却没有签名或 HMAC；只校验分块而不校验完整镜像。

# 七、RTOS 与 FreeRTOS

## 1. 为什么用 RTOS？任务状态有哪些？

RTOS 用优先级任务和同步通信机制提高模块化与实时响应，代价是 RAM、切换开销和并发复杂度。简单顺序控制未必需要 RTOS。

任务状态：Running、Ready、Blocked、Suspended。单核同一时刻只有一个 Running；抢占式调度下，高优先级任务就绪后通常会抢占低优先级任务。

## 2. 上下文切换

常见 Cortex-M FreeRTOS 端口中：SysTick 提供节拍；PendSV 以最低异常优先级做切换；硬件保存基础异常栈帧，软件再把 R4~R11 等存入当前任务栈；调度器选择新任务并切换 PSP，恢复后异常返回。SVC 常用于启动第一个任务。

## 3. MSP 与 PSP

**短答：** MSP 是复位默认栈，Handler mode 始终用 MSP；PSP 只能用于 Thread mode。FreeRTOS 通常让任务各用自己的 PSP 栈，中断统一用 MSP，实现任务栈与中断栈分离。

裸机 `main()` 通常一直用 MSP。异常前线程现场压在哪个栈由当时的 SP 选择决定，可从 `EXC_RETURN` 判断。

## 4. 同步工具怎么选？

| 工具 | 用途 | 特点 |
|---|---|---|
| Queue | 传递数据 | 复制消息，可阻塞 |
| Binary Semaphore | 事件同步 | ISR 通知任务常用，无所有权 |
| Counting Semaphore | 资源/事件计数 | 可累计 |
| Mutex | 保护共享资源 | 有所有者和优先级继承，ISR 不可用 |
| Event Group | 多 bit 条件 | 等待多个事件组合 |
| Task Notification | 一对一通知 | 快、省 RAM，可传 bit/计数/值 |

大块数据可传指针，但必须明确缓冲区生命周期和所有权。

## 5. 优先级反转

低优先级任务持锁，高优先级任务等待该锁，而中优先级任务持续抢占低优先级任务，导致高优先级间接被阻塞。使用带优先级继承的 mutex、缩短临界区、禁止持锁做慢操作，必要时让专用任务独占资源。

## 6. ISR 为什么用 `FromISR` API？

ISR 不能像任务一样阻塞。`FromISR` 版本不会阻塞，并可返回是否唤醒更高优先级任务，再在退出 ISR 前请求切换。ISR 应只清标志、搬必要数据、通知任务；不应延时、大量打印、动态分配或做耗时算法。调用 API 的 ISR 还必须满足 FreeRTOS 中断优先级限制。

## 7. 如何排查任务栈？

- 开启 `configCHECK_FOR_STACK_OVERFLOW`。
- 用 `uxTaskGetStackHighWaterMark()` 看历史最小余量。
- 考虑最深调用、局部变量、库函数和 FPU；避免栈上大数组、递归和重格式化输出。
- 栈水位正常不代表不存在野指针等内存破坏。

# 八、问题定位与 HardFault

## 1. 通用定位方法

**短答：** 先稳定复现、缩小范围，再用日志、寄存器和波形建立证据链，不随机改代码。

1. 写清预期、实际、概率、版本和复现步骤。
2. 区分硬件/软件、单板/批量、温度/电压/负载、启动/运行时。
3. 保留复位原因、错误码、PC/LR/SP、Fault 寄存器和最近日志。
4. 分层查：电源/复位/时钟 → 引脚波形 → 驱动寄存器 → 协议 → RTOS/业务。
5. 二分代码/配置，换板、降频、关闭 DMA 做 A/B 对照。
6. 修复能消失、恢复错误条件能重现，才算验证根因。
7. 增加断言、超时、错误恢复、监控和回归测试。

工具选择：示波器看电压/毛刺/模拟质量；逻辑分析仪看数字协议；调试器看寄存器/调用栈；map、反汇编和 Addr2line 把地址还原到源码。

## 2. HardFault 是什么？常见原因？

HardFault 是固定高优先级故障，可能是自身原因，也可能是未使能/无法处理的 MemManage、BusFault、UsageFault 升级而来。

常见原因：空/野指针、越界、栈溢出、返回地址或函数指针损坏、非法指令/状态、非对齐访问、访问不存在/无权限地址、异常返回栈帧损坏。

## 3. HardFault 定位步骤

先根据 HardFault 入口 LR 的 `EXC_RETURN` 判断异常前使用 MSP 还是 PSP，提取硬件栈帧：

```c
typedef struct {
    uint32_t r0, r1, r2, r3, r12, lr, pc, xpsr;
} fault_stack_t;
```

重点看 stacked PC/LR 和栈边界。M4F 可能有浮点扩展栈帧/延迟压栈，不可无条件使用固定偏移。

记录：

```c
SCB->HFSR;   // FORCED 常表示其他 Fault 升级
SCB->CFSR;   // MemManage + BusFault + UsageFault 细分原因
SCB->MMFAR;  // 有效位成立时才可信
SCB->BFAR;   // 有效位成立时才可信
SCB->SHCSR;
```

- `PRECISERR`：精确总线错误，压栈 PC 通常靠近出错指令。
- `IMPRECISERR`：缓冲写等非精确错误，PC 未必是根因。
- `UNDEFINSTR/INVSTATE/INVPC/UNALIGNED/DIVBYZERO`：继续按 UsageFault 分析。

用带符号 ELF 定位：

```bash
arm-none-eabi-addr2line -e firmware.elf -f -C 0x08001234
arm-none-eabi-objdump -d -S firmware.elf
```

## 4. 通信故障快速检查表

### I²C

空闲是否双高；上拉和上升时间；API 要 7 位还是已移位地址；NACK 在地址还是数据阶段；Repeated START/最后 NACK/STOP；是否有从机持续拉低总线。

### SPI

CPOL/CPHA、位序、位宽；CS 极性与建立/保持时间；实际 SCK；MOSI/MISO；多从机 MISO 冲突；对照数据手册和逻辑分析仪。

### UART

波特率/帧格式；TX/RX 交叉、共地和电平；实际时钟误差；ORE/FE/NE/PE；DMA/环形缓冲溢出；协议长度、CRC、超时和拆包状态机。
